# Profile coverage

Chezmoi deploys every file to every profile unless `.chezmoiignore` leaves it out. A dotfiles feature targets both desktop profiles, `personal` and `axon-work-computer`, unless its design says in one line why one is left out (rule in [AGENTS.md](../AGENTS.md)).

The table lists every path that `chezmoi managed` gives to one desktop profile and not the other, with the reason. `tests/profiles/test_coverage.py` keeps it current. It fails when a one-profile path has no row, or when a row names a path that is not one-profile any more. Rows marked `reason needed (owner)` pass; the test prints how many there are.

How to read a row:

- A path covers itself and everything under it.
- `(macOS)` in the profiles column: the gate also needs `.chezmoi.os == "darwin"`; `(Linux)`: it also needs `.chezmoi.os == "linux"`. The CI job on the other OS skips those rows; the job on the matching OS checks them.
- `(Windows)` in the profiles column: a source path that chezmoi never deploys, on any system or profile, because a script run by hand on a Windows machine puts its files in place. `tests/profiles/test_coverage.py` skips these rows; `tests/profiles/test_windows_rows.py` checks that every file under `windows/` has its own row (a folder row does not count), that each row names one existing file, and that chezmoi deploys nothing under `windows/`.
- Termux is out of scope here; it has its own block in `.chezmoiignore`.
- Not covered: profile branches inside templates (`{{ if eq .profile ... }}` in about two dozen templates) and run scripts that skip themselves by profile, such as `60_configure_rustdesk.sh`. The PR body's `Profiles:` line covers those. The T3 hook in `~/.claude/settings.json` is one of them: it lands on both profiles (each with its own coordinator repo and state dir), so it needs no row.

### 1Password service-account token

The work profile reads `privatePiProviderRef` with `op` through the service account only, never the 1Password desktop app. The token comes from `OP_SERVICE_ACCOUNT_TOKEN`, or else from `~/.config/agent-harness/op-service-token` (mode 0600, outside git). The read runs the real `op` under an empty HOME, so the app cannot answer it. With no token the render stops with a message that names the token file, and nothing calls `op`. Each render reads the secret fresh and nothing is cached, so a rotated key shows up on the next render.

### Agent jobs never reach the desktop app (playbook 78819cbd)

1Password reads use the service-account token, or the homelab Connect server when a Connect token is set (see "Connect first for agent reads" below). Each script takes the service-account token from `OP_SERVICE_ACCOUNT_TOKEN`, else from `~/.config/agent-harness/op-service-token`. A caller that refuses without a token stops before it runs `op`, so `op` cannot fall back to the desktop app. The refusal text is `1Password service account token not set; refusing to use the desktop app (playbook 78819cbd)`.

**Connect first for agent reads (personal profile only).** The work profile's `~/.pi/agent/bin/op` is the service-account-only shim, byte for byte what it was before Connect routing: `dot_pi/private_agent/bin/executable_op.tmpl` renders `.chezmoitemplates/op-shim-service-account` for every profile but `personal`, so no work render can reach the homelab Connect server (`tests/pi-op-shim/test_op_shim_work_profile.py`). The work render of `refresh_op_service_account_token.sh`, `kgate` and the Pi extensions README is likewise the pre-Connect text. On personal: with a Connect token (`OP_CONNECT_TOKEN`, else `~/.config/agent-harness/op-connect-token`, mode 0600; `seed_op_connect_token.sh` writes it on personal machines), the shim sends `op read`, `op inject`, `op run` and `op item get --format json` to the homelab 1Password Connect server (`OP_CONNECT_HOST`, default `https://op-connect.internal.cartwmic.com`). If a read, item get or inject fails there, the shim retries it once on the service account and prints one stderr line that names Connect and the reason. The Connect attempt is cut off after 4 s. `op run` is never retried, because the wrapped command may already have run. `op_read_cached.sh` and `kgate` call `op` by name, so they reach Connect when the shim is first on their PATH, with no change to them. Both still refuse without a service-account token, so a Connect token does not replace it for them.

**The agent-shell rule is a heuristic, and it is easy to extend.** The markers are the ones this Mac has observed. `CODEX_SANDBOX=seatbelt` was seen in the command shell of Codex's sandbox (`codex sandbox`); it is not seen in a model-driven Codex turn. Codex sets `CODEX_THREAD_ID` in every shell it runs, sandboxed or not, so that marker covers a Codex run with its sandbox off. Edit the `agent_shell` function in both `.chezmoitemplates/op-shim-connect` and `.chezmoitemplates/op-shim-service-account` to add one.

Known gaps:
- Closed: a Codex run with its sandbox off used to set no marker and got the terminal fallback. `CODEX_THREAD_ID` now marks it as an agent shell, so the zsh name refuses without a token (playbook 78819cbd).
- A terminal started inside an agent app inherits its marker and refuses without a token. The herdr skill reads `HERDR_ENV=1` as "inside a herdr pane", so a terminal run inside herdr may be classed as an agent shell too; not checked on this Mac.
- Retro's pane shells are zsh. They refuse only if a marker is set in them; without one they keep the terminal fallback.
- A zsh started from inside Pi's bash tool (for example `zsh -c 'op whoami'`) has no marker, and `dot_zshenv` puts the zsh name first, so its `op` runs the real CLI with the desktop-app fallback. Confirmed in a scratch run: the Homebrew `op` ran (scratch HOME, no token), because `dot_zshenv` puts Homebrew ahead of the rest of the PATH.
- The shim's own refusal writes its message to stderr and no log record. The `op_read_cached.sh` refusal is logged; the shim's is not (principle 14).
- `takes_no_path` lists six subcommands (`read`, `whoami`, `item get`, `item list`, `vault list`, `account list`) and treats five option names as path options. A flag the list does not know about that takes a relative path would resolve against the op home, not the caller's directory. The list was not checked against the full flag set of each `op` release.

The human-run flows keep their own fallbacks: fresh-machine provisioning (`run_after_05_provision_ssh_keys.sh.tmpl`), the token refresh (`refresh_op_service_account_token.sh`, biometric on purpose), and the zshrc warning block.

### pi key from the environment (work profile)

pi resolves a `!command` apiKey on every model request, through `execSync` with a hard 10 s timeout. When the machine stalls under memory pressure the key command is killed before it starts, and the turn fails with "Failed to resolve API key". So on the work profile the work-glm key is read once, at pi's launch:

- `~/.local/bin/pi` (`dot_local/bin/private_executable_pi.tmpl`, mode 0700, work only; elsewhere it stays pi's installer symlink) reads the key with `op_read_cached.sh` and the `workGlmKeyRef` data key, with no 10 s limit, exports `WORK_GLM_API_KEY`, and execs pi's own launcher, `~/.pi/agent/bin/pi`.
- models.json names the work-glm key as `"$WORK_GLM_API_KEY"`. pi reads it from its own environment on each request: no subprocess.
- If the read fails, pi still starts (its other providers need no work key), with a `[pi] WARN:` line naming `WORK_GLM_API_KEY`. A work-glm request then fails at once with pi's own `No API key found for work-glm`, which does not name the variable, so the launch warning is the clue. A key already in the environment is kept.
- A rotated key needs pi sessions restarted.
- The trade-off (the owner's choice): every tool command a pi session runs inherits the variable, so an agent that dumps its environment prints the key. The leak guard's terms hold the key's prefix (machine-local data), so it is blocked from commits and from posts to guarded repositories. Transcripts and session logs are not covered.
