# leak-guard

`cartwmic/dotfiles` is a public repository, and the work machine commits to it. `leak-guard` is a git hook, on the work machine only, that checks every commit and push for work details before the change leaves the machine. A `gh` wrapper (below) runs the same check on the text of pull requests, comments, reviews, issues and release notes before it is sent to GitHub. There is no personal counterpart (see [profiles.md](./profiles.md)).

It is one script, `dot_local/bin/executable_leak-guard` (installed as `~/.local/bin/leak-guard`), run by three git hooks in the chezmoi source dir:

- `pre-commit` checks `git diff --cached`. It cannot see the commit message, and a commit with no diff (`git commit --allow-empty`) has nothing for it to read, so:
- `commit-msg` checks the message with layer 1 only (every line is scanned, `#` lines included, since `git commit -m` keeps a line that starts with `#`; only git's scissors section, `# ------------------------ >8 ------------------------` and below, which `commit -v` fills with the diff, is skipped; so a commented line that holds a term blocks at commit time, and the override is the way out). It is a separate hook because only it is given the message; layer 2 reads every pushed message at pre-push. The author and committer of a commit are checked at pre-push, which sees them.
- `pre-push` checks, in one pass, everything the push would make public that the remote's own tracking refs do not already have:

      git rev-list <pushed tips> --not --remotes=<remote> [<each remote sha present locally>] \
        | git diff-tree --stdin -r -p --cc --root --always --no-renames --no-textconv --no-ext-diff --pretty=raw

  A commit that any branch of that remote has, as last fetched, is excluded and never rechecked; a commit shared by two pushed refs is checked once; the hook never fetches. Every commit is shown even when it has no diff (`--always`), so an empty commit's message and identities are checked too. Layer 1 scans every raw header line (author, committer, `mergetag`), every message line, every path and every added line; a merge shows only the lines it introduces itself (a `--cc` prefix as wide as the parent count, so an octopus merge works). Annotated tag objects are peeled and scanned whole (tagger included); a ref that peels to a tree or a blob blocks, since nothing here can read it. Only the **remote** ref name is checked, because the local name never becomes public. Deleted refs are skipped (a push of only deletes makes no Claude call). A push to a URL is mapped back to the configured remote whose `url` or `pushurl` it is; with no match, or with no tracking refs for that remote, it blocks with "run `git fetch <remote>`, then push again" rather than scanning the whole history. If the remote is empty (no branches at all, so there is nothing to fetch), the reason says so, and the documented way to make that first push is the override, after looking it over by hand. A remote sha that is not present locally gives a notice (run `git fetch`) and the check goes on over everything the tracking refs lack. A stale tracking ref can make the check examine less, not only more (see Residuals); a `pushurl` that differs from `url`, or a custom fetch refspec, can make the exclusion wrong (this repository sets neither).

The checks look only at **added** lines and at the **names** of added, copied, modified and renamed files (a rename counts as a new name; an empty file has a name too). File, branch and tag names are also given to Claude as data. Every diff is taken with `--no-textconv` and `--no-ext-diff`, so no diff driver can hide content. Because each commit's own patch is read, a term added in one commit and removed in the next is still seen, and pre-push backstops commits made with `--no-verify`.

**Binary files.** Their names are checked like any other, but their content cannot be read, so a binary file that is added or changed blocks (after layer 1, naming the file) until you commit it with the override. Two layers, cheapest first:

1. **Terms.** `~/.config/leak-guard/terms` is one regex per line (`#` lines are comments), matched case-insensitively. A hit blocks and prints `file:line: term N`. **Term N** is the 1-based position of the term among the terms, with blank lines and `#` lines skipped. The term's text is never printed or logged: count the lines of the file yourself, in an editor, to find term N. A regex that does not compile is named the same way (`term 7 of the terms file ... is not a valid regex`).
2. **Claude.** `claude -p` with Haiku, no tools and no MCP servers, in an empty directory, gets `~/.config/leak-guard/context` (a few lines on the employer and what counts as a work detail) and the added lines, and must answer one JSON object, `{"leak": true|false, "findings": [{"file", "line", "text", "why"}]}`. `leak: true` blocks and prints the findings. An answer that is not that JSON is a block, and so is one that contradicts itself (`leak: false` with findings, or findings that are not a list) or whose result is not text. An unexpected error blocks too, with the error's type named.

It **fails closed**. It blocks, with one line naming the failing step, when the `claude` CLI is missing, you are not signed in, the network is down, the call times out (120 s), `claude` exits non-zero, the terms or context file is missing, a term is not a valid regex, or a pre-commit change is over 200 KB (nothing is truncated; commit smaller changes or override), or one line of a push is larger than a 180 KB chunk. A push that is larger than one chunk is split into chunks of about 180 KB, each its own Claude call, and every chunk must pass.

## Text mode

`leak-guard text [--result FILE] TEXTFILE...` runs both layers on the text of each file: a PR body, a comment, release notes. It is the commit-msg code path with layer 2 added. Each non-blank line is checked by layer 1 (`TEXTFILE:line: term N`, labelled by the file's base name) and then sent to Claude with the same context file, in a prompt that says the text is about to be posted publicly on GitHub. It blocks (exit 1) on a hit, on a `leak: true` answer, and on every failure the hooks fail closed on: no `claude`, no sign-in, a timeout, an unparseable answer, an unreadable file, a missing terms or context file, or more than 200 KB of text. With no file it exits 64. A file with only blank lines passes without a Claude call. The override is the same `LEAK_GUARD_SKIP="<reason>"` on the command, and it is logged. `--result FILE` also writes `{"verdict", "layer", "findings"}`, the values the log line carries, so a caller can log them.

## The gh wrapper

GitHub keeps every earlier version of an edited PR body or comment, and the API cannot delete them, so text has to be checked before it is sent. Git hooks never see it. `scripts/leak-guard-gh` is a wrapper for `gh` that does. It is installed by `run_onchange_after_47_install-leak-guard-gh.sh.tmpl` as `~/.local/share/leak-guard/bin/gh`, only on the `axon-work-computer` profile and only with `leakGuard.repos` data (below). It calls `leak-guard text` as a process and never imports it. With no `~/.config/leak-guard/repos` file it does nothing.

**Which repository.** Every one the command names, taken together: its `-R`/`--repo` values, the GitHub URLs and `OWNER/REPO` arguments (of a parsed command, its positional arguments only, so a URL inside a body text is only text), `GH_REPO`, every remote URL of the current directory's git repository (https, ssh and scp forms), and for `gh api` the endpoint path (`repos/<owner>/<repo>/...`, with or without a leading slash, `https://api.github.com/` or `https://uploads.github.com/`, on the host `--hostname` names). A command is guarded when ANY of them is a line of `~/.config/leak-guard/repos`: `owner/name` for github.com, `host/owner/name` for another host. gh prefers one source to the others (a URL beats `-R`, `-R` beats `GH_REPO`, `GH_REPO` beats the checkout) and the order differs between commands, so the wrapper does not try to reproduce it. The price is that a command with a mixed set, such as `gh pr comment -R someone/other` in a guarded checkout, is checked as if guarded; a clean text still runs. A command whose targets are all unguarded runs the real `gh` untouched. A flag stands between `gh pr` and its subcommand only when someone wrote it that way, and then a flag's value could be the subcommand: on a guarded context such a command is refused, so put the subcommand right after the group.

**What it checks, for a guarded repository.** The title and body of `pr create`, `pr edit`, `pr comment`, `issue create`, `issue edit` and `issue comment`; the body of `pr review`; the title and notes of `release create` and `release edit`; and the text flags of `pr merge` (subject, body), `pr close`, `pr reopen`, `issue close` and `issue reopen` (comment). It reads inline values (`--body`, `--notes`), `--body-file`, `-F`, and `--notes-file`, including `-` for standard input, and passes any standard input it read on to the real `gh`. A block names the part (`title`, `body`, `notes`, `comment`, `tag`, or `field N` for the Nth field of a `gh api` call), the line and the term number (`body:3: term 2`), never a temporary path or a field key.

**`gh api`.** The keys and values of `-f`, `-F`, `--raw-field` and `--field` (`key=@file` and `key=@-` are read) and the content of `--input` are checked for a write to a guarded repository; a hit in a key reads `field N key`, never the key itself. `--hostname` sets the host, so a repository on another host is not a guarded repository unless its `host/owner/name` line is in the repos file. Any field flag makes the call a write even without `-X`, because gh then sends a POST; `-X GET` and `-X HEAD` keep it a read. A GraphQL mutation names objects by node id, not by repository, so every `gh api graphql` call whose query holds a mutation is checked, for every repository and directory: the query text and every variable, from `-f`/`-F` fields or from JSON `--input`. A query that is not a mutation passes. A call it cannot parse (an unreadable query file, `--input` that is not a JSON object) is blocked. The endpoint may be a full URL (`https://api.github.com/graphql`, `https://uploads.github.com/repos/<owner>/<repo>/...`). A write to `repositories/<id>/...` names the repository only by its numeric id, which the wrapper cannot map, so it is blocked; use the `repos/<owner>/<repo>/...` form.

**Flag tables.** What a flag's next argument is depends on the flag: `-r` takes a value in `pr create` (a reviewer) and none in `pr review` (request changes), so one list for every command hides text. The wrapper keeps one table per command whose text it reads (`FLAGS` in `scripts/leak-guard-gh`: the 14 `pr`, `issue` and `release` commands, and `gh api`), copied from `gh <command> --help` of gh 2.97.0: long name, short name, and whether the flag takes a value. It parses a command's arguments with that command's table, following gh's flag library for the forms listed here (`--name value`, `--name=value`, `-x value`, `-xvalue`, `-x=value`, clusters of switches such as `-dt`, a value flag taking the next argument whatever it looks like, `--` ending the flags). A flag that is not in the table is refused for a guarded repository, named by its argument position, because the wrapper cannot tell whether it takes a value. `tests/leak-guard/test_gh_wrapper.py` (`FlagTables`) runs the installed `gh <command> --help` for every table, when gh is present, and fails when the table differs, so a gh upgrade that adds or changes a flag shows up; update `FLAGS` from the new help then.

**Blocked without a check.** Anything that makes gh write the text itself, where the wrapper cannot see it: `--fill`, `--fill-first`, `--fill-verbose`, `--template`, `--recover`, `--editor`, `--web` and `--edit-last` on the commands that take them, and, on a terminal, every command where gh would ask for text at its own prompt: `pr create` or `issue create` without a title and a body, `pr edit` or `issue edit` with no flag, `pr comment` or `issue comment` without a body, `pr review` without its type or body, `release create` without notes, and `pr merge` without a method flag (gh then asks how to merge and offers to edit the commit message). The message says to give the text with `--title` and `--body-file` (`--notes-file` for a release, `--squash` or `--merge` or `--rebase` for a merge). On top of that, the real `gh` for a guarded write always runs with `GH_PROMPT_DISABLED=1`, so it can never ask for text at a prompt the wrapper cannot see. A merge with a method flag and no text passes. A write command it does not recognise is blocked too, with the command named (`repo edit`, `label create`, `workflow run`, `agent-task`). `gh release create TAG FILE...` is blocked when it has asset files (they would be uploaded unchecked, as `release upload` is refused); the tag name is checked as text. Read commands (`pr list`, `pr view`, `run list`, ...), write commands that carry no free text (`pr ready`, `run rerun`, ...) and every command for an unguarded repository run the real `gh` with the same arguments, the same standard input and its exit code, and `leak-guard` does not run.

**Aliases and extensions.** A name that is no built-in gh command is looked up with the real `gh alias list`, whose `name: expansion` lines are parsed exactly (a line it cannot parse refuses the command). An alias is expanded the way gh expands it (`$1`, `$2` and the appended arguments) and the expansion is classified like a typed command, so `prc = pr create --fill` is blocked and an alias with `-R <guarded>` built in is checked from any directory. A shell alias (`!...`) aimed at a guarded repository is refused. A name that is no alias is an extension; aimed at a guarded repository it is refused as an unrecognised write. Only a built-in read, or a bare built-in group with no arguments (`gh pr`, which prints help), passes without a check. `--help` and `-h` count as help only when they are flags of the command, not a flag's value.

**Fail closed.** `leak-guard` missing, not runnable or exiting non-zero blocks the command, and so does anything that makes `leak-guard text` block. A wrapper that cannot run at all (a broken `python3`, a syntax error in the installed file) fails every `gh` call, reads included; that is deliberate. A `gh` killed by a signal exits with the shell's 128 plus the signal number. The real `gh` is the first `gh` on PATH that is not the wrapper: copies, symlinks to it and a repeated directory are skipped, so it cannot run itself. With no real `gh` it exits 127.

**Override and log.** `LEAK_GUARD_SKIP="<reason>" gh ...` skips the check for that command (wrapper-only blocks too) and is logged. The wrapper appends one line per guarded command it checks or blocks, and per GraphQL mutation, to the same `log.jsonl` (see Log).

### Why the wrapper has its own directory

`~/.local/bin` comes after the directories mise puts on PATH, so a wrapper there would never run first. `mise` also re-prepends its own directories ahead of anything a `.zshrc` adds whenever its environment changes (a `cd` into a directory with a `mise.toml`), which was checked in a scratch zsh setup. Three pieces keep `~/.local/share/leak-guard/bin` first on the work profile: `dot_zshenv` puts it first when the directory exists (plain `zsh -c`); `dot_zprofile` puts it first again after `/etc/zprofile`'s `path_helper` (login shells); and the installer writes `~/.config/mise/conf.d/leak-guard-gh.toml` (`[env]` with `_.path`), which mise puts ahead of its own tool directories in every shell where it is active. The directory exists only where the installer made it, so the two zsh files do nothing elsewhere. The installer never touches `~/.local/bin/gh`. `tests/leak-guard/test_gh_path.py` runs fresh `zsh -c`, `-lc`, `-ic` and `-ic` after `mise hook-env`, and a `cd` into a directory whose `mise.toml` changes PATH, and checks each prints the wrapper.

### Prior art

`gh` extensions and aliases cannot intercept core commands (`gh pr create` runs gh's own code whatever an alias or extension is called), and gh has no hook for outgoing text. Wrapping the binary on PATH is the usual way to guard it.

### Limits

It guards against a missed step. It does not stop an agent that sets out to evade it. Known gaps and costs of the wrapper itself: a flag before the command group (`gh -R <repo> pr comment ...`) cannot be matched to a command, so on a guarded context (any target guarded) it is refused with "put the command group first", and with no guarded target it runs untouched; a flag between the group and its subcommand (`gh pr -R <repo> view 3`) is refused the same way, reads included; a remote written with an ssh host alias or a `url.<base>.insteadOf` rewrite is read as written, not as ssh or git resolve it, so it may not match a guarded repository (use the plain `github.com` URL of the remote, or name the repository with `-R`); an unusual way of writing a command that this list does not foresee can still reach gh unchecked, and is a bug to report. Other ways around it: an absolute path to the real `gh`, `curl` against the API, another tool, or the web UI all go around it. Text sent that way is not checked, and a leak that gets through still needs a person to delete the revisions in the web UI. Layer 2 costs one Haiku call per checked text and adds about 10 to 20 seconds. The wrapper checks text on its way out; it does not read GitHub back (a scan of already-published text, an `audit-github` command, is not built).

## Never print the terms file

Never cat, print or log `~/.config/leak-guard/terms` or any line of it, in a terminal, a report, a PR or a log. Name a term as "term N". The tests use a planted fake term only (`tests/leak-guard/test_terms_hidden.py` checks that a planted term appears in no output and no log line, in any mode, and in the wrapper's output).

## Same view as `git push`

Every git call the hook makes goes through one helper in a neutral environment, so local git configuration cannot change what the hook sees compared with what is pushed: `GIT_NO_REPLACE_OBJECTS=1`, `GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL=/dev/null`, `GIT_ATTR_NOSYSTEM=1`; `GIT_EXTERNAL_DIFF`, `GIT_DIFF_OPTS`, `GIT_CONFIG_PARAMETERS` and `GIT_CONFIG_COUNT` removed; and `-c` pins for the repo-level settings that change diff, diff-tree, cat-file or log output (`diff.noprefix`, `diff.mnemonicPrefix`, `diff.relative`, `diff.external`, `diff.renames`, `core.quotePath`, `color.ui`, `log.showSignature`, and others), plus `--no-textconv` and `--no-ext-diff`. `git replace` objects would show a stand-in for a pushed commit and grafts are not switched off by that variable, so **a `refs/replace/*` ref or a `$GIT_DIR/info/grafts` file blocks pre-commit and pre-push** (remove them, or override).

## Override and bypass

- `LEAK_GUARD_SKIP="<reason>" git commit ...` (or `git push ...`) skips both layers for that one command, so it has to be set on each command that needs it (a commit runs three hooks, and a push one; the variable reaches each of them). **Every skip is logged**, with its reason, in the log below.
- `git commit --no-verify` and `git push --no-verify` skip the hooks, as git always allows. That leaves no log line.

## Log

Every run appends one line to `~/.local/state/leak-guard/log.jsonl` (the file is mode 600 in a mode 700 directory): `{utc, mode (pre-commit|commit-msg|pre-push|text), head, verdict (pass|block|skip), layer (1|2|override|none), duration_s, findings}`, plus `claude_s` and `cost_usd` when Claude was called and `reason` for a skip or a failing step. Neither the diff nor any term is ever logged, and a `reason` is a short fixed code or a count, never a path from the change, a ref name or a word from Claude's answer (three reasons do name a path of the tool's own: the terms file in "invalid regex" and "no terms", and the `claude` executable in "cannot run claude"); notices such as `remote_sha_unknown` are logged as codes in `notes`. `text` mode writes the same line, so a checked PR body is a `text` line. The gh wrapper adds its own line, `{utc, mode: "gh", command, verdict (pass|block|skip), layer (1|2|override|none|wrapper), duration_s, findings}`, for every command it checks or blocks for a guarded repository and for every GraphQL mutation. `command` is the group and verb (`pr create`, `api graphql`); `layer` is `wrapper` for a block that never reached `leak-guard` (an unrecognised write, a composed-text flag, an unreadable file, `leak-guard` missing). The line never holds text, a term, a title, a path or a repository name. A pass-through read writes nothing.

## What it guards

Only the chezmoi source checkout, and the git worktrees made from it (they share its hooks directory). **A separate clone of the repository is not guarded**: hooks are not part of a clone, so a clone made elsewhere has none until you install them there by hand.

## Installing it

On the `axon-work-computer` profile, with the data key `leakGuard` in `~/.config/chezmoi/chezmoi.yaml`:

```yaml
data:
  leakGuard:
    terms: ["fooco", "project-bar"]       # regexes
    context: |
      Fooco is the employer. A work detail is anything that names it, its hosts, its repositories or its registries.
```

`run_onchange_after_46_install-leak-guard-hooks.sh.tmpl` is a chezmoi `run_onchange_` step: it runs when the rendered script changes, that is when the `leakGuard` data (or the script) changes, and not on every apply. To re-run it by hand (after fixing a hook, or removing a foreign one): `chezmoi execute-template < "$(chezmoi source-path)/run_onchange_after_46_install-leak-guard-hooks.sh.tmpl" | sh`. It writes `.git/hooks/pre-commit`, `.git/hooks/commit-msg` and `.git/hooks/pre-push` into the chezmoi source dir (each runs `~/.local/bin/leak-guard`), and `~/.config/leak-guard/terms` and `context` at mode 600. A hook file that already exists and is not leak-guard's is left alone with a warning. If `core.hooksPath` is set (globally or in the repo) nothing is installed, and the script says loudly that the chezmoi source repo is **UNGUARDED**, why (git then ignores `.git/hooks`, and a shared path would guard every repository), and how to fix it. With no `leakGuard` data, or on another profile, it does nothing. The terms are never in this repository: they live only in the machine's own chezmoi data. Git worktrees of the chezmoi source share its hooks.

The wrapper needs one more key, `leakGuard.repos`, a list of the guarded repositories (`owner/name`, or `host/owner/name` off github.com):

```yaml
    repos: ["fooco-dev/some-public-repo"]
```

`run_onchange_after_47_install-leak-guard-gh.sh.tmpl` renders only on `axon-work-computer` with `leakGuard` data. It writes `~/.local/share/leak-guard/bin/gh` (mode 755), `~/.config/leak-guard/repos` (mode 600) and `~/.config/mise/conf.d/leak-guard-gh.toml`. With empty or missing `repos` it installs nothing and prints a notice; bad `repos` data fails the render. A file already at either of the first and third paths that is not ours is left alone with a warning. To re-run it by hand: `chezmoi execute-template < "$(chezmoi source-path)/run_onchange_after_47_install-leak-guard-gh.sh.tmpl" | sh`.

## Residuals

- **A tracking ref that was never pruned.** Pre-push excludes every commit that any branch of the remote has, as last fetched. A tracking ref left behind for a branch that was since **deleted on the remote** still excludes that branch's commits. So text that was public once and then scrubbed by deleting its branch could be pushed again under a new ref without being rechecked. After deleting a remote branch, run `git fetch --prune <remote>` before the next push.
- **Template comments in the message.** `commit-msg` scans every line except git's scissors section, so it also scans the comment lines git adds when you commit in an editor, such as `# On branch <name>`. A local branch whose name holds a term therefore blocks commits made in the editor. The override gets past it.
- **The prompt is not fenced.** The diff text sits in the layer-2 prompt beside the instructions. Layer 1 is the deterministic backstop, the model has no tools, and an answer that is unparseable or contradicts itself blocks.
- **Separate clones** are not guarded, and a `pushurl` that differs from `url`, or a custom fetch refspec, can make the pre-push exclusion wrong (this repository sets neither).

## Tests

`python3 -m unittest discover -s tests/leak-guard -v`: a fake `claude` on PATH, invented terms and context, and a planted fake term wherever a term must stay hidden. `test_text.py` (text mode), `test_gh_wrapper.py` (the wrapper as a process against a fake `gh`, plus an in-process view of its decisions for the command matrices), `test_gh_installer.py` (the installer, and a journey through the installed wrapper), `test_gh_path.py` (fresh zsh shells) and `test_terms_hidden.py` cover the text mode and the wrapper.  Layer 1 hits (file, line, term; regexes; file names; removed lines ignored), Claude's verdicts (leak, clean, wrapped JSON, unparseable), the call's flags (no tools, no MCP, the model, what is sent), missing `claude`, not signed in, timeout, an oversized change, the override and its log, the pre-push ranges (new branch, existing branch, a message, several refs, a deleted ref), the real hooks blocking a commit and a push and `--no-verify`, and the installer (nothing without data or on another profile, mode 600, a foreign hook left alone, bad data).
