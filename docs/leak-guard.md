# leak-guard

`cartwmic/dotfiles` is a public repository, and the work machine commits to it. `leak-guard` is a git hook, on the work machine only, that checks every commit and push for work details before the change leaves the machine. A `gh` wrapper (below) runs the same check on the text of pull requests, comments, reviews, issues and release notes before it is sent to GitHub. There is no personal counterpart (see [profiles.md](./profiles.md)).

It is one script, `dot_local/bin/executable_leak-guard` (installed as `~/.local/bin/leak-guard`), run by three git hooks in the chezmoi source dir:

- `pre-commit` checks `git diff --cached`. It cannot see the commit message, and a commit with no diff (`git commit --allow-empty`) has nothing for it to read, so:
- `commit-msg` checks the message with layer 1 only (every line is scanned, `#` lines included, since `git commit -m` keeps a line that starts with `#`; only git's scissors section, `# ------------------------ >8 ------------------------` and below, which `commit -v` fills with the diff, is skipped; so a commented line that holds a term blocks at commit time, and the override is the way out). It is a separate hook because only it is given the message; layer 2 reads every pushed message at pre-push. The author and committer of a commit are checked at pre-push, which sees them.
- `pre-push` checks, in one pass, everything the push would make public that the remote's own tracking refs do not already have:

      git rev-list <pushed tips> --not --remotes=<remote> [<each remote sha present locally>] \
        | git diff-tree --stdin -r -p --cc --root --always --no-renames --no-textconv --no-ext-diff --pretty=raw

  A commit that any branch of that remote has, as last fetched, is excluded and never rechecked; a commit shared by two pushed refs is checked once; the hook never fetches. Every commit is shown even when it has no diff (`--always`), so an empty commit's message and identities are checked too. Layer 1 scans every raw header line (author, committer, `mergetag`), every message line, every path and every added line; a merge shows only the lines it introduces itself (a `--cc` prefix as wide as the parent count, so an octopus merge works). Annotated tag objects are peeled and scanned whole (tagger included); a ref that peels to a tree or a blob blocks, since nothing here can read it. Only the **remote** ref name is checked, because the local name never becomes public. Deleted refs are skipped (a push of only deletes makes no Claude call). A push to a URL is mapped back to the configured remote whose `url` or `pushurl` it is; with no match, or with no tracking refs for that remote, it blocks with "run `git fetch <remote>`, then push again" rather than scanning the whole history. If the remote is empty (no branches at all, so there is nothing to fetch), the reason says so, and the documented way to make that first push is the override, after looking it over by hand. A remote sha that is not present locally gives a notice (run `git fetch`) and the check goes on over everything the tracking refs lack. A stale tracking ref can make the check examine less, not only more (see Residuals); a `pushurl` that differs from `url`, or a custom fetch refspec, can make the exclusion wrong (this repository sets neither).

The checks look only at **added** lines and at the **names** of added, copied, modified and renamed files (a rename counts as a new name; an empty file has a name too). File, branch and tag names are also given to Claude as data. Every diff is taken with `--no-textconv` and `--no-ext-diff`, so no diff driver can hide content. Because each commit's own patch is read, a term added in one commit and removed in the next is still seen, and pre-push backstops commits made with `--no-verify`.

**Binary files.** Their names are checked like any other, but their content cannot be read, so a binary file that is added or changed blocks (after layer 1, naming the file) until you commit it with the override. Two layers, cheapest first:

1. **Terms.** `~/.config/leak-guard/terms` is one regex per line (`#` lines are comments), matched case-insensitively. A hit blocks and prints `file:line: term N`. **Term N** is the 1-based position of the term among the terms, with blank lines and `#` lines skipped. The term's text is never printed or logged: count the lines of the file yourself, in an editor, to find term N. A regex that does not compile is named the same way (`term 7 of the terms file ... is not a valid regex`).
2. **Claude.** `claude -p` with Haiku, no tools and no MCP servers, in an empty directory, gets `~/.config/leak-guard/context` (a few lines on the employer and what counts as a work detail), the added lines, and the repo context (below), and must answer one JSON object, `{"leak": true|false, "findings": [{"file", "line", "text", "why", "name"}]}`, where `name` is the exact word or phrase of the change that is the work detail. `leak: true` blocks and prints the findings, except that a finding whose `name` the repository already publishes is skipped (below). An answer that is not that JSON is a block, and so is one that contradicts itself (`leak: false` with findings, or findings that are not a list) or whose result is not text. An unexpected error blocks too, with the error's type named.

**The pi fallback.** The one claude failure that is retried is a spend-limit / usage-limit 429, decided only from claude's own structured verdict: the result event of its `--output-format json` output carrying `api_error_status` 429. A `429` or the words anywhere else in the output — a duration, a token count, the judged text — is not claude saying it hit its limit, and never falls back. On a 429, the same prompt goes to `pi` once — `pi -p --no-tools --no-extensions --no-context-files --no-skills --no-mcp --no-session` on pi's own default model, prompt on stdin, claude's system prompt (the one-JSON-object contract) passed as pi's system prompt, in an empty directory, the same 120 s timeout — and its answer is parsed by the same JSON contract and the same fail-closed rules. Which model judges is a per-machine choice and is never committed: the work machine's install step writes a full command line pinning it to `~/.config/leak-guard/pi-judge` (one line, from the `leakGuard.piJudge` local data key, and removed again when that key is), and `LEAK_GUARD_PI` overrides for the tests. Any other claude failure (no CLI, not signed in, a timeout, another non-zero exit, an unparseable answer) blocks with no fallback. A pi failure blocks too, naming both failures. The log records which judge answered (`judge`: `claude` or `pi`, or the list when the chunks differ, plus `pi_s`), so the decision is replayable.

**Names the repository already holds.** A finding is skipped when its `name` is a non-empty string, appears in what was sent, and `git grep -F -w` finds it in the files the repository already publishes. At pre-push those are the trees of the remote's default branch (its `refs/remotes/<remote>/HEAD` resolved, else `<remote>/main`, else `<remote>/master`) and of every pushed branch the remote already has, so a name added by an earlier commit of the same push is still new, and so is a name only one of the remote's other branches holds. At pre-commit it is `HEAD`. At `text` mode they are the commit of the default branch of the remote of the target repository — the one the text is being posted to, which the gh wrapper names with `--repo` — and only when a remote of the checkout the command runs in fetches from that target: a checkout of any other repository, a run with no `--repo`, outside a repository, or with no remote, has no base and nothing is skipped, so the other checkout's own names are never named as published. `commit-msg` runs layer 1 only, so it never skips anything. A skipped finding is printed (`skipped, its name is already in the repository: FILE:LINE: NAME`), counted in the log as `known_skipped` (the name is not logged), and does not block. A finding with no usable name is new and blocks, and so does a change with a new name next to a known one. Layer 1 is unchanged: a term that matches blocks even in a file the repository already holds.

**Repo context in the prompt.** Wherever a base exists, the layer-2 prompt also names, in one line after the context file, the name-like words (code names, hosts, paths — a token with an uppercase letter, a digit or a `. _ -` in it) that the change and the target branch both hold, so the judge does not report what the branch already publishes: `These names already appear in the files the target branch publishes, so they are not work details; do not report them: A, B`. Only names pass, never whole files; the names are found with one `git grep -o -h -F -w -f` over every candidate at once, capped (2000 candidates taken from the change, 100 names and 4000 characters in the prompt), and a grep that fails names nothing — the skip above still applies, and a missing prompt context never blocks. Ordinary lowercase words are never named.

It **fails closed**. It blocks, with one line naming the failing step, when the `claude` CLI is missing, you are not signed in, the network is down, the call times out (120 s), `claude` exits non-zero, the terms or context file is missing, a term is not a valid regex, or a pre-commit change is over 200 KB (nothing is truncated; commit smaller changes or override), or one line of a push is larger than a 180 KB chunk. A push that is larger than one chunk is split into chunks of about 180 KB, each its own Claude call, and every chunk must pass. The one retried failure is claude's spend-limit / usage-limit 429, which falls back to pi once (above); every other failure blocks with no fallback, and a pi failure blocks naming both.

## Text mode

`leak-guard text [--result FILE] [--repo HOST/]OWNER/REPO TEXTFILE...` runs both layers on the text of each file: a PR body, a comment, release notes. It is the commit-msg code path with layer 2 added. Each non-blank line is checked by layer 1 (`TEXTFILE:line: term N`, labelled by the file's base name) and then sent to Claude with the same context file, in a prompt that says the text is about to be posted publicly on GitHub. Unlike `commit-msg`, `text` has a base when the target repository is named (`--repo`, which the gh wrapper passes) and a remote of the checkout the command runs in fetches from that target: the commit of that remote's default branch, so a name the target already publishes is named in the prompt, and a finding that reports it anyway is skipped, not blocked. Any other run — no `--repo`, a checkout of another repository, no repository, no remote — has no base and nothing is skipped. It blocks (exit 1) on a hit, on a `leak: true` answer, and on every failure the hooks fail closed on: no `claude`, no sign-in, a timeout, an unparseable answer, an unreadable file, a missing terms or context file, or more than 200 KB of text — with the pi fallback on a spend-limit 429 like everywhere else. With no file it exits 64. A file with only blank lines passes without a Claude call. The override is the same `LEAK_GUARD_SKIP="ask N: reason"` on the command ([Override and bypass](#override-and-bypass)), and it is logged with its ask id. `--result FILE` also writes `{"verdict", "layer", "findings"}`, the values the log line carries, so a caller can log them.

## The gh wrapper

GitHub keeps every earlier version of an edited PR body or comment, and the API cannot delete them, so text has to be checked before it is sent. Git hooks never see it. `scripts/gh-wrapper` is a wrapper for `gh` that does. It is the one `gh` wrapper that every desktop profile has, installed by `run_onchange_after_47_install-gh-wrapper.sh.tmpl` as `~/.local/share/gh-wrapper/bin/gh` ([gh-wrapper.md](./gh-wrapper.md)); the leak-guard check runs only where `~/.config/leak-guard/repos` exists, which the installer writes only on the `axon-work-computer` profile and only with `leakGuard.repos` data (below). It calls `leak-guard text` as a process and never imports it, passing `--repo HOST/OWNER/NAME` when the command's text is aimed at exactly one guarded repository (with more, which one gh would pick cannot be told, so it passes none and there is no base). With no `~/.config/leak-guard/repos` file the check does nothing.

**Which repository.** Every one the command names, taken together: its `-R`/`--repo` values, the GitHub URLs and `OWNER/REPO` arguments (of a parsed command, its positional arguments only, so a URL inside a body text is only text), `GH_REPO`, every remote URL of the current directory's git repository (https, ssh and scp forms), read as written and as git and ssh resolve it (`git remote get-url --all`, also with `--push`, which applies `url.<base>.insteadOf` and `pushInsteadOf`; and for an ssh URL the real host name `ssh -G <host>` gives for a `Host` alias; if either cannot be resolved, the value as written still counts), and for `gh api` the endpoint path (`repos/<owner>/<repo>/...`, with or without a leading slash, `https://api.github.com/` or `https://uploads.github.com/`, on the host `--hostname` names). A command is guarded when ANY of them is a line of `~/.config/leak-guard/repos`: `owner/name` for github.com, `host/owner/name` for another host. gh prefers one source to the others (a URL beats `-R`, `-R` beats `GH_REPO`, `GH_REPO` beats the checkout) and the order differs between commands, so the wrapper does not try to reproduce it. The price is that a command with a mixed set, such as `gh pr comment -R someone/other` in a guarded checkout, is checked as if guarded; a clean text still runs. A command whose targets are all unguarded runs the real `gh` untouched. Only `-R`/`--repo` may stand between the group and its subcommand (`gh pr -R <repo> view 3`; the five spellings `-R x`, `-Rx`, `-R=x`, `--repo x`, `--repo=x`). gh finds the subcommand by skipping the group's flags, so the wrapper moves the repo flag behind the subcommand and decides on the command as if it had been written there: a read runs, a text command is checked, an unrecognised write is refused. Any other flag in that position is not read, because nothing says whether its next argument is a value or the subcommand: that includes `--help`, and `-h`, which gh does not know there and so takes the next word as its value (`gh repo -h view edit ...` runs `repo edit`). On a guarded context such a command shows the generic help when it carries a help token and is refused otherwise: put the subcommand right after the group.

**What it checks, for a guarded repository.** The title and body of `pr create`, `pr edit`, `pr comment`, `issue create`, `issue edit` and `issue comment`; the body of `pr review`; the title and notes of `release create` and `release edit`; and the text flags of `pr merge` (subject, body), `pr close`, `pr reopen`, `issue close` and `issue reopen` (comment). It reads inline values (`--body`, `--notes`), `--body-file`, `-F`, and `--notes-file`, including `-` for standard input, and passes any standard input it read on to the real `gh`. A block names the part (`title`, `body`, `notes`, `comment`, `tag`, or `field N` for the Nth field of a `gh api` call), the line and the term number (`body:3: term 2`), never a temporary path or a field key.

**`gh api`.** The keys and values of `-f`, `-F`, `--raw-field` and `--field` (`key=@file` and `key=@-` are read) and the content of `--input` are checked for a write to a guarded repository; a hit in a key reads `field N key`, never the key itself. `--hostname` sets the host, so a repository on another host is not a guarded repository unless its `host/owner/name` line is in the repos file. Any field flag makes the call a write even without `-X`, because gh then sends a POST; `-X GET` and `-X HEAD` keep it a read. A GraphQL mutation names objects by node id, not by repository, so every `gh api graphql` call whose query holds a mutation is checked, for every repository and directory: the query text and every variable, from `-f`/`-F` fields or from JSON `--input`. A query that is not a mutation passes. A call it cannot parse (an unreadable query file, `--input` that is not a JSON object) is blocked. The endpoint may be a full URL (`https://api.github.com/graphql`, `https://uploads.github.com/repos/<owner>/<repo>/...`). A write to `repositories/<id>/...` names the repository only by its numeric id, which the wrapper cannot map, so it is blocked; use the `repos/<owner>/<repo>/...` form.

**Flag tables.** What a flag's next argument is depends on the flag: `-r` takes a value in `pr create` (a reviewer) and none in `pr review` (request changes), so one list for every command hides text. The wrapper keeps one table per command whose text it reads (`FLAGS` in `scripts/gh-wrapper`: the 14 `pr`, `issue` and `release` commands, and `gh api`), one for each other command whose flags it hands to the layers (`run watch` and `pr checks`, `FOR_LAYERS` in the script), and one per command group, which lists the flags gh accepts between the group and its subcommand. They are copied from `gh <command> --help` of gh 2.103.3 (`FLAGS_FROM_GH` in the script names the release): long name, short name, and whether the flag takes a value. It parses a command's arguments with that command's table, following gh's flag library for the forms listed here (`--name value`, `--name=value`, `-x value`, `-xvalue`, `-x=value`, clusters of switches such as `-dt`, a value flag taking the next argument whatever it looks like, `--` ending the flags). A flag that is not in the table is refused for a guarded repository, named by its argument position, because the wrapper cannot tell whether it takes a value. `tests/leak-guard/test_gh_wrapper.py` (`FlagTables`) runs the installed `gh <command> --help` for every table, when gh is present, and, when the installed gh is the release the tables came from, fails when a table differs. For any other release it reports the difference and passes, since the tables cannot be compared with a different gh; CI's gh and a developer's can differ. `LEAK_GUARD_TEST_GH=<path to a gh>` compares against that gh. A gh upgrade that adds or changes a flag leaves the wrapper refusing the new flag on a guarded repository (see Limits) until `FLAGS` is regenerated. `scripts/leak-guard-gh-flags` does it from the installed gh: it runs `gh <command> --help` for every command already in `FLAGS`, rewrites those rows and `FLAGS_FROM_GH`, and prints the flags gh added and removed per command. `--check` changes nothing and exits 1 when the file would change; `--gh PATH` reads another gh. It never adds a command: a new command that carries text is added to `FLAGS`, `TEXT` and the verb lists by hand, and one a layer reads flags of is added to `FLAGS` and `FOR_LAYERS`. A flag in the table is accepted and its text read, so before committing, classify each added flag: a flag that carries text goes in `TEXT`, one that makes gh write the text itself in `COMPOSED`, one that uploads a file (as `--attach` does) in the refusals of `parse_text`. The table test and the script share one help parser (the script's). `--attach` (gh 2.103.3, on `pr`/`issue` `create`, `edit` and `comment`) uploads an image or video whose content cannot be read, so it is refused like a release asset.

**Blocked without a check.** Anything that makes gh write the text itself, where the wrapper cannot see it: `--fill`, `--fill-first`, `--fill-verbose`, `--template`, `--recover`, `--editor`, `--web` and `--edit-last` on the commands that take them, and, on a terminal, every command where gh would ask for text at its own prompt: `pr create` or `issue create` without a title and a body, `pr edit` or `issue edit` with no flag, `pr comment` or `issue comment` without a body, `pr review` without its type or body, `release create` without notes, and `pr merge` without a method flag (gh then asks how to merge and offers to edit the commit message). The message says to give the text with `--title` and `--body-file` (`--notes-file` for a release, `--squash` or `--merge` or `--rebase` for a merge). On top of that, the real `gh` for a guarded write always runs with `GH_PROMPT_DISABLED=1`, so it can never ask for text at a prompt the wrapper cannot see. A merge with a method flag and no text passes. A write command it does not recognise is blocked too, with the command named (`repo edit`, `label create`, `workflow run`, `agent-task`). `gh repo set-default` (it changes local git config only) and the shell-completion entries `gh __complete` and `gh __completeNoDesc` send no text and run untouched, in a guarded checkout too. `gh release create TAG FILE...` is blocked when it has asset files (they would be uploaded unchecked, as `release upload` is refused); the tag name is checked as text. Read commands (`pr list`, `pr view`, `run list`, ...), write commands that carry no free text (`pr ready`, `run rerun`, ...) and every command for an unguarded repository run the real `gh` with the same arguments, the same standard input and its exit code, and `leak-guard` does not run.

**Aliases and extensions.** A name that is no built-in gh command is looked up with the real `gh alias list`, whose `name: expansion` lines are parsed exactly (a line it cannot parse refuses the command). An alias is expanded the way gh expands it (`$1`, `$2` and the appended arguments) and the expansion is classified like a typed command, so `prc = pr create --fill` is blocked and an alias with `-R <guarded>` built in is checked from any directory. A shell alias (`!...`) aimed at a guarded repository is refused. A name that is no alias is an extension; aimed at a guarded repository it is refused as an unrecognised write. Only a built-in read, or a bare built-in group with no arguments (`gh pr`, which prints help), passes without a check. **Help on a guarded repository shows the command's generic help.** A help token is `--help`, `--help=...`, or any single-dash argument with an `h` before any `=` (`-h`, `-dh`, `-h=false`). When the wrapper reads a command aimed at a guarded repository as a help request, it never passes your arguments to gh. It runs `gh <group> [<verb>] --help`, built from built-in names only, with standard input closed, so flags next to `--help` are ignored. A command it parses by its table (`gh pr comment ...`, `gh api`) is a help request only when the parse is clean and the last `--help` or `-h` is true (`1 t T TRUE true True`); otherwise its text is checked and the command runs only if the check passes. An unrecognised write or a command it cannot parse, with any `--help`, `--help=...` or `-h` in it, gets the generic help; with none it is refused. `gh <alias> --help` prints `name = expansion` and, for a non-shell alias, the generic help of the command it expands to. Help for an extension is refused on a guarded repository, because `--help` would run the extension's own code. A read (`gh pr view --help`) is untouched. `tests/leak-guard/test_gh_wrapper.py` (`WrapperHelpRunsOnlyBuiltInNames`) pins the exact argument list that reaches gh for each case, and `WrapperHelpNeverSkipsTheCheck` runs about 1,700 help spellings against planted text.

**Fail closed.** `leak-guard` missing, not runnable or exiting non-zero blocks the command, and so does anything that makes `leak-guard text` block. A wrapper that cannot run at all (a broken `python3`, a syntax error in the installed file) fails every `gh` call, reads included; that is deliberate. A `gh` killed by a signal exits with the shell's 128 plus the signal number. The real `gh` is the first `gh` on PATH that is not the wrapper: copies, symlinks to it and a repeated directory are skipped, so it cannot run itself. With no real `gh` it exits 127.

**Override and log.** `LEAK_GUARD_SKIP="ask N: reason" gh ...` skips the check for that command (wrapper-only blocks too) and is logged with its ask id. The wrapper appends one line per guarded command it checks or blocks, and per GraphQL mutation, to the same `log.jsonl` (see Log).

### Why the wrapper has its own directory

`~/.local/bin` comes after the directories mise puts on PATH, so a wrapper there would never run first. `mise` also re-prepends its own directories ahead of anything a `.zshrc` adds whenever its environment changes (a `cd` into a directory with a `mise.toml`), which was checked in a scratch zsh setup. Three pieces keep `~/.local/share/gh-wrapper/bin` first (on every desktop profile; [gh-wrapper.md](./gh-wrapper.md)): `dot_zshenv` puts it first when the directory exists (plain `zsh -c`); `dot_zprofile` puts it first again after `/etc/zprofile`'s `path_helper` (login shells); and the installer writes `~/.config/mise/conf.d/gh-wrapper.toml` (`[env]` with `_.path`), which mise puts ahead of its own tool directories in every shell where it is active. The directory exists only where the installer made it, so the two zsh files do nothing elsewhere (Termux). The installer never touches `~/.local/bin/gh`. `tests/leak-guard/test_gh_path.py` runs fresh `zsh -c`, `-lc`, `-ic` and `-ic` after `mise hook-env`, and a `cd` into a directory whose `mise.toml` changes PATH, and checks each prints the wrapper.

### Prior art

`gh` extensions and aliases cannot intercept core commands (`gh pr create` runs gh's own code whatever an alias or extension is called), and gh has no hook for outgoing text. Wrapping the binary on PATH is the usual way to guard it.

### Limits

It guards against a missed step. It does not stop an agent that sets out to evade it. Known gaps and costs of the wrapper itself: a gh upgrade can add flags, and `mise` keeps gh at the latest release, so a new flag is refused on a guarded repository (the wrapper cannot tell whether it takes a value) until the tables are regenerated with `scripts/leak-guard-gh-flags`; a flag before the command group (`gh -R <repo> pr comment ...`) cannot be matched to a command, so on a guarded context (any target guarded) it is refused with "put the command group first", and with no guarded target it runs untouched; a flag between the group and its subcommand that is not one of the group's own (or `--`) is refused on a guarded context, since a flag's value could then be the subcommand; an unusual way of writing a command that this list does not foresee can still reach gh unchecked, and is a bug to report. Other ways around it: an absolute path to the real `gh`, `curl` against the API, another tool, or the web UI all go around it. Text sent that way is not checked, and a leak that gets through still needs a person to delete the revisions in the web UI. Layer 2 costs one Haiku call per checked text and adds about 10 to 20 seconds. The wrapper checks text on its way out; it does not read GitHub back (a scan of already-published text, an `audit-github` command, is not built).

## Never print the terms file

Never cat, print or log `~/.config/leak-guard/terms` or any line of it, in a terminal, a report, a PR or a log. Name a term as "term N". The tests use a planted fake term only (`tests/leak-guard/test_terms_hidden.py` checks that a planted term appears in no output and no log line, in any mode, and in the wrapper's output).

## Same view as `git push`

Every git call the hook makes goes through one helper in a neutral environment, so local git configuration cannot change what the hook sees compared with what is pushed: `GIT_NO_REPLACE_OBJECTS=1`, `GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL=/dev/null`, `GIT_ATTR_NOSYSTEM=1`; `GIT_EXTERNAL_DIFF`, `GIT_DIFF_OPTS`, `GIT_CONFIG_PARAMETERS` and `GIT_CONFIG_COUNT` removed; and `-c` pins for the repo-level settings that change diff, diff-tree, cat-file or log output (`diff.noprefix`, `diff.mnemonicPrefix`, `diff.relative`, `diff.external`, `diff.renames`, `core.quotePath`, `color.ui`, `log.showSignature`, and others), plus `--no-textconv` and `--no-ext-diff`. `git replace` objects would show a stand-in for a pushed commit and grafts are not switched off by that variable, so **a `refs/replace/*` ref or a `$GIT_DIR/info/grafts` file blocks pre-commit and pre-push** (remove them, or override).

## Override and bypass

- `LEAK_GUARD_SKIP="ask N: reason" git commit ...` (or `git push ...`) skips both layers for that one command, so it has to be set on each command that needs it (a commit runs three hooks, and a push one; the variable reaches each of them). **Every skip is logged**, with its ask id, in the log below; the reason text is never logged.
- `git commit --no-verify` and `git push --no-verify` skip the hooks, as git always allows. That leaves no log line.

The override must name an approval the agent cannot create alone. `LEAK_GUARD_SKIP` has to be `ask N: reason` — N is the number of the ask that approved the skip, and the reason is free text for the person who reads the command, never logged. Anything else is refused, with the format named. The machine's **approval checker** decides whether ask N approves this skip; it is a per-machine choice and is never committed: the work machine's install step writes its command line to `~/.config/leak-guard/approval-check` (one line, from the `leakGuard.approvalCheck` local data key, and removed again when that key is). leak-guard runs `<checker> <N>`:

- **Exit 0** approves the skip. Any other exit blocks it, with the checker's first stderr line shown.
- **The checker owns the 24-hour window**: it reads the ask's answered time and refuses an ask older than 24 hours. leak-guard passes it the ask id and nothing else.
- **Fail closed**: with no checker file on the machine, every skip is refused ("no approval checker on this machine"), as is a checker that cannot be run.
- **Single use per mode**: an approved ask id is recorded in `~/.local/state/leak-guard/used-asks` (mode 600), and a second skip with the same ask and mode is refused. One `git commit` runs pre-commit and commit-msg, and each consumes the ask once, so one override still covers a whole commit; a second commit (or push, or `gh` command) with the same ask needs a new one.

The real checker for the work machine is not part of this repository; only its contract above is.

## Log

Every run appends one line to `~/.local/state/leak-guard/log.jsonl` (the file is mode 600 in a mode 700 directory): `{utc, mode (pre-commit|commit-msg|pre-push|text), head, verdict (pass|block|skip), layer (1|2|override|none), duration_s, findings}`, plus `claude_s` and `cost_usd` when Claude was called, `judge` (`claude` or `pi`, or the list when the chunks differ, with `pi_s`) for which judge answered layer 2, `ask` for a skip (the ask id that approved it; the reason text is never logged), and `reason` for a failing step (a short fixed code, never the reason text a skip was given). Neither the diff nor any term is ever logged, and a `reason` is a short fixed code or a count, never a path from the change, a ref name or a word from Claude's answer (three reasons do name a path of the tool's own: the terms file in "invalid regex" and "no terms", and the `claude` executable in "cannot run claude"); notices such as `remote_sha_unknown` are logged as codes in `notes`. `text` mode writes the same line, so a checked PR body is a `text` line. The gh wrapper adds its own line, `{utc, mode: "gh", command, verdict (pass|block|skip), layer (1|2|override|none|wrapper), duration_s, findings}`, for every command it checks or blocks for a guarded repository and for every GraphQL mutation, with `ask` for a skip and a `reason` code for an override refusal. `command` is the group and verb (`pr create`, `api graphql`); `layer` is `wrapper` for a block that never reached `leak-guard` (an unrecognised write, a composed-text flag, an unreadable file, `leak-guard` missing). The line never holds text, a term, a title, a path or a repository name. A pass-through read writes nothing.

## What it guards

Only the chezmoi source checkout, and the git worktrees made from it (they share its hooks directory). **A separate clone of the repository is not guarded**: hooks are not part of a clone, so a clone made elsewhere has none until you install them there by hand.

## Installing it

On the `axon-work-computer` profile, with the data key `leakGuard` in `~/.config/chezmoi/chezmoi.yaml`:

```yaml
data:
  leakGuard:
    terms: ["fooco", "project-bar"]       # regexes
    context: |
      Fooco is the employer. A work detail is anything that names it, its hosts, its repositories or its registries.
    approvalCheck: "/usr/local/bin/ask-approval-check"   # optional: the skip approval checker's command line; without it every LEAK_GUARD_SKIP is refused
```

`run_onchange_after_46_install-leak-guard-hooks.sh.tmpl` is a chezmoi `run_onchange_` step: it runs when the rendered script changes, that is when the `leakGuard` data (or the script) changes, and not on every apply. To re-run it by hand (after fixing a hook, or removing a foreign one): `chezmoi execute-template < "$(chezmoi source-path)/run_onchange_after_46_install-leak-guard-hooks.sh.tmpl" | sh`. It writes `.git/hooks/pre-commit`, `.git/hooks/commit-msg` and `.git/hooks/pre-push` into the chezmoi source dir (each runs `~/.local/bin/leak-guard`), and `~/.config/leak-guard/terms` and `context` at mode 600, plus `pi-judge` (the pi fallback's pinned command line) when the optional `leakGuard.piJudge` data key is set, and `approval-check` (the skip approval checker's command line, [Override and bypass](#override-and-bypass)) when the optional `leakGuard.approvalCheck` data key is set — each removed again when its key is. A hook file that already exists and is not leak-guard's is left alone with a warning. If `core.hooksPath` is set (globally or in the repo) nothing is installed, and the script says loudly that the chezmoi source repo is **UNGUARDED**, why (git then ignores `.git/hooks`, and a shared path would guard every repository), and how to fix it. With no `leakGuard` data, or on another profile, it does nothing. The terms are never in this repository: they live only in the machine's own chezmoi data. Git worktrees of the chezmoi source share its hooks.

The wrapper needs one more key, `leakGuard.repos`, a list of the guarded repositories (`owner/name`, or `host/owner/name` off github.com):

```yaml
    repos: ["fooco-dev/some-public-repo"]
```

`run_onchange_after_47_install-gh-wrapper.sh.tmpl` renders on both desktop profiles ([gh-wrapper.md](./gh-wrapper.md) has the whole install). The leak-guard part: on `axon-work-computer` with `leakGuard` data it writes `~/.config/leak-guard/repos` (mode 600); with empty or missing `repos` it writes no repos file and prints a notice, so the wrapper's check does nothing; bad `repos` data fails the render. Until 2026-11-16 the wrapper lived at `~/.local/share/leak-guard/bin/gh` with `~/.config/mise/conf.d/leak-guard-gh.toml`; the installer removes both when they carry the old mark. To re-run it by hand: `chezmoi execute-template < "$(chezmoi source-path)/run_onchange_after_47_install-gh-wrapper.sh.tmpl" | sh`.

## Residuals

- **A tracking ref that was never pruned.** Pre-push excludes every commit that any branch of the remote has, as last fetched. A tracking ref left behind for a branch that was since **deleted on the remote** still excludes that branch's commits. So text that was public once and then scrubbed by deleting its branch could be pushed again under a new ref without being rechecked. After deleting a remote branch, run `git fetch --prune <remote>` before the next push.
- **Template comments in the message.** `commit-msg` scans every line except git's scissors section, so it also scans the comment lines git adds when you commit in an editor, such as `# On branch <name>`. A local branch whose name holds a term therefore blocks commits made in the editor. The override gets past it.
- **The prompt is not fenced.** The diff text sits in the layer-2 prompt beside the instructions. Layer 1 is the deterministic backstop, the model has no tools, and an answer that is unparseable or contradicts itself blocks.
- **Separate clones** are not guarded, and a `pushurl` that differs from `url`, or a custom fetch refspec, can make the pre-push exclusion wrong (this repository sets neither).

Layer 1 hits (file, line, term; regexes; file names; removed lines ignored), Claude's verdicts (leak, clean, wrapped JSON, unparseable), the call's flags (no tools, no MCP, the model, what is sent), missing `claude`, not signed in, timeout, an oversized change, the override and its log, the pre-push ranges (new branch, existing branch, a message, several refs, a deleted ref), the real hooks blocking a commit and a push and `--no-verify`, and the installer (nothing without data or on another profile, mode 600, a foreign hook left alone, bad data).
