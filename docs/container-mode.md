# Container mode

A setting that makes a personal Linux home fit the agent host pod (homelab repo, `k8s/agent-host`): no desktop, no systemd, no launchd, only the tools the pod uses, and Claude Code through the in-cluster cliproxy. Personal profile on Linux only; the work coordinator runs on the work Mac (see the Feature row in [profiles.md](./profiles.md)).

## Turn it on

In the pod's `~/.config/chezmoi/chezmoi.yaml` (no `read-source-state` hook in it):

```yaml
data:
  profile: personal
  container:
    enabled: true
    # cliproxyUrl: http://cliproxyapi.cliproxyapi.svc.cluster.local   # default, plain http, no /v1
    # cliproxyKeyFile: /run/secrets/cliproxy/api-key                  # default; the file holds the key
  sshHosts:                # top-level, beside container; the pod's configmap sets it (k8s/agent-host/base/configmap.yaml)
    kgate: {address: 192.0.2.12, user: "<user>"}   # real values: the homelab repo's configmap
    # kgateFallback:         # optional: more control planes, tried in order
```

Then `chezmoi init --apply cartwmic`, `npm ci` in the coordinator checkout (`~/git/coordinator`), and `chezmoi apply` once more ("Two applies"). Any other profile or OS, an unknown key under `container`, or a bad value fails the render, so nothing is applied.

| Run scripts | Only `05_container_tools.sh` (mise install, the Claude install, T3 through `install_t3.sh`, pinned: see "T3 version" below), `20_apply_harness_config.sh`, `65_agent_kit_install.sh` (gives `agent-traces`), `76_git_credential_linux.sh` (git uses `gh auth git-credential` for GitHub and `git-credential-gitea-op` for the homelab Gitea) and `77_git_identity_linux.sh` (git author) run. ## T3 version

The pod's T3 is installed on its volume (`~/.local/bin/t3`, the files under `~/.t3/runtime/versions/<version>`), not in the `agent-host` image. T3 refuses a link between two T3s of different versions, so the pod's T3 is pinned to the version of the T3 that links to it. The pin is `[t3Pin]` in `.chezmoidata.toml`: the version and the sha256 of the release's linux archive for each CPU. `05_container_tools.sh` passes it to `install_t3.sh`. It downloads the archive, checks it against the pinned sha256 (a mismatch fails the apply, so the pod does not start), unpacks that same file into `~/.t3/runtime/versions/<version>`, writes a stamp there (`.verified-by-install_t3`: the version and the sha256 of its `t3`) and runs the T3 installer with `T3CODE_VERSION` set. The installer then finds the version already downloaded and only writes the `t3` launcher, so the bytes that run are the bytes the sha256 covers. One check decides every successful exit, both the early "already on the pin" exit and the end of an install: the `t3` on PATH is a launcher that runs exactly that folder's `t3`, and the stamp matches the `t3` in it. If the check fails after the installer ran, the script fails, and it fails again on every later run until the installer is fixed or the pin changes; it never exits 0 on bytes the sha256 did not cover. The stamp holds the sha256 of `t3` and the count and total size of every file in the folder, so a folder an unclean volume detach left cut short (a truncated `t3` or zero-byte files behind a surviving `.install-complete`) fails the check, whichever file is damaged, without hashing thousands of files. The failed folder is moved aside to `versions/<version>.corrupt-<time>` (the latest one is kept) and the checked copy is put in its place, so the T3 installer never finds a bad folder marked complete. A pod that is on the pin but has no stamp (installed before the stamp existed, or by hand) is installed again once through the same path, not trusted. The launcher is replaced and older versions stay on disk. A pin change changes script 05's text, so chezmoi runs it again on the next pod start. A running pod keeps its old T3 until it restarts. Host installs (script 74, `install_t3.sh` with no pin) are unchanged. To bump: set the three values (the linux lines of the release's `SHA256SUMS`) in a dotfiles PR, and the same version and sha256s in the budget-steward Dockerfile in a second PR in that repo (the two repos cannot share one PR; `t3_pin_check.py --open-prs` opens both). After the merge restart one pod when no thread is running in it, check that `t3 --version` prints the new pin and that the pod's link reads with no `lastError`, and only then restart the others: a wrong pin fails the apply and the pod does not start, so the first restart is the test. `tests/t3-pin` runs the script and checks the pin reaches script 05.

Keeping the pin equal to the host's T3 is checked, not remembered. `t3_pin_check.py` (`~/.local/user_scripts/`, personal profile) compares `t3 --version` on the host, `[t3Pin]` on dotfiles' `origin/main` and the T3 pin in the budget-steward `Dockerfile` on its `origin/main`, and prints `in step` or `drift: ...` (exit 1; exit 3 when a source cannot be read). The two pins stay two copies: the steward image is built on the cluster from a Gitea commit, which has no dotfiles checkout to read. `t3_pin_check.py --open-prs` opens one bump PR in each repo that is behind (the sha256s are the linux lines of the release's `SHA256SUMS`; it decides per repo: a repo whose bump PR for that exact version is already open (head branch `t3-pin/<version>`, the whole version compared for equality) is left alone and one that has none gets one, so a run that stopped half way is finished by the next; it exits 4 only when every repo that is behind already has its PR; it never moves a pin back; it never merges). The daily `schedules-check` unit runs `t3_pin_check.py --notify` after every run (`ExecStopPost`), which posts drift to the coordinator inbox and fails the unit; it opens no PR there. Run `t3_pin_check.py --open-prs` by hand after a `t3 update`.

## Two applies

`modify_settings.json.tmpl` asks the coordinator's hook for its settings entries by running `node` while it renders. On a fresh pod the first apply renders `settings.json` before `05_container_tools.sh` has installed node, so it prints a `WARN ... did not print its settings entries` and leaves the hook entries out. The hook script imports from the coordinator checkout's `node_modules`, so run `npm ci` there between the applies (the image's start script does). Run `chezmoi apply` a second time and they are added. Without `node_modules` the hook does not print its entries and the hook stays off. `tests/container-mode` runs the two applies with a stub `hook.ts` that imports nothing, so it does not exercise the `npm ci` step; the pod shows that.

The shell that runs `claude`, `kgate` and the other tools needs `$HOME/.local/bin` and `$HOME/.local/share/mise/shims` on `PATH` (the `ENV` of the image), not only in `.zshrc`.

## Proof

`python3 -m unittest discover -s tests/container-mode -v` renders the source with the real chezmoi into a throwaway HOME (files only, no run script, no network) and checks the Claude settings, the exact script set, the left-out paths, `chezmoi verify`, the lean mise set and the two-apply hook sequence. It cannot show the installed tools or a model call; those need the pod (`chezmoi verify`, `mise ls --missing` and `claude -p` inside it).
