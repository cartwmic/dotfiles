# kgate

`kgate` runs a heavy gate (a repo's slow test or lint command) on a Kubernetes cluster instead of on this Mac: the personal homelab cluster by default, or a second cluster reached through kubectl for a profile with `cluster = "<name>"` (see "A second cluster, reached through kubectl" below). One Python file, `dot_local/bin/executable_kgate.tmpl`, installed as `~/.local/bin/kgate`. It takes heavy-gate's command line and meets `run-and-wake` and `heavy-gate` only on the command line:

The cluster host is not in this repo. `KGATE_SSH` (`user@address`) wins; otherwise `kgate` reads `~/.config/kgate/host`, which chezmoi renders from the local data key `sshHosts.kgate` (`address`, `user`) plus the optional list `sshHosts.kgateFallback` (same fields per entry; see [profiles.md](profiles.md), "Local data keys"). With neither set, `kgate` exits 69 and the message names the key.

Control-plane failover. `KGATE_SSH` and the host file each take one `user@address` (the old form, unchanged) or an ordered list, separated by commas or lines (`#` lines are skipped). With a list, `kgate` tries each host in order with a bare `ssh ... true` (ConnectTimeout 8 s) at job start, uses the first that answers, and prints `kgate: control plane user@address` in the job output. If none answers it exits 69. A single host is not probed first, so its behaviour is as before. Failover happens only at job start: a job whose host dies mid-run still fails (69, unknown), and a rerun picks the next host. This is the homelab path only; a kubectl cluster is unchanged.

One ssh connection per job. Every ssh a homelab job runs (the probe, each kubectl call, the poll for the pod every 2 s, the exec, the `/out` copy, the delete) rides on one multiplexed connection: `ControlMaster=auto`, a `ControlPath` of `/tmp/kgate-mux-<random>/%C` (a private folder per job, short enough for a socket path), `ControlPersist=120` (a net for a client that is killed; the client ends the master itself with `ssh -O exit` and removes the folder on every way out: normal end, failure, SIGINT and SIGTERM, and `kgate cancel` of an orphan). Before this, each call was a new ssh handshake, and master-1's sshd (`MaxStartups 10:30:100`) dropped handshakes when about 30 queued jobs polled at once, which ended jobs with exit 69 `lost the pod while waiting for it`. A job never has more than 1 ssh session open at once (2 for an instant when a stopped exec is replaced by the delete), well under sshd's `MaxSessions 10`. A client killed with SIGKILL leaves its master up to 120 s and an empty `/tmp/kgate-mux-*` folder.

```sh
run-and-wake -- kgate -- sh -c 'npm ci && npm run typecheck && npm test'
```

A suite too slow for one pod can be split across several with `kgate-split` (`docs/kgate-split.md`, personal profile): its `[split]` table in the same `kgate.toml` is ignored by `kgate`.

The pane that started the job is woken when it ends, with the exit code and the log path. The cluster side (image, `kgate` namespace, pull token) is in the homelab repo, `docs/kgate.md`.

## CLI

```
kgate [--profile FILE] [--wait SECONDS] [--cpu N] [--mem SIZE] [--mem-limit SIZE] [--image REF] [--node NODE] [--sched-wait SECONDS] -- CMD [ARGS...]
```

- `--profile FILE`: the gate's profile. Default `kgate.toml` at the worktree root. A repo with several gates keeps one profile per gate next to its script and passes `--profile`.
- `--wait`: how long to wait for the pod to start (default 3600).
- `--sched-wait`: how long the pod may stay unschedulable before kgate gives up with exit 75 (default 1800; env `KGATE_SCHED_WAIT`, the flag wins). Homelab only. See "When the cluster is full".
- `--cpu`, `--mem`, `--mem-limit`, `--image`: override the profile. `--mem` sets the memory request, `--mem-limit` the limit (see "Memory: request and limit"). `--node`: pin one node (never an excluded one: see "Nodes kgate never uses"). On the homelab `--cpu` is rounded up to whole 4-CPU slots (see "CPU slots").
- CMD runs in the same directory, at the same absolute path, inside the pod.
- `kgate cancel [--wait SECONDS] JOB_ID` and `kgate cancel --list` stop one job and list the running ones; see "Cancelling a job".
- `kgate report [--days N] [--repo NAME] [--all] [--json]` summarises the job log and changes nothing; see "Report".
- `kgate prune [--delete]` removes old job output folders; a dry run unless `--delete`; see "Prune".

## What it does

1. Ships the git worktree of the current directory to one pod: tracked and untracked non-ignored files, the `.git` file and the shared git folder (on a kubectl cluster no `.git`: see "A second cluster"), all at the same absolute path. The shared git folder is shipped lean: `rr-cache/`, the reflogs (`logs/`, `worktrees/<name>/logs/`) and the `worktrees/<name>/` metadata of every other linked worktree stay here, since git in the pod reads none of them (2026-11-16: a coordinator pod uploaded 279 MB and took about 12 s to prepare, against about 3 s for a lean tree). Objects, refs, `packed-refs`, `HEAD`, `config`, `info/` and the shipping worktree's own `worktrees/<name>/` (its index and `HEAD`) ship. Ignored files (`node_modules`, `target`) stay here. Git submodules are skipped (see below).
2. **Tree hash.** Before sending, it computes the git tree hash of the shipped files (what `git write-tree` gives for an index of exactly those files). The pod recomputes it after unpacking. If they differ, the job fails and CMD never runs.
3. **Version preflight.** The pod checks each tool in the profile. A mismatch fails the job and prints the tool, expected and found.
4. Runs CMD with the output streaming back live. CMD's exit code is kgate's.
5. **`/out`.** Whatever CMD writes to `/out` (also `$KGATE_OUT`) in the pod is copied to `<state>/<id>.out/` before the pod is deleted, whether CMD passed or failed.
6. Deletes the pod and its Secrets, on every path: CMD's exit, exit 69 (including "lost the pod while waiting for it") and an interrupt. If the delete fails (the 2026-11-16 etcd timeout did), kgate tries again for up to 60 s (`CLEANUP_RETRY_S`; each attempt is cut off after 30 s, waits between attempts 2, 4, 8, 15 s) and then gives up with `cleanup not confirmed`. A job that never created a pod (cluster unreachable, refused before the create) tries once. At each start it also removes what a client that died left behind.
   A process CMD leaves behind (`( sleep 600 ) &`) can keep the exec stream open after CMD ends. Once the `end` line is read, the client gives the stream `END_GRACE_S` (10 s) to finish, then drops the exec, keeps CMD's exit code from the end line, and deletes the pod, which ends what was left. The note `CMD left a process holding the exec stream; not waiting for it` is printed when that happens (five coordinator jobs held their pods 2 to 2.5 hours before this, 2026-11-16).

**A file outside the worktree is refused.** The pod gets only the worktree, so a CMD element that names an existing local file or directory outside it would not be found there and the job would fail after waiting for scheduling (2026-11-13: `kgate -- sh /tmp/.../unit.sh`, twice). Before anything is submitted, kgate checks each element after `--`. If it resolves, relative to the current directory, to a path that exists here, is outside the worktree root and lies under the home folder, `/tmp`, `$TMPDIR`, `/var/tmp` or `/run/user`, kgate prints `kgate: refused: PATH is outside the worktree ROOT; ...` and exits 64 with no log record and no cluster call. System paths (`/bin/sh`), pod-only paths (`/out`, `/cache`: they do not exist here), the folders themselves (`/tmp`) and options (`-x`) pass. The text inside `sh -c '...'` is one element and is not read. `--profile FILE` may be anywhere: kgate reads it here. A path that the pod would create (such as `--out /tmp/jout`) is refused when a file of that name happens to exist here; use `/out` or another name. The shared git folder of a linked worktree is shipped on the homelab but is not part of the worktree root, so a path inside it is refused too. A script the check misses (a path inside a `sh -c` string, or `--flag=/tmp/x`) still fails in the pod. To fix a refusal, put the file in the worktree or run the command inline.

**Submodules are skipped, not shipped.** A submodule is a gitlink (mode 160000) in the index, and it shows up in the file list as a directory, empty when it was never initialised. kgate leaves every gitlink out of the file list, so it is neither in the tar nor in the tree hash. The Mac and the pod hash the same list, so the check matches whether the submodule is initialised or not, and a real mismatch still fails it. kgate prints one line, `kgate: not shipping submodules: a, b`. On the homelab, where `.git` ships too, the gitlinks stay in the shipped HEAD and index, so kgate adds an empty directory at each skipped path to the tar: that is what a clone without `--recurse-submodules` leaves, and `git status` in the pod is clean. A submodule's own repository (`.git/modules/<name>`, also `worktrees/<name>/modules` of a linked worktree) is left out of the tar, since its files are not shipped and git does not need it for a clean status. A kubectl cluster has no `.git` in the pod, so it needs neither. A job that needs a submodule's files cannot run on kgate. Any other directory in the list, such as a nested repo that is not a submodule, is still refused with exit 69.

The pod's first process is `tini` (`tini -- sleep infinity`), so processes a gate orphans are reaped, not left as zombies. The pod's memory request is `memory` and its limit is `memory_limit`, which equals `memory` unless the profile sets it (see "Memory: request and limit"). `CARGO_BUILD_JOBS`, `RAYON_NUM_THREADS` and `MAKEFLAGS=-jN` are set to the CPU request (after the round-up in "CPU slots"). The image is pinned by digest. The scheduler places pods, and a full cluster queues jobs on this machine before they make a pod (see "When the cluster is full"). Pods run on amd64 nodes other than the control plane and the Mac mini (`NEVER_NODES` in the script: a required `NotIn`, and both also carry a taint kgate pods do not tolerate). agent-4, the GPU node, takes jobs only as overflow (`OVERFLOW_NODES`): the pod has a `preferredDuringScheduling` node affinity of weight 100 for every other node, so agent-4 is eligible but scores lowest and is used only when no other node has room for the pod's requests (Michael, ask 742, 2026-11-08). The G14 (`cartwmic-g14-wsl`) is preferred (`PREFER_NODES`, a second weight-100 term): it runs the same gate about twice as fast, so a job goes there first when it is up and has room, else to agents 1 to 3, and agent-4 last (Michael, ask 765, 2026-11-08). A pinned `--node` ignores the preference. The preference applies to every unpinned job, journeys included (Michael, ask 775, 2026-11-09: journeys may use the G14; the coordinator-session race that once kept them off it was fixed in coordinator #299. Their run time there varies with the load on the laptop: the median in the kgate log is about 770 s against 1280 to 1600 s on the agents, but one run on 2026-11-09 beside other jobs took 1239 s). A profile with `prefer_nodes = false` leaves the G14 term out; no profile sets it today. `--node` still refuses agent-4, the control plane and the Mac mini. The G14 laptop (`cartwmic-g14-wsl`) is schedulable again since 2026-11-06; `--node cartwmic-g14-wsl` pins a job there. Until homelab#101 (9f6ef66, 2026-11-05, systemd-timesyncd off) its WSL2 wall clock stepped back about 2.8 s every 30 s (a probe on 2026-11-05: 11 s of drift in two minutes; agent-1 had none), so tests that compare times flaked there (an agent-kit watchdog test, a heavy-gate 20-second check). It now follows the Windows clock, which slews up to 8% for about 15 s roughly every 9 h, and it can read up to about 2 s ahead of other nodes.

## Cancelling a job

```sh
kgate cancel --list                     # the jobs running now: id, run-and-wake job id, pid, node, age, cwd, command
kgate cancel [--wait SECONDS] JOB_ID    # stop that one job (default wait 120)
```

**Never `pkill`, `killall` or `kill $(pgrep ...)` to stop a kgate job.** A pattern kills every seat's job that matches it, on every node. `kgate cancel` is the only supported way, and a caller cancels **its own job id only**. For the other processes around a job (an ssh tunnel, a test server, a runner), `kill-mine '<pattern>'` signals only those your own session started.

How it works:

- Each running client has an entry in `<state>/active/<kgate id>.json` (id, run-and-wake job id, pid, the process's start time and command, `pidns` and `locked` (what they mean: "A starting job ends the orphans", below), cwd, node once known, and `thread`: the T3 thread that started it, from `T3CODE_THREAD_ID`, else null; the builder seat's Stop hook reads it, see docs/run-and-wake.md). It is written when the job starts and removed when the job ends, including when kgate fails with an unexpected error, but not while the job's pod may still exist: if the delete was not confirmed (the end line says `cleanup` false) or the client died inside it, the entry stays, so a later client or `kgate cancel` can find and delete the pod. The first SIGTERM or SIGINT ends the job; later ones are ignored while the cleanup runs (a stop that signals the whole process group reaches the client twice: dotfiles#481). The client starts ignoring them only once the job has the stop, not when the signal arrives: Python drops an interrupt that is raised inside a `__del__`, and every finished kubectl call frees a `Popen` whose `__del__` runs, so a stop can be lost. Until the job has it, a signal more than 1 s after the last one raises it again.
- `JOB_ID` is kgate's id (`kgate-<epoch>-<pid>`, printed in the job log and the record) or the run-and-wake job id (`RUN_AND_WAKE_JOB`, `job` in the record). The match is exact. A prefix, a pattern, or an id that matches no job or more than one job is refused with exit 64, and nothing is signalled. There is no cancel-all.
- Before signalling, cancel checks that the pid is still the same process (same start time and command as the entry). Then it writes `<state>/active/<id>.cancel` and sends SIGTERM to that one pid: not a process group, not a parent, not a child, not the `run-and-wake` wrapper. The client's SIGTERM path runs as it always did: copy `/out` back, delete the pod and both Secrets, write the record, exit 143. Because the marker is there, the record's `reason` is `cancelled by kgate cancel` (and `"cancelled": true`), not `interrupted (SIGTERM)`.
- Cancel waits up to `--wait` seconds for that job's end line in `log.jsonl`, prints it, and exits 0. While it waits it sends SIGTERM again every 2 s (to the same pid, after checking again that it is the same process), so a stop the client lost is raised again; a client that has the stop ignores the repeats. The job's own exit code (143) is in the line. If the job has not ended by then, cancel exits 69, prints the client's pid and says it did not force it. Cancel never escalates to SIGKILL by itself; the caller decides (`kill -9 <that pid>`).
- **Orphan.** If the client is already gone (killed -9, or the Mac rebooted) and left no end line, cancel deletes exactly that job's `pod/<id>`, `secret/<id>-env` and `secret/<id>-pull` (after checking that the pod, if it exists, carries the `app=kgate` label), writes an end line with exit 143, `reason` `cancelled by kgate cancel (client already gone)`, `cleanup` true or false and `"cancelled": true`, and removes the entry. If the cluster is unreachable it exits 69 and keeps the entry so you can run it again.
- A job that ended on its own but left its entry behind is reported from its end line and the entry is removed. If its end line says `cleanup` false (its delete was never confirmed), cancel deletes the pod first, keeps the job's own end line and removes the entry only once the delete is confirmed.
- **A starting job ends the orphans of its cluster.** The pod cannot see this machine's pids, so a pod whose client died keeps running; the next client to start can tell. After kgate reaches the cluster and before it creates its own pod, it does what the Orphan step above does for every entry of that cluster whose client is gone. A client is gone when nobody holds its lock: every client keeps an exclusive `flock` on its own job log (`<state>/<id>.log`) for as long as it runs, and the entry and the queue ticket say `"locked": true`. The kernel drops the lock when the process dies, and every pid namespace on the machine sees it alike, so this tells a client that died with its container (a restart ends the old pid namespace for good) from one that is running in another, live namespace, which a pid cannot. Both are handled with no pid check. That works the same on the agent host, on a plain Linux machine and on a Mac (no pid namespace there, same lock). Each is ended with exit 143, `reason` `ended by kgate: its client (pid N) is gone`, `"cancelled": true` and `reaped_by` (the id of the job that did it), and one `kgate: ended <id>: ...` line in the new job's output. Each kubectl call is cut off after 30 s. A delete that is not confirmed, or a pod that is not kgate's, leaves the entry for the next client, prints one `could not end ...` line and never changes the new job's exit code. An entry whose client ended with its end line written and `cleanup` false is handled the same way: the pod is deleted, the client's own end line stays, and the entry goes only when the delete is confirmed (`kgate: ended <id>: its client ended without confirming the pod delete; pod deleted`). Two clients starting together take a lock on the job's entry file (`flock`, no extra file), and one that finds it held skips the job, so a job gets one end line. An entry from an older client, which holds no lock and has no `locked` mark, is judged as before: gone when its start time and command are not running here and it was written in this pid namespace; with no `pidns`, or from another pid namespace (a live client looks gone there), it is left to `kgate cancel`. Those entries end with their jobs, so this is only the jobs that were running when kgate was updated. Nothing runs between jobs: if no client starts, an orphan stays until one does.

| Exit | Meaning |
|---|---|
| 0 | The job ended. Its end line is printed. |
| 64 | Bad command line, or the id matched no running job or more than one. Nothing was signalled. |
| 69 | The job was signalled and did not end in `--wait` seconds, or the orphan cleanup could not reach the cluster. |

## The CI `tests` check on kgate (the fallback)

When GitHub's runners fail twice the same infrastructure way, the same check runs on kgate at the same commit; if that run is green, the PR merges with `--admin` (ask #849=A). The check is `scripts/ci-linux.sh`, the command the CI `tests` job runs. The kgate image carries what it needs (chezmoi, zsh, rsync, sqlite3, jq, lsof; `images/kgate` in the homelab repo), and `kgate.toml` pins it. From the PR's worktree:

```sh
run-and-wake -- kgate --cpu 4 --mem 4Gi --mem-limit 6Gi --wait 1800 -- scripts/ci-linux.sh
```

`CI_PAR_JOBS` is the width of `scripts/ci-par.py`'s suite pool. A homelab pod has a CPU request and, unless the profile sets `cpu_limit`, no CPU limit, so the pool cannot read its size from the cgroup and would use the node's CPU count; kgate sets it to the pod's CPUs (the `--cpu` value, rounded up to a slot; see "Pod environment"). `ci-par` prints `suite counts (ran, skipped)` at the end. Compare it with the same block in the GitHub `tests` log at the same commit: a pass that skips tests GitHub runs is not the same check. Only the exception below may differ. When you merge on kgate's green run, say so in the PR: the two failed GitHub runs, the kgate job id and log path, the head it ran, and the counts comparison; then merge with `--admin`.

**The one exception (CI-plan lead's decision under #849=A).** kgate runs the same `tests` check except `RestartJourneyTest` in `tests/agent-browser/test_login_unit.py`. It starts the real `agent-chrome.service` unit under the user systemd manager and restarts it ten times, and a pod has no user manager (and no `ss`). It skips there: one extra skipped test in `tests/agent-browser`.

**The guard.** The fallback does not apply to a PR that changes any of the code that test runs:

- `dot_config/systemd/user/agent-chrome.service`
- `dot_local/bin/executable_agent-chrome`
- `tests/agent-browser/test_login_unit.py`

For such a PR, wait for GitHub's run, or run that one test on the host desktop machine (`python3 -m unittest discover -s tests/agent-browser -p test_login_unit.py`, where a user systemd manager runs), and say which in the PR.

## No fallback; exit codes

| Exit | Meaning |
|---|---|
| CMD's code | CMD ran to its end. |
| 64 | Bad command line, or CMD names a file that is not in the worktree (see "A file outside the worktree"). Nothing was submitted. |
| 69 | The job could not start or finish on the cluster. The reason is printed and in the record. |
| 75 | The pod was still unschedulable when `--sched-wait` ran out. The pod is deleted, CMD never ran. |

69 covers: cluster unreachable, no or bad profile, image not pinned by digest, a secret or the pull token unreadable, a service the gate needs that the pod cannot provide, pod never started (wait ran out, image pull failed), the node evicted the pod (`evicted: <the kubelet's message>`, see "Ephemeral storage and eviction"), tree hash differs, tool version differs, and a lost connection to a pod after CMD started (on a kubectl cluster, one the cluster did not evict, or a second eviction).

**A lost pod says why.** When the connection to a started pod ends before CMD reports its end (`lost the pod before CMD finished (kubectl exit N)`), kgate reads the cluster before it deletes the pod and appends `; pod end reason: ...` to the reason (and records it as `lost_pod`): the pod's phase and message, the container's terminated state, a node that is not Ready, the pod's warning events (and `Killing`, `Preempted`, `Evicted`), and `oom_kill` in the container's `memory.events` when the pod is still Running (CMD runs under `tini -- sleep infinity`, so the kernel killing CMD for memory leaves the pod and its container looking fine: only the cgroup says so). Each read is cut off after 20 s and a read that fails is left out. The text before `; pod end reason:` is unchanged. A failed read of the pod while waiting for it (an etcd timeout or a dropped ssh) is tried again for 60 s (`POLL_RETRY_S`) before the job ends as `lost the pod while waiting for it`; a pod that is `NotFound` ends it at once, with the same end reason.

**kgate never runs CMD on this Mac, and never reruns a job that started, except once on a kubectl cluster when the cluster evicted its pod ("Eviction" below).** A cluster outage shows as failed gates. A CMD that itself exits 69 looks the same by code; the record's `reason` tells them apart (it is JSON `null` when CMD ran to its end, and a text reason otherwise).

## When the cluster is full

When no node has room for the pod's CPU or memory request, the pod stays `Pending`. Since 2026-11-16 a homelab job does not make such a pod while others like it already wait: it waits in a local queue, says so, and creates its pod when there is room. It never runs the job on the Mac.

- **The queue (homelab).** Before it creates its pod, the client lists the cluster's `app=kgate` pods. A pod counts as waiting for room when it is `Pending`, `PodScheduled` is `False` with reason `Unschedulable`, and the scheduler's message says `Insufficient` (a node-selector or taint miss is not "full"). A waiting pod holds this job back when it asks no more of any resource (cpu, memory, ephemeral storage), is pinned to no node or to the node this job is pinned to, and its priority is at least this job's. If one does, no node has room for this job either, so the job prints `kgate: queued: the cluster is full: N kgate pods already wait for room and ask no more than this job (<pod>: <scheduler message>)` and looks again every 3 s. When none is left it prints `kgate: left the queue after Ns; creating the pod` and goes on as before. The record has `queue_wait_s` (absent when the job never queued). A job that asks more than the waiting pods (a 6-cpu journeys gate behind 2-cpu pods) is not held: they say nothing about it. The rule has no pod count and no CPU budget in it: the scheduler's own answer is the limit (design principle 9; a count would be a guess, pods ask 1 to 12 CPU).
- **Order on this machine.** Each waiting client writes a ticket in `<state>/queue/<id>.json` (its size, pin, priority, arrival time, its own `--wait` deadline and, once the quota has refused the job, a `quota` mark that holds the refusing quota's name; removed on every way out. The next client that sees one removes it when its client is gone (the same lock check as the orphan reaper above, so a ticket whose client died with its container goes too), or when it is more than 60 s past its client's deadline, which covers a client that is stopped, or an older one in another pid namespace whose pid cannot be checked: a stale ticket holds later jobs back for at most that long). A job is also held while a live ticket that arrived before it (higher priority first) blocks it by the same rule (or is marked with a quota that counts this job, see "Quota" below), so a `kgate-main` job is not made to wait behind PR gates, and one `flock` on `<state>/queue/.lock` covers "look, create, wait until the scheduler has answered for the new pod (at most 20 s)", so two clients that start together do not both see room that only one of them gets. A job that waits only for a neighbour's placement (the cluster has room) looks at the local tickets every 0.3 s and says nothing unless that lasts 5 s; it records no `queue_wait_s`. Only a client with no ticket ahead of it looks at the cluster, so a long queue costs about one `kubectl get pods` every 3 s, not one per waiting job. Clients on other machines are not in this queue; they see the pods in the cluster.
- **Cancel and limits.** `kgate cancel` works while a job queues (exit 143, no pod made). The queue wait counts against `--wait` (default 3600 s); when it runs out the job exits 69 with `reason` `pod did not start within <N>s: Unschedulable (queued, the cluster is full: ...)`. A job that cannot read the waiting pods (the call fails) prints `could not read the waiting pods; creating the pod without queueing` and creates its pod as before. A create that the namespace's ResourceQuota refuses is a wait in this queue too ("Quota" below), and then the exit-69 reason is `quota not available within <N>s: <message>`; a job held behind one the quota refused ends with `pod did not start within <N>s: Unschedulable (queued, behind <id>, which the quota refused and was first)`. A kubectl cluster is not queued (its autoscaler and namespace quota have their own waits).
- A full cluster leaves a pod `Pending`, with `PodScheduled` `False` and reason `Unschedulable`, for the first job that finds no room, or any job the queue's rule lets through (it asks more than the waiting pods, or it is more urgent). The client waits by itself. It prints `kgate: waiting for the pod: Unschedulable` to the job log when that state first appears.
- **Scheduling deadline (homelab).** `--sched-wait SECONDS` (default 1800; env `KGATE_SCHED_WAIT`; the flag wins; whole seconds, at least 1) counts from the moment the pod is created (not from the queue). If the pod is still `PodScheduled=False` with reason `Unschedulable` when it passes, kgate deletes the pod, prints one line and exits **75**: `kgate: pod not scheduled within <N>s: <scheduler message> (pinned to node <NODE>); exit 75, CMD was not run on this Mac` (the pin part only when `--node` was given). The record's `reason` is `pod not scheduled within <N>s: <scheduler message>[ (pinned to node <NODE>)]`. There is no retry. 75 is `EX_TEMPFAIL`; kgate uses it for nothing else, though a CMD that itself exits 75 looks the same by code (as with 69, `reason` tells them apart). Only the jobs the queue lets through sit in the cluster waiting, so far fewer jobs reach 75 (L6, 2026-11-09 to 11-16: 206 jobs exit 75, and 344 jobs in all were lost to a full cluster). A pod that is already scheduled and is pulling its image or running an init container is not unschedulable: the deadline does not apply to it, and only `--wait` ends it. A kubectl cluster is not covered (its autoscaler can take longer to add a node); there only `--wait` applies.
- Otherwise it keeps waiting until `--wait` seconds (default 3600) after the job started.
- If the wait runs out, it exits 69. The record's `reason` is `pod did not start within <N>s: Unschedulable <scheduler message>` (the pod waited in the cluster) or `pod did not start within <N>s: Unschedulable (queued, ...)` (the job waited here). kgate copies the scheduler message unchanged, up to 300 characters. Kubernetes scheduler messages look like `0/N nodes are available: ... Insufficient memory`.

The reason tells a full cluster apart from the other ways a job fails to start. These are the prefixes kgate writes:

| `reason` starts with | Cause | Capacity? |
|---|---|---|
| `pod not scheduled within <N>s:` (exit 75) | No node had room for the `--sched-wait` deadline. | Yes |
| `pod did not start within <N>s: Unschedulable` | No node had room for the whole `--wait` (a kubectl cluster, `--sched-wait` set above `--wait`, or the job queued here the whole time). | Yes |
| `pod did not start: ` (for example `ErrImagePull`, `ImagePullBackOff`, `CreateContainerConfigError`, or a pod phase of `Failed`) | The pod failed before CMD ran. | No |
| `cluster unreachable (` | The cluster or its ssh route is down. | No |
| `could not create the pod: ` | The cluster refused to create the pod. | No |

Every other exit-69 reason (a bad profile, a tree hash or tool version mismatch, an unreadable secret) is not a capacity problem either.

**What callers do.**

- Wait. Pass `--wait 1200` for short gates.
- On exit 75, or exit 69 whose `reason` starts `pod did not start within` and contains `Unschedulable`, the caller may run heavy-gate once, but only when the profile fits some kgate node (see the node table in "How many jobs at once"). Every committed profile does. Then it must report "(2) no kgate capacity" and quote the reason.
- A profile bigger than every node is a profile bug. Report it as one, with the reason quoted. Never run heavy-gate for it as (2).
- Every other exit 69 is not a capacity problem. Report it as it is. Never report it as a Mac run in disguise.
- The client never falls back to the Mac. A fallback inside the client would make a result's origin ambiguous.

**The limit.** `Unschedulable` means no node can take the pod now. It does not say that no node ever could. A profile bigger than every node gets the same prefix, with `Insufficient memory` or `Insufficient cpu` in the scheduler message, and so does a `--node` that matches no node. The reason alone cannot separate those cases from a full cluster, so the caller's fit check does.

## The coordinator's pause

The coordinator can pause new work on the fleet. Its pause is a folder, `$COORDINATOR_STATE_DIR/brake/` (when it is unset, the profile's own coordinator state: `~/.local/share/coordinator/brake/` on the personal profile and `~/.local/share/coordinator-work/brake/` on the work profile), with one file per reason, named for the trigger that wrote it (the inbox lag alarm writes `lag`). The pause is on while the folder holds any file.

Before it makes a pod, kgate looks at that folder. If it holds a file, the job prints one line naming each reason, `kgate: paused: waiting for the coordinator's pause to lift before creating a pod (cpu: <words>; lag: <words>)`, makes no pod and does not touch the cluster, and looks again every 10 s (`KGATE_BRAKE_POLL_S` changes that, for tests). When the folder is empty or missing it prints `kgate: the pause lifted after Ns; going on` and carries on as before. A reason that appears while it waits is named again. kgate does not know what a reason is: any file counts, except a dot file or a folder, so a new trigger needs nothing here. There is no switch to skip the wait.

The wait does not count against `--wait`: `--wait` counts from the job's start, and the time spent waiting for the pause is added to it (the first pod and the rerun alike), so a pause longer than `--wait` does not fail the job when it lifts. `kgate cancel` or a stop ends a paused job with no pod made. A pod that is already running is left alone. The rerun of a pod the cluster evicted (`<id>-r2`) makes a pod, so it waits for the pause like the first one; the job's `--wait` (plus the pause time) and the pod deadline (which does count the pause) are read after that wait, so a pause long enough to use up the pod deadline ends the job with the usual "not rerun" reason. The record has `brake_wait_s` (absent when the job never waited; the sum when it waited more than once). The default folder is chosen when chezmoi renders the script, so each profile reads its own coordinator's folder; on a host with no coordinator state the folder is missing and nothing changes.

## Nodes kgate never uses

A homelab pod carries a required node affinity that keeps it off `ubuntu-server-k8s-master-1` (control plane), `mac-mini-worker` and `ubuntu-server-k8s-agent-3` (`NEVER_NODES` in the client). `--node` with any of them is refused (exit 69, `excluded`, no pod). agent-3 is the GitHub CI runners' node: kgate pods had reserved its CPU and CI runners stalled, so kgate never runs there (coordinator decision #3311; the homelab repo pins the runner sets to agent-3). kgate can use agent-1, agent-2, agent-4 (overflow only, below) and the G14. Every pod also carries a required pod anti-affinity against the live agent host (namespace `agent-host`, label `app=agent-host`): no new kgate pod lands on the node the agent host runs on, wherever it moves, and a pinned `--node` on that node waits. Running jobs are not moved. On 2026-11-22 agent-1 reached load 82 on 16 cores with two 4-CPU kgate pods beside the agent host, and coordinator turns crawled (Michael asked for this fix).

The rule works both ways: a running kgate pod also keeps a new agent-host pod off its node. So during an agent-host restart (its Deployment uses `Recreate`), kgate pods waiting for room can take agent-1, and the agent host then starts on its fallback node, agent-4. If agent-4 also has a kgate pod, the agent host (priority `homelab-critical`) preempts it, and that job ends with exit 69 and is not rerun; this is accepted, because an agent-host restart already ends every agent session in that pod, and most kgate callers run there. A job pinned with `--node` to the agent host's node waits for the schedule wait (`--sched-wait`, default 30 min) and then exits 75.

## CPU slots

On the homelab, nodes are split into slots of 4 CPUs (`SLOT_CPU` in the client; homelab ask 1187). kgate never runs on agent-3: that node belongs to the pinned GitHub CI runners (decision #3311, after kgate pods reserved the CPU the runners needed and stalled CI; see "Nodes kgate never uses"). The slots were first made so kgate pods and the runners could share agent-2 and agent-3; the rounding stays, so a pod of 1, 3 or 6 CPUs still does not strand a part slot. The client therefore rounds every homelab pod's CPU request up to a whole number of slots: 1 to 3 become 4, 4 stays 4, 5 and 6 become 8, 12 stays 12. This applies to the profile's `cpu` and to `--cpu`, before any pod is made. `CARGO_BUILD_JOBS`, `RAYON_NUM_THREADS` and `MAKEFLAGS` follow the rounded-up request, and so does the job record's `cpu`. When the client raises a request it prints one line, `kgate: cpu request raised from N to M: a homelab pod takes whole 4-cpu slots` (to the console and the job log, like every kgate note), and the pod line shows the new value.

If the profile sets `cpu_limit` below the rounded-up request, the job is refused before any pod is made (`cpu_limit (N) must be at least cpu (M)`, M being the rounded-up value); raise or drop the limit. A request of 4 or more that is already a whole number of slots is unchanged. Service containers count toward the total, and the job container takes the rise. On the homelab the only service is the Docker sidecar (see "Docker jobs"): its `[docker] cpu` plus the job's `cpu` is rounded up as one pod, so a pod of 2 + 3 CPUs asks for 8, not 5. A kubectl cluster is unchanged: it asks for exactly the `cpu` it is given.

## Priority

Every homelab pod runs in the `kgate` PriorityClass (`PRIORITY_CLASS` in the client; the class is in the homelab repo, `k8s/kgate/priorityclass.yaml`: value -100, `preemptionPolicy: Never`, not the global default). It is below every app and system pod, so an app pod that cannot be placed may preempt a running job, and a job's pod is evicted first under node pressure. A preempted job ends like any lost pod: exit 69, `lost the pod before CMD finished; the result is unknown and the job is not rerun`, and the cluster's `Preempted` event on the pod says why. A job pod never preempts anything. The class changes scheduling, preemption and eviction order only: it does **not** change a pod's CPU share at run time, and jobs still have no CPU limit unless the profile sets `cpu_limit`. A second cluster's pods (`cluster = "<name>"`) set no class; that cluster's own policy decides.

A profile may opt in to a second class, `priority_class = "kgate-first"` (the default is `kgate`; the accepted values are `kgate`, `kgate-first` and `kgate-main`; homelab only, a profile for a kubectl cluster that sets the key is refused). `kgate-first` is value -50 (homelab repo, `k8s/kgate/priorityclass-first.yaml`, `preemptionPolicy: Never`): the scheduler places the pod ahead of waiting `kgate` pods, and it still never evicts a running job or outranks an app or system pod. A third class, `kgate-main`, is value -40 (homelab#440, `preemptionPolicy: Never`): it is placed ahead of `kgate-first` and `kgate`, and also never evicts a running job. The coordinator's main run asks for it so it schedules before PR gates (decision #3034). A fourth class, `kgate-docker` (value -100 like `kgate`, `preemptionPolicy: Never`), is set by kgate itself on a Docker job and cannot be chosen: a profile `priority_class` or `KGATE_PRIORITY_CLASS` together with `services = ["docker"]` is refused (exit 69, no pod), because the Docker quota is scoped to that class. Any other value is refused with `profile priority_class must be kgate or kgate-first or kgate-main` (exit 69, no pod).

The environment variable `KGATE_PRIORITY_CLASS` picks the class for one run and wins over the profile's `priority_class`, the way the `--sched-wait` flag wins over `KGATE_SCHED_WAIT`. It takes the same three values; an unknown value is refused as `KGATE_PRIORITY_CLASS must be kgate or kgate-first or kgate-main` (exit 69, no pod), and on a kubectl cluster it is refused like the profile key. Unset or empty leaves the profile's choice. Apply order is the same: the homelab repo first (the class must exist), then this client. The client's pod line and the job record say which class a job ran in (`kgate: pod <id> on ...: ..., priority class kgate-first`, and `priority_class` in the record), and the profile's `cpu_limit` when one is set (`, N cpu limit`, `cpu_limit` in the record), so runs can be told apart afterwards.

The class must exist before a client that names it runs: a pod that names a missing class is refused at creation (`no PriorityClass with name kgate was found`), so every job exits 69 with that message. Apply the homelab repo first.

## Docker jobs

A gate that builds or runs containers can ask for a Docker daemon. It is opt-in: a profile with `services = ["docker"]` and a `[docker]` table (profile example in "Gate profile"). A job with no service is unchanged, byte for byte. Homelab only: a profile for a kubectl cluster that has `[docker]` is refused.

- **What the pod gets.** A native sidecar (an init container with `restartPolicy: Always`, like the mssql sidecar) running the dind image from `[docker] image`, started as `dockerd --host=tcp://127.0.0.1:2375` by the image's own entrypoint (`dockerd-entrypoint.sh`). A short `command` runs first: `unshare --mount --propagation private` and a bind mount of the sidecar's own cgroup (from `/proc/self/cgroup`) over `/sys/fs/cgroup`. It is the pod's one privileged container, and so it shares the node's cgroup namespace; without the bind mount the image's `dind` script made `/init` and `/docker/<id>` at the node's root cgroup, outside the pod: the containers a job ran were left out of `docker_peak` and the sidecar's memory limit did not hold them. With it they are children of the sidecar's cgroup, so `[docker] memory_limit` is the limit for every container the job runs, `docker_peak` counts them, and the node's root cgroup is not touched (busybox `unshare` has no `--cgroup`, so a private cgroup namespace is not available). It has no TLS (`DOCKER_TLS_CERTDIR=""`) and listens on the pod's loopback only. Its data root `/var/lib/docker` is an `emptyDir` that only the sidecar mounts: no `hostPath`, no host socket, and the layers count against the pod's ephemeral storage (see "Disk" below). A startup probe runs `docker info` every 5 s for `ready_s` seconds, so the job container starts only once the daemon answers. The job container stays unprivileged, keeps the `/cache` hostPath, and gets `DOCKER_HOST=tcp://127.0.0.1:2375`.
- **`[docker]` keys.** `image` (required, pinned by digest: `name@sha256:<64 hex>`, any host), `cpu` (2), `cpu_limit`, `memory` (4Gi), `memory_limit` (the memory), `ready_s` (120, an integer of at least 30). The sidecar's sizes follow the same rules as the mssql sidecar's. Unknown keys, a `[docker]` without `services = ["docker"]` and `services = ["docker"]` without `[docker]` are refused (exit 69, no pod).
- **Disk.** The profile's `ephemeral_storage` and `ephemeral_storage_limit` are the Docker pod's disk in total, and every container has its own request and limit that add up to them. The API server admits a pod with no disk values and does not count it, so kgate sets both on every container itself; the kubelet also enforces a pod's disk only when every container has a limit. The sidecar takes `512Mi` and `1Gi` for its writable layer and logs (`DOCKER_SIDECAR_DISK`, `DOCKER_SIDECAR_DISK_LIMIT`) and the job container gets the rest (the default `24Gi` and `40Gi` give it `24064Mi` and `39936Mi`). The data root `docker-data` is an `emptyDir` with a `sizeLimit` equal to the pod's `ephemeral_storage_limit`, so a pull or build that grows past it evicts the pod (exit 69, `evicted: ...`). A Docker profile that sets neither key gets the campaign default, request `24Gi` and limit `40Gi` (not an error); one that sets only `ephemeral_storage` gets the larger of `40Gi` and that request as its limit; one that sets only a limit below `24Gi` is refused, like any limit below the request. A request or limit that leaves the job container nothing past the sidecar's share is refused. The disk is bounded by these values and by the node: the `kgate-docker` quota counts pods, CPU and memory, not disk.
- **Class and quota.** The pod runs in the PriorityClass `kgate-docker` (value -100, as `kgate`), and the homelab's ResourceQuota `kgate-docker` in namespace `kgate`, scoped to that class, counts only these pods. A profile `priority_class` or `KGATE_PRIORITY_CLASS` together with docker is refused; so a Docker job started from a shell that sets `KGATE_PRIORITY_CLASS` (the coordinator's main run sets `kgate-main`) is refused until that variable is unset. The class and the quota are in the homelab repo (`k8s/kgate/priorityclass-docker.yaml`, `k8s/kgate/resource-quota-docker.yaml`); apply it first, as for any class a client names.
- **Sizing and slots.** The pod's CPU is the job's `cpu` plus `[docker] cpu`, rounded up to whole 4-CPU slots as one pod (see "CPU slots"): `cpu = 2` with the default sidecar's 2 is 4; `cpu = 3` with 2 is 5, which becomes 8. kgate says so (`cpu request raised from 5 to 8: ... (with the docker sidecar's 2)`) and the job container takes the rise. The quota counts the rounded request, so size the profile to a whole number of slots. The memory is the job's plus the sidecar's (builds and containers run in the sidecar's memory, not the job's).
- **Start failure.** If the sidecar does not pass its probe (it exits, restarts, or `ready_s` runs out), kgate exits 69 with `the docker sidecar did not become ready (exit X, N restarts); its last log lines: ... (CMD not run)` and CMD never runs. The record's `reason` is that text.
- **Death after CMD started.** CMD's exit code is CMD's, whatever the daemon did: a CMD whose docker client is cut off exits non-zero by itself, and kgate does not turn it into 69. After CMD ends kgate reads the pod's status once if CMD exited 0, and again every second for up to 5 s if CMD failed (the kubelet shows a daemon's end about a second after the client is cut off). If the sidecar restarted or stopped it prints `kgate: the docker daemon restarted during the job (N restarts, last exit X, reason R); CMD's exit code is unchanged`, adds the old daemon's last log lines (`--previous`), and records `docker_sidecar` as `{restarts, exit, reason}`. A job whose CMD never started has no such note: its failure is the start failure above. A restarted daemon has lost its images and containers, so a job that needs them fails on its own; it is not rerun.
- **The queue.** A Docker job the `kgate-docker` quota refuses waits in the local queue like any quota refusal, and holds back only later Docker jobs ("Quota", above). A node job that fits is not held behind it. Node jobs still wait, as before, when the namespace's other quota or the cluster is full: a Docker job's CPU counts toward that quota too, so a busy day of Docker jobs can make some node jobs wait for quota.
- **v1 limits.** No bind mounts from the job's tree into containers (the daemon is in another container, so `-v $PWD:/x` mounts the sidecar's empty path; copy with `docker cp` or build with a context); no registry mirror, so every pull goes to the internet; no buildx cache export; the data root is gone with the pod, so layers are not kept between jobs. What stays out: Docker socket mounts, `--privileged` containers for the job's own use beyond what dind does, and anything on the host's own daemon.
- **Proof.** `docs/kgate-docker-live-proof.sh` is the live check for a deployed cluster (pod spec, build, run, compose, the sidecar restart, the start failure, the quota and queue). It changes the cluster only through kgate jobs. Unit tests: `tests/kgate/test_docker.py`.
- **Profile coverage.** The client reaches both desktop profiles unchanged (see "Profiles"); the Docker path runs on a personal machine with a homelab host only.

## Record

One JSON line per job in `${XDG_STATE_HOME:-~/.local/state}/kgate/log.jsonl`; the full output is `<id>.log` beside it. The older lines from before this version (with a `fallback` field) have a different shape.

| Field | Meaning |
|---|---|
| `id` | kgate's job id, also the pod's name |
| `cluster` | `homelab`, or the name of the cluster file |
| `cache` | kubectl clusters only: `pvc`, `fallback` or `none` (see "The cache claim") |
| `services`, `pod_start_s`, `service_ready_s`, `service_peak_bytes`, `service_cpu_usec` | kubectl clusters with a sidecar only: the services, seconds until the pod ran, seconds until the sidecar's startup probe passed, the sidecar's peak memory, and the sidecar's CPU time (its cgroup's `cpu.stat` `usage_usec`, read after CMD ends, same as `service_peak_bytes`; absent when it cannot be read) |
| `docker_sidecar`, `docker_peak` | a Docker job only (the record has `services: ["docker"]`). `docker_sidecar`: present only when the daemon was restarted or stopped after CMD started: `{restarts, exit, reason}` (see "Docker jobs"). `docker_peak`: the sidecar's peak memory in bytes (the `memory.peak` of the sidecar's own cgroup, which is `/sys/fs/cgroup` in the sidecar (see "Docker jobs"), so it counts every container the job ran, read once when CMD ends; absent after a restart, when the number would be a new daemon's) |
| `priority_class` | the PriorityClass the pod ran in (`kgate`, `kgate-first`, `kgate-main` or `kgate-docker`) on the homelab; null on a kubectl cluster, whose own policy decides. Absent on lines older than this field and on an orphan's end line |
| `cpu_limit`, `quota_wait_s` | `cpu_limit`: on a kubectl cluster, the effective CPU limit (`cpu` when the profile sets none); on the homelab, the profile's `cpu_limit`, present only when the profile sets one. `quota_wait_s`: the seconds spent waiting for namespace quota: on a kubectl cluster always (0 when none), on the homelab only on a job the quota refused (counted inside its `queue_wait_s`) |
| `queue_wait_s` | homelab, only on a job that waited in the local queue: seconds spent queued (see "When the cluster is full") |
| `brake_wait_s` | only on a job that waited for the coordinator's pause: seconds waited (see "The coordinator's pause") |
| `hold_wait_s` | only on a job a cluster hold held (the `kgate-hold` quota, on the job it refused and on jobs queued behind it): seconds held, part of `quota_wait_s` or `queue_wait_s`, and added to `--wait` like `brake_wait_s` (see "Quota") |
| `lost_pod` | only on a job whose pod was lost (exit 69, `lost the pod before CMD finished`): what the cluster said about why, also appended to `reason` as `; pod end reason: ...` |
| `job` | the run-and-wake job id (`RUN_AND_WAKE_JOB`), or null |
| `start`, `end`, `duration_s` | UTC times and seconds. `duration_s` is the whole job on the Mac: queue, pod start, unpack, CMD and copy-back |
| `run_s` | seconds CMD itself ran in the pod, from just before it started (the `running` line) to its exit. Two readings of a clock in the pod, so it leaves out queue, `pod_start_s`, unpack, tree hash and tool checks, and always lies below `duration_s`. Null when the pod never ran CMD |
| `repo`, `cwd`, `head` | repo name (the last part of the `origin` remote's URL without `.git`, so a clone in any folder logs its repo's name; the folder that holds `.git` when there is no origin), working directory, Mac HEAD |
| `tree` | the tree hash of what was shipped |
| `node`, `image`, `profile`, `cpu`, `mem`, `mem_limit` | where and how it ran; `cpu` is the CPU request the pod asked for (on the homelab, after the round-up to whole slots, see "CPU slots"); `mem` is the memory request and `mem_limit` the limit |
| `cpu_usec` | the job container's CPU time in microseconds: `usage_usec` in its cgroup's `cpu.stat`, read once when CMD ends, the way `memory.peak` is. It counts the container's whole life, so it includes the pod side's own unpack, tree hash and tool checks as well as CMD. One busy core for `run_s` seconds reads as about `run_s` × 1,000,000. Null when `cpu.stat` cannot be read (the field is not the same as `cpu`, the CPU request) |
| `peak_bytes`, `peak_source` | the container's peak memory: `cgroup` (`memory.peak`, kernel 5.19 and later) or `sampled` (highest `memory.current` seen every 0.5 s, on older kernels). It includes page cache. |
| `install`, `install_s` | the cached `npm ci` (see "Cached npm install"): `hit` (unpacked from the node cache), `miss` (a real `npm ci`, then kept) or `none` (the command never ran `npm ci`, or the profile has no `[install]` step), and the seconds the install steps took in the pod (0.0 for `none`). Both null when the pod never ran CMD |
| `ran` | CMD started |
| `exit`, `reason` | exit code; the reason when it is 69 |
| `out_files`, `cleanup`, `output`, `cmd` | files copied back; pod and Secrets confirmed deleted; log file; the command |
| `cleanup_attempts` | delete attempts made, only on a job that created a pod; `cleanup` is true when one was confirmed |
| `cancelled` | only on a job stopped by `kgate cancel` or ended by a later job because its client was gone: `true` |
| `reaped_by` | only on a job ended because its client was gone: the id of the kgate job that ended it |

## Report

`kgate report [--days N] [--repo NAME] [--all] [--json]` reads `${XDG_STATE_HOME:-~/.local/state}/kgate/log.jsonl` and writes nothing. It covers the jobs that started in the last `--days` (default 7). It prints one row per repo, command and node class. Rows whose median wall is over 300 s come first, then the rest; within each group, the most total wall time comes first, so a gate that runs often ranks above a one-off. The text table shows the first 30 rows; `--all` shows every row. `--json` always prints every row. The command is on both desktop profiles, as the kgate binary is.

- `runs`: jobs in the row. `not run`: jobs that exited 69 or 75 (could not start or finish; not scheduled before `--sched-wait`), or were killed (137, 143: `kgate cancel`, an interrupt, or an orphan ended by the next job).
- `wall med s`, `wall p90 s`, `wall total h`: execution time, `duration_s - pod_start_s`, over the jobs that ran. Jobs that did not run are left out, so a job killed at the limit does not move the median. p90 is the nearest rank: nine runs in ten finish within it. Total is the sum over those jobs.
- `cpu-s med`, `cores used`, `cores asked`: from `cpu_usec`, which only newer records have; older records are left out of these three. Cores used is the total CPU-s over the total `run_s` of those jobs. Cores asked is the median CPU request. `cpu_usec` also counts the pod's unpack and checks, so cores used reads a little high. A pod with no CPU limit can use more cores than it asked for.
- `peak max GiB`, `limit GiB`, `peak % limit`: the highest `peak_bytes` and the highest `mem_limit` in the row, and the worst single job's peak as a share of its own limit. 100% means that job reached its limit. The first two can come from different jobs, so a 100% can sit beside a peak below the row's limit: the job at 100% had the smaller limit.
- node: `g14` is `cartwmic-g14-wsl`; `other` is any other node; `unplaced` is a job that never got a node.

The command is grouped as the gate runs it: leading `env` and `NAME=value` words are dropped, since they carry ids and payloads that differ from run to run. So `env KGATE_RUNS=30 scripts/gate.sh` and `scripts/gate.sh` are one row, while `scripts/gate.sh` and `sh scripts/gate.sh` stay apart. Lines in the log that do not parse are skipped and counted in the header. A missing log is an empty report. The code is `report_*` in `dot_local/bin/executable_kgate.tmpl`; tests are `tests/kgate/test_report.py`, on a fixture log.

## Prune

`kgate prune [--delete]` is the retention for `<state>/kgate-<epoch>-<pid>.out/`, the folders `/out` is copied back to. Nothing else removed them (2026-11-20: 5,740 folders, 3.5 GB, the oldest 9 days). Without `--delete` it is a dry run: it prints each folder it would remove, a total and the bytes it would free, and changes nothing. `--delete` removes them, recomputing the list at that moment. Both run on both desktop profiles, as the kgate binary does; it is run by hand, nothing schedules it.

A folder is deleted when it is older than 3 days (`PRUNE_AGE_DAYS`; the age is the epoch in its name, which is when the job started) and none of these keeps it, checked in this order (the output counts each kept folder under the first that applies):

1. **Running.** `<state>/active/<id>.json` exists.
2. **Logged.** `log.jsonl` has a record for the id whose `start` is within the last 7 days (`PRUNE_LOG_DAYS`; a record with no readable `start` counts as recent). Because every finished job gets a record, this keeps every job for 7 days and the 3-day line only matters for jobs the log does not name.
3. **Cited by the main-run journal.** The coordinator's `main-journeys.jsonl` (`${XDG_STATE_HOME:-~/.local/state}/coordinator-ci/`, written by `scripts/main-journeys.sh`) has one line per run. A line names its receipt files (`receipts.cluster`, `receipts.bookends`), which print the `kgate-<epoch>-<pid>` ids of the runs' jobs. Every id in every receipt file of every line is cited. Lines with no `receipts` (flake rulings) cite nothing. A machine with no journal file has no such citations (the output says `journal not present`).
4. **Cited in an open PR body.** The ids in the body of every open PR of each GitHub repo whose name the log records as `repo`. `repo` is only a name (the last part of the origin URL), so each name is matched against the repos `gh api user/repos` lists; a name with no such repo (a scratch folder, a repo on another host such as gitea) is printed as not scanned. The whole body is searched, so the Proven section is covered.

It never touches `log.jsonl`, `active/`, the `<id>.log` files, `merged-*.out`, `split-*`, the queue and run files, or anything else: a candidate is a real directory directly under the state folder named exactly `kgate-<digits>-<digits>.out`.

**It fails closed.** Every source is read before anything is decided. If one cannot be read (`gh` fails or is missing, a line of `log.jsonl` (once NUL bytes are taken out of it, below) or of the journal does not parse, a journal receipt file is missing, `log.jsonl` is missing, `active/` is there but cannot be listed; no `active/` at all means nothing is running), it prints `kgate prune: refused, nothing deleted: <the source and why>` and exits 69, dry run or not.

**A line with NUL bytes is read without them.** A torn append to `log.jsonl` (a client killed mid-write, a pod restart; the writer is still open in dotfiles#774) leaves NUL bytes in a line, sometimes in front of a whole record (on the agent host, 1,278 NULs and then a job's end record). A refusal over it would block retention on every run until someone edited the job log by hand. So prune takes the NUL bytes out of such a line first:
- what is left parses as JSON: the record counts like any other, so a job named only there is kept for its 7 days;
- nothing is left: the line is skipped;
- text is left that does not parse (`\0\0{broken`): it refuses, as for any line that does not parse.

Each NUL line is named on stderr, dry run or not: `kgate prune: <state>/log.jsonl line <n> holds <count> NUL bytes: record kept` (or `: skipped`). A `--delete` run also records them in its `prune.jsonl` line (`nul_lines`: a list of `{"line", "nul_bytes", "record_kept"}`, empty when none). Any other line that does not parse, `{broken` for one, still refuses, because it could be a lost record of a recent job. Only prune reads through the NULs: `kgate report` does not use such a record and counts the line under `unreadable_lines`, and `end_line` (the end record of a running job) still passes over the line (dotfiles#774).

The byte count is disk blocks (`st_blocks`), what `du` reports and what deleting frees, not file sizes. A `--delete` run appends one line (time, folders, bytes, kept counts, NUL lines) to `<state>/prune.jsonl`; `log.jsonl` is the job log and is not written. Exit 0 when every planned folder went (or in a dry run), 69 when a source was refused, a folder could not be removed (the others still go, and the run is recorded), or `prune.jsonl` could not be written after the deletes (one line on stderr names the file), 64 for a bad command line. Tests: `tests/kgate/test_prune.py`.

## A second cluster, reached through kubectl

A profile with `cluster = "<name>"` runs the same contract (ship the worktree, verify the tree hash, stream output, copy `/out` back, delete the pod, one record, `kgate cancel`) on a second Kubernetes cluster that this machine reaches through local `kubectl`. Only the cluster adapter and the pod side differ. The homelab path is untouched and stays the default: a profile with no `cluster` key, or `cluster = "homelab"`, is a homelab job.

Everything about the second cluster is in a file on the machine, not in this repo: `~/.config/kgate/clusters/<name>.toml`. A machine without that file cannot reach the cluster. The profiles for it live next to the repo they gate, or in `~/.config/kgate/profiles/` (`--profile FILE`).

```toml
# ~/.config/kgate/clusters/example.toml   (invented values)
kind = "kubectl"                      # the only kind besides the built-in homelab one
kubeconfig = "~/.kube/kgate-example"  # a kubeconfig that holds only the one context below
context = "example-ctx"
namespace = "jobs"
registries = ["registry.example"]     # image hosts (or host/path prefixes, see below) a profile may use here (still pinned by digest)
tree_roots = ["Users", "Volumes", "private"]   # top-level directories the shipped tree may live under
user = "65532:65532"                  # uid:gid the pod runs as (never root); a profile's own `user` overrides it
deadline_s = 7200                     # activeDeadlineSeconds
cache_claim_default = "my-cache"      # optional: a persistent cache claim used unless the profile names its own cache_pvc
cache_cap = "8Gi"                     # optional: trim /cache/go-build and /cache/pnpm-store to this each, oldest files first (0 disables)

[pod_labels]                          # optional: what the cluster's admission policy requires on every pod
"example.org/owner" = "team-a"
[pod_annotations]                     # optional
"example.org/evict-ok" = "true"
```

A missing or invalid file is exit 69, and the reason names the file and the key (`cluster file <path> is missing the key 'namespace'`). Unknown keys are refused.

**Setup, once.** `kgate cluster-setup <name> --from-context <ctx> [--namespace NS] [--from-kubeconfig FILE] [--kubeconfig-out FILE]` writes a kubeconfig that holds only that context (mode 600). It writes to the `kubeconfig` the cluster file names when that file exists (`--kubeconfig-out` must then match it, and so must `--from-context` and `--namespace` match the file's `context` and `namespace`, or the command refuses and leaves the working kubeconfig alone); otherwise to `--kubeconfig-out`, default `~/.kube/kgate-<name>`. It marks the file as kgate's, never replaces a file it did not write (or one with more than one context), and never writes `~/.kube/config` or the file it reads from. It switches an exec login of `kubelogin` to `--login azurecli` (only when the source context uses it, so the token comes from the cli login and there is no browser sign-in per job). If no cluster file exists yet it also writes a skeleton (mode 600, values escaped) with `registries = []`, which kgate refuses until you fill it in; it never overwrites an existing cluster file.

**Where the files come from on a machine.** `run_onchange_after_45_kgate_cluster_files.sh.tmpl` writes the cluster and profile files from the machine's own chezmoi data, on any profile that has it: `kgate.clusters.<name>` and `kgate.profiles.<name>` hold the TOML text, and the file names are the keys. With no `kgate` data nothing is written. **Removing a key from the data does not remove the file the step already wrote**; delete `~/.config/kgate/clusters/<name>.toml` or `~/.config/kgate/profiles/<name>.toml` by hand (a cluster file that is gone makes kgate refuse that cluster with exit 69; a stale one keeps working). See `example.chezmoi.yaml` and [profiles.md](./profiles.md).

**Constants.** `kubectl --kubeconfig <kubeconfig> --context <context> -n <namespace>`, always all three, from the cluster file. kgate never reads the current context. The reachability check is `kubectl auth can-i create pods` answering `yes`; anything else is exit 69 with a hint to sign in and kubectl's message. A missing kubeconfig is exit 69 naming `kgate cluster-setup`.

**What kgate does there.** It needs only pods (get, list, watch, create, delete), `pods/exec`, `pods/log` and events. kgate creates a bare pod, execs into it and deletes it. No Secrets, ConfigMaps or Jobs. The sweep at each start deletes finished `app=kgate` pods only.

**Pod spec.**

- Labels `app=kgate`, `kgate-job=<id>`, plus the cluster file's `pod_labels` (which may not set kgate's own `app` or `kgate-job`), and its `pod_annotations`.
- Non-root: `runAsNonRoot`, `runAsUser` and `runAsGroup` from the profile's `user`, else the cluster file's (`0:0` is refused). seccomp `RuntimeDefault`, `allowPrivilegeEscalation: false`, drop `ALL`, no service account token. The exec-as-root-then-drop path is not used.
- Requests and limits for cpu, memory and ephemeral-storage, from the profile: `cpu` (request), `cpu_limit` (limit, what the pod may burst to; default `cpu`; must be at least `cpu`), `memory` (request), `memory_limit` (limit), `ephemeral_storage` (request and limit; default `10Gi`). `GOMAXPROCS`, `CARGO_BUILD_JOBS`, `RAYON_NUM_THREADS` and `MAKEFLAGS` follow the CPU limit, not the request.
- `activeDeadlineSeconds` from the cluster file. The container runs `sleep 86400` (no `tini` needed), so the deadline ends a pod whose client died.
- emptyDirs at the top directory of the shipped tree (`/Users` for `/Users/me/git/repo`, so the Mac's absolute paths unpack as the non-root user), at `/cache` and at `/out`. Only trees under the cluster file's `tree_roots` are accepted (an allow-list, so no emptyDir hides anything in the image); any other top directory is refused.
- `cache_pvc = "<claim>"` in the profile (or `cache_claim_default` in the cluster file) makes `/cache` that persistent claim instead of an emptyDir (see "The cache claim"). The pod then also gets `fsGroup` (the gid) with `fsGroupChangePolicy: OnRootMismatch`, so the non-root user can write a new disk.
- Env: kgate's usual set, plus `HOME=/cache/<job id>/home` (per job, removed with the job's directory at the end, so nothing a job writes to HOME, such as `~/.gitconfig` or `~/.npmrc`, reaches a later job on a shared disk), `GOCACHE=/cache/go-build`, `GOMODCACHE=/cache/gomod`, `npm_config_cache=/cache/npm` and `npm_config_store_dir=/cache/pnpm-store`. Only those caches live on the claim.
- No hostPath, affinity, tolerations, Secrets or imagePullSecrets (nodes pull with their own identity). `--node` is refused.

**Sidecar and mounts (all optional, kubectl clusters only).**

A `registries` entry is a host (`registry.example`) or a host plus a path prefix (`registry.example/team/db`). An image matches an entry when it starts with `entry + "/"`, or when its repository (the part before `@sha256:`) equals the entry. The same rule applies to job images, the sidecar image and image volumes. A host entry admits every repository on that host; a path-scoped entry admits that repository and anything under it, and refuses a sibling repository on the same host. Use a path-scoped entry to admit only the sidecar image.

- `services = ["mssql"]` with an `[mssql]` table adds a SQL Server container to the pod. It is a native sidecar (an init container with `restartPolicy: Always`) with a startup probe, so the job container starts only once the database accepts a login. The sidecar runs as uid 10001 (the image's `mssql` user) with group 0, because the image's data directory is group-owned by root, and with `drop: [ALL]` plus `add: [NET_BIND_SERVICE]` only on this container, because `sqlservr` carries that file capability and cannot be started without it. These are fixed, not profile settings. kgate generates a throwaway SA password for each job (`Aa1_` and 32 hex characters), puts it in the pod spec of both containers (`MSSQL_SA_PASSWORD`, `SA_PASSWORD`) and tells CMD where the database is (`MSSQL_HOST=localhost`, `MSSQL_PORT=1433`). The password is never written to the log, the record, the console or an error message: anything that would print it prints `***`. `[mssql]` keys: `image` (required, by digest, host in the cluster file's `registries`), `cpu` (2), `cpu_limit`, `memory` (4Gi), `memory_limit`, `ephemeral_storage` (4Gi), `ready_s` (300, how long the startup probe may take). The sidecar's requests count toward the namespace quota. If it crashes or restarts, kgate exits 69 with the last 15 lines of its log (password masked) and CMD does not run.
- `[[image_volumes]]` with `image` and `path` mounts an image read-only at `path` (a Kubernetes image volume). The image is pinned by digest and must match `registries`, the same rule as the job image. `path` must be absolute and normalized (`posixpath.normpath(path) == path`: no `.`, `..`, `//` or trailing `/`; `/./usr`, `/a/../usr` and `/usr/` are refused). It may not be `/`, `/cache`, `/out`, a tree root, or `/usr`, `/etc`, `/bin`, `/sbin`, `/lib*`, `/proc`, `/sys` or `/dev` (or anything under them).
- `local_hostnames = ["db"]` makes those names resolve to `127.0.0.1` in the pod (`hostAliases`), for a repo whose own configuration names the database by host. Plain host names only; an address is refused.
- **Running a tool from an image volume.** A volume brings only the image's files, not its environment, and absolute symlinks and paths inside it point at the job container's own root. So: call the tool by its path under the mount (`/mnt/tool/usr/share/.../tool`), link only the few binaries the job needs into `$HOME/bin` and put that first on `PATH`, and never put a mounted image's `/usr/bin` on `PATH` (its coreutils need that image's libraries and fail with `error while loading shared libraries`). For a Java tool in a FIPS image, set `FLYWAY_JAVA_CMD`-style launcher variables to the mounted JVM and give the JVM the provider jars explicitly (`JAVA_ARGS="-p /mnt/tool/usr/share/java/bouncycastle-fips"`); without that module path the JVM has no BouncyCastle FIPS provider and fails with `SHA-1 not available`. FIPS stays on. The working command for a profile belongs in that profile's comments.
- **SQL Server client notes.** `sqlcmd` from the Go-based go-sqlcmd rejects the SQL Server 2019 image's self-signed certificate (a negative serial number) even with `-C`; set `GODEBUG=x509negativeserial=1` for it. That certificate is a throwaway one on localhost inside the pod, so this is safe here. Encryption stays on and the server is unchanged. The sidecar's own startup probe uses the image's ODBC `sqlcmd`, which does not need it.
- With a sidecar the pod has two containers, so kgate sends its `exec` calls to the container named `job`. The record gains `services`, `pod_start_s`, `service_ready_s` (seconds from pod creation to the sidecar's first pass) and `service_peak_bytes` (the sidecar's own peak memory) and `service_cpu_usec` (its CPU time). The log says `SQL Server ready after Ns`, `peak mssql N cgroup` and `cpu mssql N usec`.

**Refused with exit 69, before anything is created:** a profile with `[secrets]` or a service other than `mssql`, an image whose host is not in the cluster file's `registries` (or that is not pinned by digest), a root user, an invalid cluster file. The record names the profile's cluster even for these refusals, and no homelab connection is made.

**The cache claim.** With a claim, `GOCACHE`, `GOMODCACHE` and the package-manager caches are warm after the first job. The claim is created by whoever runs the cluster, not by kgate, and mounting a claim in the pod's own namespace needs no PVC rights. A claim with access mode ReadWriteOncePod lets one pod use it:

- **One job holds the cache; a second runs cold.** A second job's pod stays `Pending` (`Unschedulable`, "node has pod using PersistentVolumeClaim with the same name and ReadWriteOncePod access mode"). If it is still Pending on that reason after about 10 s (`CACHE_BUSY_S`), kgate deletes the pod, creates the same pod again with an emptyDir `/cache` (no claim, no `fsGroup`), prints `kgate: cache in use by another job; running without it`, and the job runs cold. The record's `cache` field says which: `pvc`, `fallback`, or `none` (no claim; kubectl-cluster records only). Any other Pending reason (quota, capacity) keeps the existing waits, with the cache.
- **Zone.** A disk lives in one availability zone, so a pod that mounts the claim is scheduled in that zone; a pod that falls back to the emptyDir can go anywhere.
- **A dead client's pod.** If a client dies, its pod keeps running until the deadline and can hold the disk that long; other jobs then run cold. `kgate cancel` deletes it sooner, and so does the next job that starts on this cluster.
- **Cleanup.** The pod side removes `/cache/<job id>` (the job's own script, file list, error file and HOME) at the end of every job, pass or fail, and at its start removes any other `/cache/kgate-*` directory older than a day (a dead client's leftover).
- **Cache cap.** Before the job runs, the pod side trims `/cache/go-build` and `/cache/pnpm-store` to the cluster file's `cache_cap` each (default `8Gi`; a byte count or a quantity like `8Gi`, at most `1Pi`; a value under 1KiB such as `100m` or `500` is refused, because it would reach the pod side as 0 KiB and silently disable the trim; `0` disables the trim), deleting the oldest files first until the cache fits. The pnpm listing walks the version directories in the shell and reaches only each version directory's `files/` blobs and old `index/` JSON files (the index as it was before pnpm 11 moved it into one SQLite database); it never lists `index.db` and the `-wal` and `-shm` files SQLite writes beside it, at any version directory (pnpm 11 keeps the store's one SQLite index at `v11/index.db`, and pnpm does not touch store files on use, so an old, stable store has an old index that the trim would otherwise delete whole as one old file), nor anything under `v*/links/` (pnpm 11 keeps whole package directories there, the global virtual store: deleting single files could leave a package half-deleted that pnpm still treats as installed) nor `v*/projects/` — including a path under `links/` or `projects/` that merely contains a `files/` or `index/` part, which is why the walk is in the shell and not a `find -path` pattern (a pattern's `*` crosses `/`). The trim is at file level, because the real layouts defeat a trim of whole directories: `go-build` is 256 bucket directories (`00`..`ff`) whose directory mtimes do not move when Go rewrites the files inside, and a pnpm store holds only version directories (`v3`, `v10`, `v11`), so trimming children by their own mtime would evict `go-build` in a random order and wipe a whole store at once. Only files are removed, never a directory, so the cache, its version and bucket directories all survive. The trim is only safe because the claim is ReadWriteOncePod: one job at a time, so nothing else writes the cache while it runs; and kgate does not create the claim (whoever runs the cluster does, above). Without a cap, the caches on a persistent claim grow without bound: a shared claim can fill, and the next job then dies with exit 69, "no space left on device". A file that vanished since the listing, or that this job's user may not delete, is skipped; a failed trim is logged and the job goes on; and if the cache is still over the cap after the trim (`index.db`, `links/` and `projects/` can exceed it on their own), that is logged too. `/cache/gomod` is not trimmed: a trimmed module is downloaded again in full, so a cap there buys little and costs proxy round trips.
- **Missing claim.** The pod would stay `Pending` with `persistentvolumeclaim "<name>" not found`. kgate sees that at once and exits 69 with `the cache claim <name> does not exist in <namespace> (cache_pvc in the profile)`; the pod is deleted.

**Quota.** A shared namespace can have a ResourceQuota. A create call that the quota refuses is not fatal: kgate prints `kgate: waiting for quota: <the quota message>` (and a new line when the message changes), retries the create with backoff (5 s, doubling to 60 s) until the job's `--wait` deadline, and records the time spent as `quota_wait_s` (0 when it did not wait; on the homelab the key is there only when the quota refused the job). `--wait` counts from the job's start and `quota_wait_s` from the first refusal, so on a slow machine, without a cluster hold, `quota_wait_s` is shorter than `--wait` by the time the job spent before that refusal (start-up, the tree hash, shipping); the job still gives up no sooner than `--wait` after it started (the record's `duration_s` is from that start). At the deadline it exits 69 with `quota not available within <N>s: <message>`. Only the API server's ResourceQuota refusal is waited for: `Error from server (Forbidden): ... pods "x" is forbidden: exceeded quota: <name>, requested: ..., used: ..., limited: ...`. Any other text that merely says `exceeded quota` (an admission-webhook denial, say) is an immediate 69. The whole message is parsed; only what is printed and recorded is cut to 300 characters. If a requested amount in that message is above the quota's own limit for it (`requested` greater than `limited`), waiting can never succeed, and kgate exits 69 at once with `request exceeds the namespace quota: <message>`. Any other create error is also an immediate 69. `kgate cancel` works while a job waits for quota. **On the homelab** the wait is in the local queue ("When the cluster is full"): the job prints `kgate: queued: waiting for quota: <the quota message>`, releases the queue's lock while it sleeps (a job ordered before it, by priority or arrival, is placed meanwhile) and keeps its place in line: its ticket is marked with the name of the quota that refused it, and every job ordered after it that this quota counts waits behind it (`queued: behind <id>, which the quota refused and was first`), whatever that job asks, until it is placed, gives up at its `--wait` or its client dies (a dead client's ticket is cleared like any other). Without that, a stream of small jobs that fit would take the quota a large one waits for, and it would wait out its whole `--wait`. A quota that counts only some pods holds back only those: the `kgate-docker` quota counts only pods in the `kgate-docker` class, so a Docker job it refuses holds back later Docker jobs and no others, and a job it does not count passes it. A quota name kgate does not know (`SCOPED_QUOTAS` in the client) is treated as counting every job, as before. The order is the queue's: a later job of a higher priority class is still placed first. It holds on one machine, where the queue directory is; a kubectl cluster has no queue and is unchanged. The record's `queue_wait_s` includes the quota wait. The homelab creates a job's Secrets in the same call as its pod, ahead of it, so when the quota refuses the pod kgate deletes those Secrets before it sleeps; the next try makes them again. **A cluster hold does not count against `--wait`.** The homelab's `scripts/kgate/hold.sh` holds new jobs with a ResourceQuota named `kgate-hold` (`HOLD_QUOTA` in the client). A job that quota refuses prints `kgate: waiting for quota: exceeded quota: kgate-hold, ... (a cluster hold: not counted against --wait)` and keeps retrying; the time held is added to the job's one `--wait` deadline, the one the coordinator's pause also pushes back (the quota wait, the queue, the wait for the pod to start, the cache fallback and an eviction rerun all read it), so a hold of any length leaves the job its whole `--wait` once it lifts. A timeout after a hold names the real limit: `within 63s (--wait 3s plus 60s held by the cluster)`. On the homelab the same goes for the time a job spends queued behind a job the hold refused, and the job's ticket carries the pushed-back deadline so other clients do not clear it as stale. Any other full quota, whatever its name, still ends the job at `--wait`. The record's `quota_wait_s` is the whole wait, hold included; `hold_wait_s` is the part held by the hold, on the held job and on the jobs queued behind it (the key is there only when a hold held the job). Requests small and limits large (`cpu` small, `cpu_limit` large) let more jobs fit a quota; size a profile from its measured working set (cgroup anon, not the cgroup peak, which includes page cache).

**Eviction.** The cluster's autoscaler can take a pod away (it consolidates an underused node), and so can the taint manager or the scheduler. kgate's pods carry the eviction-ok annotation the cluster's policy requires and nothing that resists eviction. When kgate loses the pod before CMD finishes, it checks whether the cluster evicted it: the pod's status (`reason: Evicted`, or a `DisruptionTarget` condition) if the pod still exists, and the namespace events for that pod name (`Evicted`, `TaintManagerEviction` with a "Marking for deletion" message only, `Preempted`, `Disrupted`; nothing else, so the node autoscaler's `DisruptionBlocked`, `FailedScheduling` and `Nominated` give no rerun). Only a confirmed eviction is rerun, once: kgate deletes what is left of the pod, prints `kgate: pod <id> was evicted by the cluster (<reason>); rerunning once`, and starts the same tree, profile and CMD in a new pod `<id>-r2` of the same job (the quota wait and the cache fallback work as before; the job's `/out` is the second pod's). The record gains `attempts` and `evicted` (a list of `attempt`, `pod`, `reason`). A second eviction is exit 69 naming both reasons. The clocks are not reset: kgate reruns only while the job's `--wait` has not passed, and the new pod's `activeDeadlineSeconds` is what is left of the cluster file's `deadline_s` since the first pod was created (no time left: exit 69, not rerun). The pod's own status comes first: a pod that still exists, is Running or Pending, is not being deleted and has no true `DisruptionTarget` was not evicted, and its events are not read. The taint manager also emits `TaintManagerEviction` for "Cancelling deletion of Pod ..." (the taint cleared and the pod was not deleted), so that message is no eviction. Any other lost pod keeps exit 69 and its text, `the result is unknown and the job is not rerun`, because CMD may have had effects; so does an eviction before the pod is running. The deadline covers the whole job on purpose, so a job whose `--wait` has passed when its pod is evicted gets no rerun. The record's `cache` is the cache mode of the pod that ended the job. The homelab is unchanged.

**Pod side, no Python.** The image need not have `python3`, so the pod runs `sh /cache/<id>/kgate.sh` (the `POD_SH` constant in the script) instead of `kgate.py --pod`. It prints the same `kgate[<id>]: start|hash|preflight|running|peak|end` markers, so the Mac side reads them unchanged.

- Repo and hash: no `.git` is shipped. The script makes a fresh repo at the tree root, adds exactly the shipped file list (`files.nul`) to its index hashed as bytes (`core.autocrlf=false`, `safe.directory=*`, and an `info/attributes` that turns text, eol, filter, ident and working-tree-encoding conversion off), and compares `git write-tree` with the Mac's hash. Only on a match it makes one commit (author and committer `kgate`, date 2000-01-01, so the same tree gives the same commit) on `main`. Tools then find a working `HEAD` (`git rev-parse`, VCS stamping in builds). The Mac's real HEAD is in `KGATE_HEAD` in CMD's env and in the record's `head`. If git cannot commit, the pod prints `commit FAILED git commit failed: ...` and exits 69, and kgate fails the job with that reason, CMD not run.
- If the image lacks `git` or `tar`, the pod side stops first with `image FAILED image lacks <tool>; kgate's pod side needs git, tar and sh`; kgate exits 69 with `image lacks <tool>; ... (CMD not run)`, not a hash mismatch.
- If the image lacks `git` or `tar`, the exec checks for them first and prints `image FAILED image lacks <tool>; kgate's pod side needs git, tar and sh` (exit 69); if the container cannot start `sh` at all, kgate reads the runtime's message and gives the same reason for `sh`. kgate exits 69 with `image lacks <tool>; ... (CMD not run)`, never a hash mismatch or a lost-pod error.
- Tools: as the Python side. The expected version must appear in the command's output as a whole version. A tool whose version flag differs needs `cmd` (for example `go version`, since `go --version` is not a flag).
- CMD runs in the same directory. Peak memory is read from `memory.peak` (`unknown` when the kernel has none). The end line carries CMD's exit code.
- Exit codes inside the pod: CMD's, 70 for a hash mismatch, 71 for a tool mismatch, 69 for a missing tool or a failed commit. The Mac side checks that kubectl's exit code equals the reported one.
- Only POSIX features are used, so a busybox userland works.

**What differs from the homelab.**

| | homelab | second cluster |
|---|---|---|
| Reach | `ssh` + `kubectl` on a control plane | local `kubectl` + the cluster file's kubeconfig, context and namespace |
| Secrets, pull credential | `[secrets]` as a pod Secret; ghcr pull Secret | none; `[secrets]` refused |
| Pod user | root to unpack, then `user` | non-root `user` throughout |
| Pod side | `kgate.py --pod` (python3) | `kgate.sh` (POSIX sh, git) |
| Tree location | the pod's filesystem | emptyDir at the tree's top directory |
| Git history | `.git` and the shared git folder shipped | none shipped; one synthetic commit built in the pod |
| Caches | hostPath | emptyDir `/cache` (cold each job), or a claim (warm; one job holds it, a second runs cold) |
| Deadline | 4 h (`MAX_RUN_S`; the longest job on record ran 3 h 3 min) | the cluster file's `deadline_s` |
| Scheduling | node affinity | the cluster's |
| Cleanup | pod and two Secrets | pod only |
| Image needs | `tini`, `python3` 3.11+ | `sh`, `tar`, `git` |

On a kubectl cluster the history is a single synthetic commit, and the Mac's uncommitted and untracked shipped files are in it, so `git status` and `git diff` in the pod show a clean tree (use the Mac's `git status` to see what changed). `git log`, `git describe`, `git blame` and tags show nothing of the real history. A command that needs history must run locally or on the homelab (which still ships `.git`). Exit codes are the same (CMD's code, 64, 69). When the cluster is unreachable or the sign-in has lapsed, the job exits 69 with the sign-in hint; kgate never falls back to the Mac.

**Costs on the Mac.** kgate ships every tracked file on every job and builds that tar in memory, so a very large repo costs the client memory (about the size of the tar) and a minute or more to the pod-side start. A warm pod with diff sync, or shipping only what a package needs, is the next improvement.

- **Tools.** The pod runs the command and the expected version must appear in its output as a whole version (`1.98.0` does not match `11.98.0` or `1.98.01`). Any tool with a version command fits without changing kgate: `cargo`, `rustc`, `helm`, `kustomize`, `ansible-lint`, `python3`.
- **Secrets.** Read with `op read` on this Mac at run time into a temporary pod Secret and passed as environment variables. Never in the image, a profile value or the log. `op` runs only with the 1Password service-account token (`OP_SERVICE_ACCOUNT_TOKEN`, else `~/.config/agent-harness/op-service-token`); with neither, the job exits 69 before `op` runs, so it never reaches the desktop app. With the op shim first on PATH and a Connect token (`~/.config/agent-harness/op-connect-token`), that `op read` goes to the homelab 1Password Connect server first and falls back to the service account (see the shim header in `dot_pi/private_agent/bin/executable_op`). If `op read` fails the job exits 69.
- **Secret cache.** Each reference is read with `op` at most once in 24 hours on a host (2026-11-13: 637 jobs in a day used up the service account's 1000 daily reads). The value is kept in `${XDG_CACHE_HOME:-~/.cache}/kgate/`, one file per reference named by the SHA-256 of the reference, files mode 0600 in a 0700 directory, written through a temp file and a rename. A job finds a file under 24 hours old (by its modification time) and uses it without running `op`, and without needing the token. An older or missing file means `op read`, then a new file. A failed read writes nothing. Jobs that start together take turns on `.lock` in that directory, so only the first reads. If the directory cannot be used, `op` is read for every job as before. To force a fresh read, delete the file (or the directory).
- **User.** The pod's exec starts as root to unpack. kgate then gives the shipped tree, `/out`, a home and the caches (`/cache/u<uid>`: npm and Cargo, with `CARGO_HOME=/cache/u<uid>/cargo`, because the image's own `/usr/local/cargo` is root-owned) to `user` and runs the version checks and CMD as it, as on a developer's Mac. (As root, `chmod 000` tests pass that a user fails.)
- **Services.** If the gate needs something the image cannot provide (Docker, a database), list it. The homelab offers `docker` (opt-in, see "Docker jobs") and refuses any other service with 69; that gate is not a kgate gate. A kubectl cluster offers `mssql` (see "Sidecar and mounts") and no `docker`.
- **Image pull.** The image registry `ghcr.io` is private; kgate reads the 1Password item `kgate-github-packages-read` for each job's temporary pull Secret (expires about 2026-12-02; see the homelab `docs/kgate.md`).
- The image needs `tini` (the pod's first process) and `python3` (3.11 or later): the same script runs in the pod to verify the hash and check versions. The version commands run in the job's directory, so per-directory tools (rustup with a `rust-toolchain.toml`) report what CMD will use. `git` is needed when the gate itself uses it.

## GitHub CI is the receipt

Playbook 83fbe006: do not run a suite on kgate when GitHub CI already ran it green on the same commit. A profile with a `[github_ci]` table (`workflow`, a workflow file name such as `ci.yml`; `suites`, a list of strings) makes kgate check first. It refuses with exit 69 (`GitHub CI already ran this suite green on <sha12> (<run url>): GitHub's run is the receipt`) when all of these hold: one of `suites` appears in the shell-quoted CMD; the worktree is clean (`git status --porcelain` is empty, untracked files that are not ignored count); and `gh run list --workflow <workflow> --commit <HEAD>`, run in the worktree, shows a completed, successful run on exactly `HEAD` whose event is `push` or `workflow_dispatch` (a `pull_request` run tests the merge commit, not `HEAD`, so it never counts). The check runs after the profile is read and before any cluster call. If `gh` is missing, not signed in, takes over 15 s or fails, kgate prints one `kgate:` note with the first line of its error and runs the job as before. A profile with no `[github_ci]` table, or a table of the wrong shape (a profile error, exit 69), is unchanged or refused like any other bad key. To run the suite anyway, change something in the tree or use a CMD the suites do not name. The dotfiles `kgate.toml` lists `tests/heavy-gate`, `tests/workstream-rank` and `scripts/ci-linux.sh`.

## Pod environment

Every pod starts CMD with these variables set, so no repo has to remember them (stack audit candidates 3, 5 and 8, workstream coordinator-test-speed):

| Variable | Value | Why |
|---|---|---|
| `NODE_COMPILE_CACHE` | `/var/tmp/kgate-node-cache` | Every Node process in the job shares one compile cache; only the first start pays. The cache is keyed on file content, so it cannot go stale. |
| `PYTHONPYCACHEPREFIX` | `/var/tmp/kgate-pycache` | The same for Python bytecode, written outside the checkout (so a test run leaves the tree clean). |
| `KGATE_CPUS` | the pod's CPUs | The number `CARGO_BUILD_JOBS`, `RAYON_NUM_THREADS` and `MAKEFLAGS` already use: the CPU request on the homelab, the CPU limit on a kubectl cluster. A pod sees the node's CPUs, not its own, so a tool that reads the machine oversizes its pool. |
| `VITEST_MAX_WORKERS`, `CI_PAR_JOBS` | `KGATE_CPUS` times the profile's `workers_per_cpu` (default 1) | Worker pools sized from the pod. Raise `workers_per_cpu` only where a measured run shows it pays. |
| `TMPDIR` | `/kgate-scratch` | Only with `scratch_tmpfs` (below). |

A profile secret with one of these names wins (kgate leaves that variable out). A CMD that sets one itself wins too, since CMD starts after the pod's environment is in place: `kgate -- sh -c 'VITEST_MAX_WORKERS=2 npm test'`. The compile caches live in `/var/tmp` on the pod's disk on purpose: they are large and should not take memory, and `/var/tmp` is not `/tmp`, which `tmp_tmpfs` (below) can put in memory.

**`scratch_tmpfs = "256Mi"`.** kgate mounts a memory-backed folder (`emptyDir` with `medium: Memory` and that `sizeLimit`) at `/kgate-scratch` and sets `TMPDIR` to it. A suite that makes and removes many small files and folders runs faster there than on the pod's overlay disk. No key, no mount and no `TMPDIR`. **The size counts toward the pod's memory limit:** the files sit in memory the container's cgroup is charged for, so a full folder uses `memory_limit` that the job's own processes then do not have. Size the profile's `memory` and `memory_limit` to include it (job peak plus the scratch you expect to use; kgate refuses a `scratch_tmpfs` that is not smaller than `memory_limit`). Too much scratch fails the job as out of memory, not silently. A write past the folder's size fails with "no space left on device"; size the key from one measured run, the way memory is sized. Tests about real disk behaviour (sync, renames across file systems) should name a disk path themselves.

**`tmp_tmpfs = "2Gi"`.** The same memory-backed folder, mounted at `/tmp` itself and with no `TMPDIR` set, for a suite that names `/tmp` in its code (a literal path, not `$TMPDIR`) and so ignores `scratch_tmpfs`. A suite that makes SQLite files commits each write with an `fsync`, and on a pod's disk that waits on the node's filesystem journal (`jbd2_log_wait_commit`); in memory the wait is gone. The compile caches are in `/var/tmp` for this reason: they stay on disk. The size counts toward the memory limit the same as `scratch_tmpfs`, and the two keys together must stay below `memory_limit` (kgate refuses a profile where they do not). A write past the size fails with "no space left on device"; size it from one measured run, the peak `/tmp` use plus margin. Everything a job writes under `/tmp` is in memory and is gone with the pod, and the shipped tree is not affected: on the homelab it lands at the worktree's own path, so a worktree itself under `/tmp` would be in the mount. It works the same on the homelab and on a kubectl cluster.

## Cached npm install

`npm ci` spends its time deleting and rebuilding `node_modules`, not downloading, and every pod starts with none. A profile with

```toml
[install]
npm = true
```

makes the pod put a small `npm` first on the job's `PATH` (`INSTALL_SH` in the kgate file; the homelab pod side writes it, a kubectl cluster's job ships it). Callers keep typing the same command: `sh -c 'npm ci && npm run typecheck && npm test'` stays the command, and its `npm ci` is served from the node cache. kgate refuses nothing and rewrites nothing.

- **What it intercepts.** `npm ci` (also `clean-install`, `ic`, `install-clean`) typed by the command itself, run in a folder inside the shipped tree that has both `package.json` and `package-lock.json`. Every other npm command, `npm ci` in a fixture folder outside the tree or without a lock file, and everything the real npm starts (lifecycle scripts, tests that run `npm ci`), meets the real npm: the wrapper takes its own folder out of `PATH` before it calls it.
- **Key and layout.** `/cache/u<uid>/nm/<repo>/<key>.tar`, one folder per repo (the repo's name as in the record's `repo`, so every clone of it shares one). `key` is the first 16 hex characters of the sha256 of `package.json`, `package-lock.json`, `.npmrc`, the node and npm versions and the arguments after `ci`, so a changed lock, another node or `--omit=dev` is a different key. The tar is not compressed (packing and unpacking are most of what a hit costs) and ends with a marker file, so a cut file is never trusted.
- **Hit, miss, damage.** A hit deletes `node_modules` and unpacks the tar, and sets the file's time to now. A miss runs `npm ci --prefer-offline --no-audit --no-fund` (the caller's own arguments after it), then writes the tar under a temporary name and renames it into place, so a pod reading the folder sees a whole file or none; a pod that finds the file there when its install ends does not write one. A tar that does not unpack is removed and the pod does a real install. A failed `npm ci` fails the command with npm's exit code and keeps nothing.
- **Disk.** The 2 newest keys of each repo stay (about 560 MB per key for the coordinator). Each `nm/<repo>` folder is an entry of the node cache's least-recently-used trim (see "The node cache"), so one repo's installs never push out another's together.
- **kubectl clusters.** The step works where `/cache` outlives the pod: the profile needs `cache_pvc`, and the folder is `/cache/nm/<repo>` on the claim. Without a claim kgate prints a note and `npm ci` runs as typed.
- **pip is not covered, and `[install] pip` is refused.** A Python gate's `pip` is usually a venv's own (`/tmp/v/bin/pip`), which a `PATH` wrapper never sees, and setting `PIP_CACHE_DIR` and `UV_CACHE_DIR` per repo gains nothing: pods already keep pip's cache in `HOME` on the node. Measured 2026-11-19 on amazon-itemizer's real command (`python3 -m venv /tmp/v && /tmp/v/bin/pip install -q -e . pytest pytest-xdist pyotp playwright`), two jobs on the same node: as it is today 15.1 s then 14.7 s; with a fresh per-repo `PIP_CACHE_DIR` cold 16.6 s then warm 19.3 s (ledger decision #4361). A mechanism with a measured gain (a kept venv, for example) is a later change.
- **A package that writes the checkout's path into `node_modules` at install time** would break in another checkout of the same repo. Check a new repo for it once. What a test stops proving: that a clean install works on every run; a miss still does one, and any lock change is a miss.
- **Proof of the record.** `install` and `install_s` in `log.jsonl`: `miss` then `hit` on the same node, `hit` well under 10 s for a repo whose install takes 20 to 60 s.

## Memory: request and limit

- `memory` is the pod's **request**: what the scheduler reserves on a node to place it. It decides where a job fits.
- `memory_limit` is the pod's **limit**: the line at which the pod is OOM-killed. It is optional. When set, it must be at least `memory`, and it takes the same format (`Gi` or `Mi`). Without it the limit equals the request, which is how every profile ran before this key existed.
- A pod whose request is below its limit is Burstable. Under node memory pressure Kubernetes evicts pods that use more than their request first. Above the limit the pod is killed whatever the node has free.
- Sizing rule for a profile: set `memory` (the request) to 1.2 times the highest measured peak, rounded up to 0.5 GiB, with a floor of 0.5 GiB. Keep `memory_limit` as the OOM guard: sizing the request does not raise or lower the limit. The peak kgate records (`peak_bytes`) is the container's cgroup peak, and it includes page cache. The kernel can reclaim page cache, so the peak overstates what the job needs; read it as an upper bound.
- Overrides: `--mem` sets the request. `--mem-limit` sets the limit. A `--mem` above the profile's `memory_limit` is refused unless `--mem-limit` is given too.

## Ephemeral storage and eviction

A homelab pod's writable layer (the unpacked worktree, `node_modules`, build output) and its `/out` count as the node's ephemeral storage. The `/cache` mount is a host path and does not. Until dotfiles#484 a homelab pod asked for none. The scheduler could then not keep it off a node short on disk, and under disk pressure the kubelet evicts the pods that use more than they asked for, first (2026-11-16: coordinator #802's unit gate, evicted from agent-4 after 12 minutes of passing tests with 1.15 GiB used).

- `ephemeral_storage` is the request. The default is `4Gi` (`EPHEMERAL_DEFAULT`); a profile may set another. `ephemeral_storage_limit` is the limit: a pod that writes past it is evicted by the kubelet, so a gate that fills the disk is the one that goes, not its neighbours. The default is `12Gi` (`EPHEMERAL_LIMIT_DEFAULT`), or the request when a profile raises only the request past that (a limit below the request is refused by the API); a profile that sets `ephemeral_storage_limit` wins (homelab only; at least the request). A kubectl cluster keeps its own rule: the request is also the limit, default `10Gi`.
- Sizing, request: per-pod use read from each node's kubelet stats (`/api/v1/nodes/<node>/proxy/stats/summary`) on 2026-11-16 across 14 live pods on all five schedulable nodes: coordinator unit gate 0.87 to 1.29 GiB, coordinator journeys 0.91 to 1.18 GiB, storycraft Go gate 1.92 GiB (still growing when read), lean-change `npm ci` jobs 0.1 to 0.2 GiB. Nothing else is recorded (the record has no disk figure). The first default, `3Gi`, was about 1.5 times the highest of those readings. A second read the same day (a sampler took each pod's peak every 30 s, 17 pods) found a Rust workspace gate (loop-engine `cargo build --workspace --all-targets` plus mutation runs, default request) at 5.6 GiB and still growing, an agent-kit gate at 1.85, and the storycraft Python environment build at 4.4 (it sets its own 25Gi). The request is now `4Gi`: it is above every typical gate (0.9 to 1.9 GiB), where the kubelet evicts last. A gate that writes more (a Rust or Go build, a big Python environment) sets `ephemeral_storage` in its profile; a pod above its request is the first the kubelet evicts under pressure. A node's allocatable ephemeral storage is 53 to 906 GiB, so the request does not limit how many jobs fit.
- Sizing, limit: `12Gi` is 9 times the coordinator gate's peak and 2.2 times the largest default-profile peak read (5.6 GiB, a Rust gate), and below the 15 GiB or so that agent-2 (and agent-3 when it was measured, before kgate left it) have above the kubelet's eviction line, so one runaway pod cannot take a whole node. Before this default a pod had no limit: on 2026-11-16 about 13:37Z agent-4 ran short of disk, the kubelet evicted many other pods (not kgate's) and a kgate gate. A gate that needs more sets `ephemeral_storage` or `ephemeral_storage_limit`.
- No cap on the number of kgate pods per node, and none overall (the queue above waits on the scheduler's own "Insufficient" answer, not on a count). The scheduler counts a node's allocatable ephemeral storage, not its free disk, and the CPU requests already bound pods per node first (a 4-CPU gate: 2 on agent-2, 4 on agent-1 and agent-4; agent-3 takes none). A pod-count number would be a guess (design principle 9); the limit bounds each pod's worst case and the node cache is capped separately.
- Eviction: when the node evicts the pod (status phase `Failed`, reason `Evicted`), kgate reads the status before it deletes the pod. On the 2026-11-16 live run the evicted pod stayed `Running` for a moment after its container was killed, then showed a deletion time, then was `NotFound`, all within about a second; the kubelet's `Evicted` event for it (`Pod ephemeral local storage usage exceeds the total limit of containers 512Mi.`) was there throughout and outlives the pod. So the event is the fallback and counts whatever the pod looks like (only the kubelet gives that reason on the homelab, and a pod name is never reused). kgate prints `kgate: evicted: <the kubelet's message>; exit 69, CMD was not run on this Mac` and records `reason` as `evicted: <the kubelet's message>`. This applies to a pod evicted before CMD ran and to one lost while CMD ran. The exit is still 69, because the result is unknown (CMD may have had effects), and the job is not rerun. A kubectl cluster's rerun after an eviction ("Eviction" above) is unchanged.

## The node cache

Every homelab pod mounts `/var/lib/kgate/cache` on its node (a host path) at `/cache`. That folder is where a job's `HOME` is (`/cache/u1000/home`: go build and module caches, pip, pnpm, playwright, each gate's own scratch folders), its npm and cargo caches (`/cache/u1000/npm`, `/cache/u1000/cargo`) and two older root-owned ones (`/cache/npm`, `/cache/cargo-registry`). Only the jobs write it: the client's pod side creates the user folders (`prepare_user`) and CMD fills them. Nothing emptied it. On 2026-11-16 it held 7.1 GiB on agent-4 (the largest parts: go build cache 1.7 GiB, go packages 1.5 GiB, playwright 0.7 GiB, pnpm 0.44 GiB, npm 0.44 GiB) and 8.0 GiB on agent-3 (kgate no longer runs there, so that folder stops growing), and agent-4 had about 3 GiB above the kubelet's disk-pressure line (coordinator decision #2755). It holds no container images: the kubelet keeps those under `/var/lib/containerd` (55 GiB on agent-4), so a trim cannot bring back the image re-pulls that dotfiles#390 stopped.

- **The cap is 8 GiB** (`CACHE_CAP`), the disk the cache may use when a job starts. It was 4 GiB, which is below what the hot gates keep warm. Agent-4's cache at 15:51Z on 2026-11-16 was 7.93 GiB, all uid 1000: Go build cache 3.9 GiB, Go modules 2.1, pnpm 0.44, pip 0.28, npm 0.20, per-gate scratch folders under `HOME` (about 0.28 GiB each, they are trimmed like any entry) and small ones. A 4 GiB trim of that data removes Go modules, pnpm and pip, and the next Go job downloads the modules again. Agent-4 had 27 GB free and its pods are capped at 12Gi. `KGATE_CACHE_CAP` (bytes) in the client's environment overrides it, for a live proof of the trim.
- **The job enforces it, at its own start, on an idle node.** Every job holds a shared lock on `/cache/.kgate-use` for as long as it runs. A job that starts first tries to take that lock exclusively. That works only when no other job is running on the node, so a running job's caches are never removed. If it works and the cache is over the cap, the pod side removes the least recently used entries, oldest first, until the cache is within the cap, prints `kgate: cache over <cap> MiB: removed the <n> least recently used entries (<m> MiB)` and then takes the shared lock and runs CMD. Jobs that start meanwhile wait for the trim. A job does not trim when it ends: the lock is let go when its process exits, after the `end` line, and nothing runs after that line (a trim there ran inside the 10 s the client gives the exec stream to close, was cut off, and the client then blamed CMD for a process it had not left, dotfiles#493). A node that is never idle is not trimmed (the large nodes: the G14 has 906 GiB). There is no new cluster object and no timer.
- **An entry is trimmed whole.** Entries are the children of `/cache`, of each `u<uid>` folder, of its `home`, of its `home/.cache` and of its `nm` (the cached npm install, one folder per repo); anything else under those is part of its entry. "Used" is the newest of mtime, atime and ctime in the entry. An entry is renamed into `/cache/.kgate-trash` and then deleted, so a trim that is cut short never leaves half an entry, and the next trim empties the trash.
- A trim that fails is printed (`kgate: cache not trimmed: ...`) and CMD still runs. A kubectl cluster has no node cache (its `/cache` is an emptyDir or a claim) and is unchanged.

## Switching a gate: the parity run

A gate moves to kgate one at a time, each with its profile in its own repo:

1. Write the profile. Take the image digest from the homelab image build and the tool versions from `/usr/local/share/kgate/versions.txt` in the image.
2. Run the gate on the Mac and through `kgate` on the same commit. Results must match: same pass or fail, same counts. Record both in the PR.
3. Only with Michael's approval does the gate's script switch to `kgate`.
4. When the image or a tool version changes, change the pin and the profile and repeat the parity run.

## Profiles

The `kgate` binary lands on both desktop profiles. The homelab host file (`~/.config/kgate/host`) is personal only, so a work machine has no homelab address. The second-cluster files (`~/.config/kgate/clusters/`, `~/.config/kgate/profiles/`) come from a machine's own chezmoi data on any profile that has it, so a machine without that data cannot reach a second cluster.
