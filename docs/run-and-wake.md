# run-and-wake

`run-and-wake` runs a command detached and, when it exits, wakes the Pi session or T3 Code thread that started it with one tagged prompt or message. A worker can start a long or gated job and end its turn; a T3 builder waits for it with `run-and-wake --wait <job>` instead (see the builder-seat bullet below). Nobody polls, and a message that would say nothing new is not sent (see "Wakes that say nothing new").

```sh
run-and-wake -- heavy-gate --wait 7200 -- npm test
run-and-wake -- sh -c 'make build && make proof'
run-and-wake --wait <job>     # block until that job ends and print its result; its own message is then not sent
```

It returns at once and prints the job id, the job's pid, its output file and the log path, unless nothing could wake the caller (below). When the job exits, the pane that started it gets one line like:

```
[run-and-wake k:20261030T013613Z-86e5e7] job finished: exit 7 after 47m03s: heavy-gate --wait 7200 -- npm test. Output: ~/.local/state/run-and-wake/jobs/20261030T013613Z-86e5e7.log
```

Source: `dot_local/bin/executable_run-and-wake` (Python 3, standard library only), installed as `~/.local/bin/run-and-wake`. heavy-gate is unchanged; the two compose through argv.

## Contract

- **Detached.** A watcher process in its own session (`fork` plus `setsid`) starts the job and waits for it. Ending the launching tool call, which kills that call's process group, ends neither, even if it happens before the watcher reports the pid to the launcher. The job's stdout and stderr go to `jobs/<id>.log`; a watcher crash prints its traceback there too.
- **Its own systemd scope (Linux).** `setsid` leaves the caller's process group but not its cgroup. T3 runs each Claude session in a user scope (`t3code-claude-<id>.scope`) and stops it when it releases the session, which kills every process in it: a job started with plain `setsid` died with no `end` record and no wake (durable-leads kgate job `20261112T082346Z-841136`). On Linux with a working `systemd-run --user`, the launcher therefore re-runs itself as `systemd-run --user --scope --quiet --collect --expand-environment=no --property=OOMPolicy=continue <placement> --unit=run-and-wake-<job> -- run-and-wake --scoped <job> …` (`<placement>` is under Resources) (an exec in place: same environment, cwd and stdio, no new process to wait on). The watcher and the job live in `run-and-wake-<job>.scope`, which only they own; the `start` record names it (`scope`) and the launcher prints it. It runs a probe first (the same options with `-- true`, as T3 does), because an exec cannot fall back: where the probe fails (`--expand-environment` needs systemd 254), or there is no `systemd-run` (macOS, the work Mac), the launcher takes the old path unchanged. `--expand-environment=no` is there because systemd-run expands `$VAR` in the command's arguments, and only since systemd 258 not in `--scope` mode: with it, a `$` reaches the job as typed on every version. `OOMPolicy=continue` means a kernel OOM kill takes the job (the `end` record then says `SIGKILL`), not the watcher that must record it. `--scoped` is internal.
- **A stop that signals the watcher too.** The watcher forwards SIGTERM, SIGHUP and SIGINT to the job and keeps waiting, so stopping the job's own scope (`systemctl --user stop run-and-wake-<job>.scope`) or signalling its whole group still ends in an `end` record with the job's signal and a wake, not silence. A signal the watcher was started ignoring stays ignored and the job inherits it, as before (`nohup run-and-wake …` still keeps SIGHUP off the job). When the whole scope is stopped, the job gets SIGTERM twice (from systemd and from the watcher); the second changes nothing for a job that exits on the first. Nothing in the setup stops a job's scope in practice: T3's stops match `t3code-*.scope` only (see Resources); what does is `systemctl --user stop` by hand and the user manager at logout or shutdown. Then the wake must be sent before the scope's stop timeout (systemd's default, 90 s) or SIGKILL takes the watcher; a send takes milliseconds, a wake held back by a blocked pane may not make it, and the stop timeout is left at the default.
- **The builder seat will not stop while the job runs.** The `start` record's `thread` is what the builder seat's Stop hook matches against `T3CODE_THREAD_ID`; a builder that ends its turn with a job of its own still running is told to wait for it first (agent-harness README, "Builder Stop hook"). For a T3 thread the start line says how: `run-and-wake --wait <job>` in Bash with run_in_background, then `t3_background_wait`, the same command the hook names (`--wait` is below). A job that has ended no longer blocks.
- **The job knows its id.** The job's environment has `RUN_AND_WAKE_JOB=<job id>`, so a tool it runs (kgate) can key its own record by the same id.
- **The job can read 1Password with the service account.** When this process has no `OP_SERVICE_ACCOUNT_TOKEN`, the job gets the token from `~/.config/agent-harness/op-service-token` in its environment. The token is never in argv, the log, the job record or the job's output; the `start` record says only where it came from (`op_token`: `env`, `file` or null). Without a token the job runs without one, so `op` cannot reach the desktop app in a job (playbook 78819cbd).
- **Any exit wakes.** Exit 0, a failure, heavy-gate's 75 (gave up waiting) and 76 (refused for disk: a watched volume under the floor, or `/Volumes/Workshop` not mounted), a signal (`killed by SIGTERM`) and a command that could not start (exit 127) all wake.
- **Starting session, best effort.** At launch it captures `HERDR_PANE_ID` and `PI_SESSION_FILE` (Pi sets both on every bash call). At exit it asks `herdr agent get <pane>` and sends only if, at check time, that pane shows the same session file. Compaction keeps the session file, so it still wakes; a `/new` or a resume before the check does not.
- **The check/send window (accepted by Michael, ask #347, 2026-10-29).** herdr's prompt targets a pane, not a session, so the check and the send are two calls milliseconds apart. A `/new` in that window can put the message in the new session. This is not prevented. The pane's session is read again right after the send, and the `wake` record carries `session_after` when it differs.
- **T3 Code thread.** A worker started as a T3 thread has no Herdr pane. If `T3CODE_THREAD_ID` is set and there is no pane with a Pi session, the wake is one `t3 thread send <thread> -` with the same one-line text on stdin (CLI: `$T3CODE_CLI_PATH`, else `~/.t3/bin/t3`; the same form the coordinator's deliverer uses). A busy thread takes it as its next turn; an idle one starts a turn. The launcher says "T3 thread X gets one message". A send that finds no T3 server (T3 is restarting) is retried every 5 s for up to 10 minutes and still delivers one message (`RUN_AND_WAKE_T3_RETRY=<interval>:<window>` tunes it, in seconds; a value that is not two numbers falls back to `5:600` with a warning on stderr; if T3 stays down past the window, the watcher records a failed wake and stops, and nothing reaches the thread until `run-and-wake --recover` runs, because no timer retries it: run by hand in the same boot it sends the result marked "delivered late"; after a restart, the login run sends the did-not-finish text below); a job that was stopped (a signal reached the watcher, as at a shutdown) gets one attempt and no wait, because a watcher still retrying would hold the shutdown for the scope's stop timeout, and `--recover` owes the wake; a send the server answers and refuses (thread not found) is logged and not retried, and a missing CLI is a failed wake. If both a pane with its Pi session and a thread id are set, the pane wins: Pi sets `HERDR_PANE_ID` and `PI_SESSION_FILE` on every bash call, so that pair names the real caller, while `T3CODE_THREAD_ID` can be inherited from the app that launched the shell.
- **At most one delivered wake per job.** One `herdr agent prompt`, or one `t3 thread send` that gets through (tries that found no T3 server do not count: nothing was delivered). A refused or failed prompt is logged and not retried. A watcher killed between the send and its `wake` record can make `--recover` send a second copy: an accepted duplicate.
- **Blocked pane.** If the pane shows a dialog, it waits with `herdr agent wait` until herdr reports another state, re-checks the session, then sends. A failed wait ends the wake as `pane-gone` or `herdr-error`.
- **Busy pane.** Herdr submits the text; Pi takes it as a queued message after the current tool call.
- **No wake target: the launcher waits.** With no `T3CODE_THREAD_ID` and no Herdr pane with a Pi session (a plain terminal, Codex, Claude Code outside T3, or a Pi child that T3 runs), nothing could ever be woken, so a detached job would only lose its result. The launcher starts the job as usual (its own session, scope, output file and `end` record), then waits for it exactly as `run-and-wake --wait <job>` does: it prints the line the wake would carry and exits with the job's status (`128+n` for a signal). Before it waits it prints a WARN with the job id and the exact `run-and-wake --wait <job>` command: the job runs in the watcher's own session, so if the caller is cut off (a tool timeout kills the launcher's process group), the job keeps running and that command gets its result. The watcher still logs `skip` `no-pane` or `no-session`, and the launcher a `read` record.
- **Every skip is logged with its reason:**

| Reason | When |
|---|---|
| `no-pane` | No `HERDR_PANE_ID` at launch (a plain terminal) and no T3 thread. With no wake target the launcher does not return at once: it waits (below). |
| `no-session` | No `PI_SESSION_FILE` at launch (not started from Pi) and no T3 thread. The launcher waits too. |
| `pane-gone` | herdr no longer has an agent in that pane. |
| `session-changed` | The pane shows a different session; `detail` names it. |
| `herdr-error` | Any other herdr error; `detail` has its code and message. |
| `waited` | A `run-and-wake --wait` is blocked on the job or already printed its result. |
| `cancelled` | The session stopped the job with `kgate cancel`. |

- **A host restart.** Nothing survives a reboot: every job is killed and the T3 server stops in the same shutdown. The user manager stops each job's scope with SIGTERM, the watcher forwards it and records `end` (with `stopped: ["SIGTERM"]`), and its one wake then finds no T3 server; on the 2026-11-15 reboots every such wake failed, and when the shutdown outran a watcher there was no `end` or `wake` at all. So the job is gone and cannot be saved, but the wake can be delivered: `run-and-wake --recover`, run by `run-and-wake-recover.service` at login (after `t3code.service`), reads the log and, for every T3-thread job that started in an earlier boot (`start.boot` differs from this boot) and has no delivered wake, writes the missing `end` (`error: "host-restarted"`, `recovered: true`) and sends:

```
[run-and-wake k:<job>] job did NOT finish: the host restarted at <this boot's time, UTC> and the job was killed. Rerun it; this is not a result. Started <ts>: <cmd>. Partial output: <file>. Its last record, an end at <ts> (killed by SIGTERM), is not a result either.
```

  Every earlier-boot job gets this text, whatever its `end` says: on 2026-11-15 at 21:02:33-34Z four wrapper shells (`bash -c "...; echo exit $?"`) have an `end` of exit 0 within a second of the SIGTERM ends, because the job inside died first. The rare job that really finished before the restart and whose wake never got through is told the same, with its end quoted; a needless rerun is the cheaper mistake. A job from the current boot whose wake stayed unreachable past the retry window gets its normal result text plus "(delivered late: T3 was not reachable when the job ended.)". Recovery waits for T3 like the watcher does, once for the whole run; if T3 never answers it exits 1 and the next run (the next login, or by hand) tries again. It skips a job with a `sent` wake, a `skip`, or a refused send, so running it twice sends nothing twice (a lock keeps two runs apart). Jobs logged before the `boot` field existed and pane/Pi-session jobs (the pane died with the host) are never replayed.

- **A watcher that is gone: the sweep.** Not every loss is a host restart. The agent host pod (no systemd, so no `run-and-wake-recover.service`) restarts its t3 container on its own: the lease fence, a move to another node and back, a new image. When pid 1 of a container exits, the kernel kills every process in it, setsid sessions and the watcher included, and the node's boot id does not change, so `--recover` (which keys on the boot id) never saw the job. Job `20261122T153308Z-5950c9` (`agent_kit_bump.py 0.69.0`, 15:33Z) was lost this way when the container started again at 15:47:58Z (`~/.local/state/agent-host/start.log`; its job output last changed at 15:43Z): `start`, no `end`, no wake, and the lead that started it waited 2.5 hours. Of the 1,016 jobs started on this node boot, 26 were left in that state (a start with no end, no wake, process gone), and each is followed by a container start in `start.log` (14 by the one at 10:56:39Z, 4 by 15:48:09Z, 3 by 16:03:24Z, 5 by others); 13 more older ones are from the desktop host and before the boot field existed. Now the watcher takes an exclusive lock on `jobs/<job>.lock` before it writes `start`, keeps it while it runs and wakes (the job does not inherit it), and removes the file when it is done. A lock file nobody holds is a dead watcher, whatever killed it and whichever container or namespace the sweeper runs in (a flock is the kernel's, and a pid is not: another container cannot see this one's pids, and a restarted container reuses them). **Every `run-and-wake` call sweeps first**: a launch, `--wait` (every second it waits) and `--recover`. For each lock file nobody holds it checks that the job's own process is gone too (its pid with its start stamp, `pid_start`, so a recycled pid is not taken for it; a live job whose watcher died is left running and swept once it ends), writes `end` with `exit` and `signal` null, `error` `lost` and `lost` true (the job's own status is not known), and sends the owner the one wake: `job did NOT finish: its watcher is gone and sent no result ..., so its status is unknown. Rerun it; this is not a result`. A watcher that died after `end` but before its wake (no `wake` or `skip`) gets the same text and no second `end`: whatever status it recorded is not passed on as a result (a shutdown makes wrapper shells record exit 0 as the job inside dies). A job from an earlier boot (its `boot` is not this boot's: a host restart, or the pod moved to another node) is left to `--recover`'s text, which the sweep runs for it once, without waiting for T3 and without printing; so the pod, which has no systemd, still tells its threads, and the sweep and `--recover` cannot both send. A sweep that raises for a job writes an `error` record (`step` `sweep`) for it and goes on to the next; one that cannot run at all writes it under the job name `run-and-wake`. `--recover` sweeps even when recovery could not reach T3. A `--wait` run by the owner stands in for the wake (`skip` `waited`) and prints the same did-not-finish line, exit 1. A launch or `--wait` tries T3 once; if no server answers, the wake is logged as failed with `swept` true, the lock stays, and the next call tries again. `--recover` waits for T3 the way the watcher does (run it from a boot or start script and it delivers as soon as T3 answers). `lost` is also not a result in the log: readers that ask only "did it end" (the coordinator's running-jobs page, the builder Stop hook) are right to see it as ended. A job logged before the lock existed (no lock file) is never swept.

Not covered: a job whose watcher died while the job lives on in another container's pid space (a sweep from the other container reads the job as gone: a pid cannot be checked across namespaces; the job is then called lost while it runs. The pod starts every job from the t3 container, and the daemon container never sweeps). A pod start with no run-and-wake call afterwards: the wake waits for the next call, so on the pod the start script should run `run-and-wake --recover` detached (follow-up in the coordinator repo: dotfiles cannot add it, container mode runs no script on every apply). A restart of the work Mac while nothing calls run-and-wake: the sweep runs at the next call there too, but no boot-time unit exists on macOS.

**Why jobs were lost on 2026-11-15 (evidence): the host rebooted, not T3.** Boot -2's journal: `sudo systemctl reboot` at 11:45:54 PST (19:45:54Z, from a seat-lead's scratch directory), logind "System is rebooting" at 11:46:24, then the user manager stopped everything: "Stopping run-and-wake job …" for 9 scopes and "Stopping T3 Code server" at 11:46:25 (stopped 11:46:28). The watchers recorded `end` SIGTERM at 19:46:25.4Z and each wake failed at 19:46:26-28Z with `exit 1: Could not reach the T3 Code server at http://127.0.0.1:3773. fetch failed`. A second reboot at 13:02:34 PST (21:02:34Z) did the same to 9 more jobs (a lead's 22:21Z merge timer among them) and 10 more had an `end` and no `wake`. A T3 restart alone does not stop these scopes (see Resources); the bundled launcher (`t3 __service-launcher`) can also swap the server process without `t3code.service` starting, which is why the live watcher waits for T3 instead of relying on a unit trigger.

**Why a job in a T3 session died (evidence, 2026-11-12).** Read from the bundled T3 server (0.1.10-nightly.20261111.4529): it releases a Claude session when it has had no turn for 30 minutes (`DEFAULT_IDLE_TIMEOUT_MS = 1_800_000`); it keeps one up to 4 hours past that only while Claude itself reports background tasks or subagents, and a run-and-wake job is neither. On release the Claude process exits and T3 runs `systemctl --user stop t3code-claude-<id>.scope`. It stops scopes in other ways too: a thread force-stop (`forceStopThread`), a runtime error, and `stopLeftoverAgents` at server start. The lost kgate job's thread (resumed in scope `t3code-claude-36716fbb`, matched by `--session-id` in the journal) completed its last run at `08:24:35.761Z`; the scope was stopped at `08:54:36`, 30 min 0.2 s later. The other scope stopped that second, `t3code-claude-03faff1d`, resumed the launch thread whose last run completed at `08:24:38.3Z`. Of the 200 `t3code-claude-*` scopes the user journal has stopped since 2026-11-11 00:00, 70 lived 30 to 35 minutes (one short turn, then the idle release). A restart does it faster: `systemctl --user restart t3code` at 2026-11-11 21:24:15 stopped about 20 session scopes within 9 seconds (which of T3's stop paths did each one is not shown by the journal). So a job that outlives its session by 30 minutes is lost without this scope, whatever the thread does.

**Resources.** A job must not escape the memory limit the agents have: this host has already had an out-of-memory kill, and it runs coordinatord and T3. T3 sets `MemoryHigh` (total RAM minus 6 GiB) and `MemoryMax` (minus 4 GiB) on `app-t3code-agents.slice` at server start, and `CPUWeight=10` on its parent `app-t3code.slice`, so agents get 10 against the server's 1000 when the CPU is contended. The scope is therefore started with `--slice=app-t3code-agents.slice`: it shares exactly the agents' budget and CPU weight, one pool rather than two. A separate `run-and-wake.slice` with copied limits was rejected: jobs and agents would each get the full budget, so the worst case is twice the limit, and the host would hit the kernel's global OOM killer instead of the slice's. In the shared slice a runaway job is throttled with the agents at `MemoryHigh` and killed inside the slice at `MemoryMax`.

Why that slice is safe to put a job in (T3 0.1.10-nightly.20261111.4529, `src/process/agentScope.ts`): T3 puts a session's scope in `app-t3code-agents-<sha256(stateDir)[0:12]>.slice`, a child of the agents slice (the dash in the name), and puts a scope that must survive a server restart (`survivesRestart`) directly in `app-t3code-agents.slice`, where the job's scope sits. Its stops are narrow. The server-start sweep `stopLeftoverAgents` stops only that per-state-dir slice, not the agents slice. `AgentScope.stop` (session release) returns unless the unit name starts `t3code-` and ends `.scope`. `AgentScope.kill` (force-stop) acts only on the unit it tracks for that thread. Nothing stops `app-t3code-agents.slice` itself. A job placed in the per-state-dir slice would be killed by the sweep: do not use it. (The lines are in `~/.local/share/coordinator-workspace/raw-scope-fix/t3-strings.txt`, the bundled server's text, lines 2134770-2135060; a T3 release that widens a stop would show in the live proof.) The proof reads the slice from `/proc/self/cgroup` into the `start` record (`slice`), not from what was asked.

When T3 has not run since boot, the agents slice has no limit (`systemctl --user show app-t3code-agents.slice -p MemoryMax` says `infinity`) and no agents run either. The launcher then puts `MemoryHigh` and `MemoryMax` on the scope itself, with T3's formula, in `app.slice`: a lone job is still capped below the host's RAM. Placing the scope in a slice that does not exist would make an unlimited one. The work Mac has no `systemd-run` and none of this.

**Interim wrap.** Before this change a lead could run `systemd-run --user --scope --quiet --collect -- run-and-wake -- <cmd>` (Linux host only; it fails where there is no `systemd-run`). With this change the wrap is unnecessary and harmless (two scopes; the job ends in `run-and-wake-<job>.scope`).

## Wakes that say nothing new

The audit of 2026-11-09 to 11-16 (token-efficiency audit-1116, B `q:wake`) counted 6,761 wake turns that did nothing, 1,369 of them from this tool, and found 5 of 5 hand-read run-and-wake samples were no-news (a result already reported, a superseded gate, a job already resubmitted, a stale failure, a refused first run). Three changes follow. None drops a result nobody has seen: every other end, success or failure, still wakes.

- **`run-and-wake --wait JOB`.** Blocks until JOB's `end` record, prints the line the wake would have carried and exits with the job's status (`128+n` for a signal, `1` when the job cannot end: its host restarted, or its watcher died and left no `end` for four seconds, and `64` for a job that is not in the log). While it blocks it holds a shared lock on `jobs/<job>.wait`; when it prints it writes `jobs/<job>.read` and a `read` record. The watcher, after it writes `end`, tries to take the lock and looks for the marker. A held lock or a marker means the session has the result, so the watcher writes `skip` with reason `waited` and sends nothing. The kernel drops the lock if the waiter dies, so a killed waiter does not hide the wake; the one window left is a waiter killed in the milliseconds between the watcher's check and its own print. A waiter that attaches after the wake went out prints at once and the wake stands. Only a wait run by the session the wake is for counts: the same `T3CODE_THREAD_ID`, or the same `HERDR_PANE_ID` and `PI_SESSION_FILE` (the rule that picks the wake target). Only that waiter takes the lock and writes the marker. A wait from any other session (a lead waiting on a builder's job) prints the result, writes `read` with `owner: false`, and leaves the owner's wake to go out. For a builder it replaces `tail --pid` (the Stop hook names it, `run_and_wake_wait_hint`). Before this a builder that waited with `tail --pid` read the result inline and then got the same result again as a wake after its turn (#507 started that; the audit window ends before #507 merged).
- **A job the session cancelled is not announced.** `kgate cancel` stops one job, only the caller's own, and prints that job's end line to the caller (docs/kgate.md, "Cancelling a job"). kgate's end line for it has `"cancelled": true` and `job` set to the run-and-wake id. The watcher reads that line (the last megabyte of `${KGATE_STATE:-~/.local/state/kgate}/log.jsonl`) and writes `skip` with reason `cancelled`. 267 of the 1,369 no-news wakes were this (their output ends `kgate: cancelled by kgate cancel`). Applies to a pane wake too. A job killed any other way (a signal from elsewhere, an OOM kill, a restart) still wakes. Not done: guessing that a job was replaced because the same thread started the same command again. Parallel flake reruns do exactly that on purpose (playbook 8fff2add: up to 3 at once), and their results are all wanted.
- **A burst is one message.** A T3 thread's wakes for jobs that end within `RUN_AND_WAKE_COALESCE` seconds (default 10; `0` turns it off; a value that is not a non-negative number warns and uses 10) go out as one `t3 thread send`, one line per job, each line the text that job would have sent alone (`[run-and-wake k:<job>] job finished: ...`). Each watcher appends its line to `spool/<sha1(thread)[:16]>.jsonl` under a lock and sleeps the window; the first to wake sends everything queued and writes every merged job's `wake` record (`merged_with` lists the other jobs), the rest find their job gone and exit. At send time a job whose result was read in the meantime is dropped (`skip`, `waited`). A stop signal during the sleep sends at once (the host may be going down), and a job that was itself stopped is sent at once without the window. Pane wakes are not merged. The lock is held across the send, so a job that ends while T3 is down joins the next message. Cost: a job's wake arrives up to 10 s later than before. Of 5,124 T3 wakes in 11-11 to 11-16, 633 came within 15 s of another to the same thread. A watcher SIGKILLed during the window or the send leaves its line in the spool: it goes out late with the next burst on that thread (and after a host restart `--recover` may send the job a second time, as the did-not-finish text).

## Log

`${XDG_STATE_HOME:-~/.local/state}/run-and-wake/log.jsonl`, one JSON record per line. Every record has `ts` (UTC, milliseconds), `job` and `event`:

| Event | Fields |
|---|---|
| `start` | `cmd` (argv), `cwd`, `pane`, `session`, `thread` (null unless woken through T3), `pid` (null if it could not start), `pid_start` (the job process's start stamp: Linux `/proc` start ticks, else `ps lstart`), `watcher` (the watcher's pid), `output`, `op_token` (`env`, `file` or null: where the job's 1Password token came from; the value is never logged), `scope` (the job's systemd scope, `run-and-wake-<job>.scope`; null on the plain path), `boot` (the kernel boot id, `/proc/sys/kernel/random/boot_id`; null off Linux) |
| `end` | `exit` (null if killed), `signal`, `duration_s`, `error` (could not start; `host-restarted` when `--recover` wrote it), `stopped` (the signals the watcher forwarded to the job; absent if none), `recovered` (true when `--recover` wrote it), `lost` (true with `error` `lost` when a sweep wrote it: the watcher was gone, `exit` and `signal` null) |
| `blocked` | none: the pane showed a dialog and the wake is waiting |
| `error` | `step` (`sweep`), `error` (the exception): a sweep failed for this job (job `run-and-wake` when the sweep itself could not run) |
| `wake` | `target` (`herdr` or `t3`), `result` (`sent` or `failed`), `error` if failed, `duration_s` (from job end to send; for a merged message, from the moment the merged send began), `attempts` (when T3 had to be retried), `recover` (true when `--recover` sent it), `swept` (true when a sweep sent it), `merged_with` (the other jobs in the same message), `session_after` if the pane showed another session right after the send (herdr only) |
| `read` | `owner` (true when the waiter ran in the session the wake is for; only then is the wake dropped) |
| `skip` | `reason`, `detail` |

Replay one job: `grep <job-id> ~/.local/state/run-and-wake/log.jsonl`. Job output files are not pruned.

## Profiles

It lands on `personal` and `axon-work-computer`, like heavy-gate: `dot_local/bin` with no ignore rule, so no `docs/profiles.md` row. Termux already ignores `.local/bin/*` except `passage-review`, and has no herdr panes. On the work Mac, Michael applies it himself.

| Profile | Path that runs |
|---|---|
| `personal` (this Linux desktop, user manager present) | the probe passes, so the launcher execs `systemd-run --user --scope` and the job runs in `run-and-wake-<job>.scope` inside `app-t3code-agents.slice` (or `app.slice` with its own limits when T3 has not set the slice's) |
| `personal` where `systemd-run --user` fails (a shell with no user manager, a kgate pod) | the probe fails: today's path, fork and `setsid` only. A scope stop still takes the job. |
| `axon-work-computer` (macOS) | no `systemd-run`: today's path, unchanged. No T3-in-systemd scope exists there, so nothing is lost. The signal-forwarding in the watcher applies on every path. |
| `termux` | not deployed |

The sweep and the lock ship in the one script, so every profile has them (Linux and macOS: `flock` and `ps` exist on both; the start stamp uses `/proc` where there is one and `ps -o lstart` where not). What differs is who calls it with nothing else running: `personal` Linux desktop, `run-and-wake-recover.service` at login (it runs `--recover`, which now sweeps too); the agent host pod, any call (an agent launching or waiting on a job), and a start script that runs `--recover` detached would make it prompt (follow-up); `axon-work-computer` (macOS), any call, and nothing at boot.

The recovery unit (`run-and-wake-recover.service`) and the script that enables it (`90_run_and_wake_recover_systemd.sh`) land on `personal` Linux only (`docs/profiles.md` has the row): the work profile is macOS, which has no systemd and no T3 service from this source, so a restart there still loses the job and its wake. The `--recover` command and the `boot` field ship everywhere and do nothing where there is no boot id.

## Tests

`python3 -m unittest discover -s tests/run-and-wake -v` runs the real script with a fake `herdr` and a fake `t3` (records argv and stdin) first on PATH, and a fake `systemd-run` that fails by default, so every test takes the plain path whatever the host is. (The suite runs in CI through `scripts/ci-linux.sh`.) It covers the wake, exit statuses (0, 7, 75, 127, SIGTERM), the job outliving a SIGKILLed launching process group, heavy-gate composition (the real gate giving up with 75), a blocked pane, a failed wait, a refused prompt, a session swapped between check and send (`session_after`), the launcher killed before the watcher reports, a T3 thread woken with the same text, a failed or missing T3 CLI, the pane-over-thread choice, the 1Password token given to the job from its file, from the environment, or not at all (the value kept out of the log and output), and two seeded faults: the pane closed before the job ends (`pane-gone`) and the session swapped (`session-changed`). Scope tests: a recording `systemd-run` (which refuses a call without `--expand-environment=no`) shows the probe, the exec with the same options and the agents slice, and the cwd and environment arriving in the scope; with the slice unlimited, or no `systemctl`, the limits go on the scope; `$` and `%` reach the job as typed, with the fake and with the real `systemd-run`; a failing `systemd-run` and a PATH with none keep the plain path; and, only where a real user manager exists, a scope of the test's own (`raw-test-outer-<id>`) is stopped the way T3 stops a session's and the job must still finish, write `end` and wake. Signal tests: the watcher's group signalled together (as a scope stop does), the watcher alone, a job SIGKILLed, the job not inheriting a signal the watcher handles, and a signal ignored at launch (nohup) staying ignored for the job. Recovery tests: T3 down for a few tries still delivers one wake; a refused send is not retried; T3 down past the window leaves a failed wake that `--recover` delivers once and not twice; a stop signal ends a watcher that is waiting for T3; a job cut off by a restart (seeded with a foreign boot id, with and without an `end`) is told it did not finish, and a shutdown exit status is never sent as a result; an earlier-boot job with a clean `end` whose wake only found T3 down is still told it did not finish; old records, pane jobs, running jobs and delivered jobs are left alone and nothing is written; `--recover` exits 1 while T3 is down and delivers on the next run; and one real job stopped with T3 down, then "restarted" and recovered. A malformed `RUN_AND_WAKE_T3_RETRY` (five bad values) warns and still runs and wakes; log lines that are JSON but not a job record are skipped by `--recover`, which still recovers the real record after them. The fake `t3` prints the two answers the real CLI gives (probed 2026-11-15: no server, and `Thread <id> was not found.`, both exit 1). Each test reads the job back from the log alone. Lost-watcher tests (the sweep): the watcher and the job SIGKILLed together (a container restart) leave a `start`, and the next launch writes `end` (`lost`) and sends the one did-not-finish wake and no second one; a finished job leaves no lock and a running job is not swept; the job does not inherit the lock; a dead watcher with a live job is left until the job is gone; a recycled pid is not taken for the job; `--recover` waits for T3 and delivers; a sweep that finds T3 down keeps the debt and delivers on the next call; `--wait` on a lost job prints the did-not-finish line, exits 1 and sends no second wake; a lost pane job is woken through herdr; a watcher that died between `end` and its wake gets the did-not-finish text and never its recorded status as a result; a shutdown-cut earlier-boot job whose wrapper recorded exit 0 gets recover's restart text from the sweep, once, and the lock is cleared on the next call; an earlier-boot job with no end (the pod on another node) gets it too, without the sweep waiting for T3; `--recover` does not quote a lost end as a status; a sweep that raises leaves an `error` record and the call goes on; `--recover` sweeps when T3 never answered; a job from before the lock is left alone; the `ps` fallback for the start stamp. `tests/run-and-wake/proof_lost_watcher.sh <script>` is the same break outside the unit tests, with scratch state and a fake `t3`: the old script leaves a `start` and nothing else, the fixed one an `end` and a wake. Two scripts prove it outside the unit tests, on a Linux host with a user manager: `tests/run-and-wake/proof_t3_outage.sh <script>` stops a scratch unit that stands in for T3 while a real job ends (run it with the old and the fixed script), and `tests/run-and-wake/proof_t3_restart.sh launch|check` does the same against the real T3, with jobs that end by themselves when T3's port stops answering, so nobody acts during the restart. No wake target: a launch with no pane (and with a pane but no Pi session) and no thread waits for the job, prints the result line and exits with the job's status; a waiting launcher whose whole process group is SIGKILLed leaves the job running, and `--wait` then returns its result. The no-news changes: a waiter gets the result and the watcher sends nothing (`skip` `waited`); a waiter killed before the job ends does not hide the wake; waiting on an ended job prints at once; a signal death is `128+n`; an unknown job is 64; a restart-cut job says it did not finish; a job whose kgate end line says cancelled sends nothing, for a thread and for a pane, while a kgate line that is not cancelled, or is another job's, still wakes; a burst of three jobs is one message of three lines with one `wake` record each and `merged_with`; a lone job is sent alone after the window; two threads and two bursts further apart than the window are separate sends; a result read inside the window is dropped from the merged message; a stop signal in the window and a stopped job send at once; a pane wake is never merged; the window setting parses as above. A wait from another thread leaves the owner's wake in place. The default test environment sets `RUN_AND_WAKE_COALESCE=0`; the cancelled tests write kgate's log where kgate does, under `XDG_STATE_HOME`.
