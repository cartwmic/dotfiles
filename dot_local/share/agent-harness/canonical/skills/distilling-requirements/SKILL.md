# Distilling Requirements

Read a repo and write down what it must do, including what nobody wrote down and the non-functional requirements (quality), with evidence for every line and the test that covers it. The output is a snapshot: one file that records the code at one commit and is never maintained, in a fixed shape ([references/output-shape.md](references/output-shape.md)) so a person, another skill or a later run reads it the same way.

**How it differs from neighbours.** `review-map` explains a diff. This skill needs only the repo, covers four lenses, and adds state machines, unenforced invariants and test-coverage gaps. It mints no `LE-n` ids.

## Inputs

- Repo path (required), optionally a scope. For a repo over ~20k lines, scope it. Scope means the named files, their first ring of callees (direct callees whose types or effects the scope's requirements depend on; read nothing further), and the direct callers that write the state you model; list both in the header `scope:`, and write `path (lines)` for a callee you read only in part. Never silently sample.
- Output path. Default: a scratch folder outside the repo. Never write a root-level `REQUIREMENTS.md` in a repo: it looks live. To keep it, write `docs/snapshots/<YYYY-MM-DD>-<sha7>/REQUIREMENTS.md` in the repo, or the same folder name elsewhere, only when asked.
- Record the commit SHA at the start; it is the snapshot commit (header `snapshot:`). At the end run `git diff --stat <sha> -- <scope paths>`; if the scope moved, re-read what changed and say so in the header. With no git history (an archive), set `source: archive` and write `no-git` for the sha in the header instead.
- Read the repo's own docs and `AGENTS.md`/`CLAUDE.md` first.
- An interview answers file (`interview.md` from [references/interview.md](references/interview.md)), when given. Its answers apply to the whole repo; a scoped run takes only those that bear on its scope.
- `repo-wide: yes | no`. Repo-wide history and interview answers go to one run: when several scoped runs cover one repo, the owner or caller names exactly one `repo-wide: yes` and gives that run the other runs' scope lists. It runs `history_signals.py` unscoped, and takes the signals and interview answers that touch none of the given scopes: an answer whose code lies in another run's scope belongs to that run. A run with no scope is `yes`. A scoped run takes only history that touches its scope paths.
- A `GUIDE.md` from deriving-readable-docs, when present, is a map, not truth: use its surface table (A1) and capability sections (A4 on) to scope the work and find entry points. Open every line you cite before writing a row. A guide claim is never a stated source. Without a guide, work as before.
- A scope path that does not exist: say so in the header and an open question; write no rows from it.
- Depth: this is a first pass. Read test bodies for the rows that matter most (high impact, or ones a finding rests on) and judge the rest `title`. Stop when new reads stop producing new rows; merge rows that share one source and one check.

## Rules for every row

- **Evidence or it does not go in.** Cite `path:line` you opened, or a `commit:`, `pr:` or `issue:` ref you looked up, or `owner:`. Never infer from a name.
- **Outcome, not mechanism.** Write each requirement as what the user or caller needs, not as how the code does it. A row that restates the code can never be violated, so buggy code passes as "intended". Treat "by design" as a claim to check against stated intent (docs, PRD, names, error text), not a reason to drop a finding; if intent is unstated, ask a Q.
- **One obligation per row.** If a check covers only one clause of a row, `fit` is `partial`; split a row that joins two obligations.
- **Kind** (`explicit`, `inferred`, `implicit`) is what told you it is a requirement: apply the one rule in [references/output-shape.md](references/output-shape.md). Name the source kind in `note` when it is only a comment or a test title.
- **Status** is `proposed` until the owner accepts it during this run (an interview answer); set `accepted` only for those, with `owner:` evidence. An inferred row is `proposed` or `disputed`; once the owner confirms it, it is `explicit` and `accepted`, keeps its history refs and gains `owner:` evidence.
- **Inferred rows** keep the evidence rule. `check`, `fit` and `enforced` are judged against today's code like any row. Drop a row whose code no longer exists at the snapshot commit and say so in the report. `lens: quality` is a non-functional requirement (performance, reliability and availability, security and privacy, maintainability, operability and observability, portability, compatibility, cost, data retention); `technical` is a constraint the code depends on (runtime, schema, layering, interfaces).
- **A snapshot is never evidence.** A file under `docs/snapshots/`, or any file carrying the line "Snapshot of ... Not maintained", is never evidence or a stated source; skip it. A `GUIDE.md` or `REQUIREMENTS.md` whose snapshot sha is not the commit you work on is stale: say so and use it only as leads.
- **Enduring or incidental.** Do not promote every implementation detail to a requirement. Mark `durability`, and use `unclear` plus an open question when you cannot tell.
- **Conflicts stay visible.** If doc, test and code disagree, write one row per claim, status `disputed`, and leave the choice to the owner.
- **Say what you did not read**, including test bodies you judged from titles (`fit: title`).
- **One fact, one table.** Link by id (`I-3`, `F-2`) instead of repeating it; a row of another register is `<label>:<id>` (see output-shape). If you looked at something and found it intentional, say so in `note` or an open question.

## Procedure

1. **Orient.** Entry points, docs, tests, config, schema, and how tests run. Run only what is cheap and safe; heavy jobs go where the owner says.
   The repo's surface list comes from `python3 -I <sibling skill>/deriving-readable-docs/scripts/surfaces.py REPO` (the same list the guide and the design facts use); read it for entry points.
2. **Explicit requirements.** Pull what the repo's own words say the system does or must do from docs, README, `AGENTS.md`, issue text, CLI help, schemas, contracts, test names and assertions. One row each, as an observable "shall" sentence.
3. **History (mandatory).** Run `history_signals.py` at the snapshot commit and read all of what it lists as leads, with the repo's docs, PRs and issues: follow [references/history.md](references/history.md). It cuts nothing unless you pass `--limit`; on a long history write it with `--out FILE` and read the file in parts. Never read only the top of a list: if you cut one, say so in the report. Write the rev you ran it at in the header `history:` (`no-git` for an archive); `check_shape.py` requires it. It runs before the interview so the proposals have leads. Say in the report if there was no history to read.
4. **Interview (optional).** Only when this session can ask the owner, or an answers file is given. Before asking, the session that asks runs `history_signals.py` and skims the code for timeouts, limits, retries, retention and auth settings, so the proposals have leads; when a caller runs the interview and hands the file to a subagent, the caller does this. Follow [references/interview.md](references/interview.md). Answers become `explicit` `quality` rows with evidence `owner:interview <date> Q<n>`; set the header `interview:` to the answers file (in the caller's output folder), or `none`. A subagent that cannot ask takes the file as input; the interview runs earlier, in the session that can ask.
5. **Product lens.** Who uses this, for what outcome; the user-visible journeys, inputs, outputs, and what a user would call broken.
6. **Behavioral lens: state machines.** Trevin Chow's prompt, word for word:

   > Find the app's explicit and implicit state machines and document their states, invariants, and transition tables in one file. Identify invalid states or transitions the code can actually reach, with evidence, including through retries and concurrency. Prioritize confirmed bugs by impact, group related fixes into issues, then fix them with regression tests and keep the document updated.

   This step does its first two sentences. Sentences three and four are "Acting on findings" below. The "keep the document updated" part is replaced here by writing a new snapshot.

   Look for status/phase/enum fields, booleans that combine into a mode, lifecycle columns, queues, retries, locks, caches, and "if X then skip" guards. For each machine write its states, invariants and transition table, and list every process or caller that writes the state and whether each uses a stale-write guard. Then walk the code for transitions the table does not allow but the code can reach: a retry repeating a side effect, two writers racing, a crash between two writes, a read-then-write with no guard, a state with no way out, a startup migration that checks then changes (a second process can run between the two). A finding is `confirmed` only with a reproducible path or an unambiguous code path, after you have read the callee that would do the write (not just the caller); `likely` when the code path is certain but a library's or system's behavior is assumed; otherwise `suspected`.
7. **Technical and quality lenses.** Technical: constraints the code depends on: runtime and versions, storage and schema, layering and import rules, interfaces to other systems, limits, configuration. Source: manifests, build/CI config, boundary tests, comments. Quality: the non-functional areas above (including compatibility across versions); take rows from timeouts, limits, retries, auth checks, logging, retention settings and CI matrices, and from the history step.
8. **Unenforced invariants.** Find every invariant the repo relies on but does not explicitly enforce: a consumer that assumes a field is set, ordered, unique, non-empty or in a range, with no type, check, constraint or test that makes it so. Check both directions: a consumer that trusts a value nothing guarantees, and a validator stricter or looser than the values the system really produces (ids, names, paths: compare every boundary check against real examples in tests, fixtures, docs and other components). Give the place that relies on it, the missing guard, and whether a violation is reachable. If it is reachable and does harm, also add an `F` row that cites the `U` id.
9. **Coverage per requirement.** For each register row, name the check that covers it (test, type, schema, CI gate; at most three, `+N more` if more) and compare what it asserts with what the requirement says. `full`, `partial` (name what is not asserted in `note`, for example "requirement: title or description; test: title only"), `none`, or `title` (judged from the test name; bodies not read). Set `enforced` from the code, apart from tests, and judge only the row's own claim: `yes` means the code makes the claim hold on every path that can break it; a different writer skipping the mechanism is a separate row or an F row, not `partial` here.
10. **Write the file** in the shape in [references/output-shape.md](references/output-shape.md) (header, the snapshot line under the title), then run these three scripts, each every time:
    - `python3 -I <skill dir>/scripts/check_shape.py REQUIREMENTS.md REPO`: fix what it reports and rerun until it prints `ok`. It checks structure only, not truth, and rejects a citation into `docs/snapshots/` or any file marked "Not maintained".
    - `python3 -I <skill dir>/scripts/surface_coverage.py REQUIREMENTS.md REPO` (a scoped run adds `--scope <path>`, repeatable; only in-scope surfaces need an answer. A repo-wide run runs it without `--scope`: with the other runs' scopes it lists "0 of 0"): it lists the surfaces (commands, flags, routes, env, config, entry points) that no R-row cites by `path:line` or names. Each is a requirement to write or a surface to say you judged incidental in an open question. It checks citation only, and it needs `deriving-readable-docs` installed beside this skill.
    - `python3 -I <skill dir>/scripts/check_history_refs.py REQUIREMENTS.md REPO`, with or without checker sessions: it resolves every `commit:`, `pr:` and `issue:` ref (output in [references/truth-check.md](references/truth-check.md)) and exits 1 on an UNRESOLVED one: fix the ref.
11. **Truth check.** Check that the lines each row cites show what the row says, and that history refs resolve: follow [references/truth-check.md](references/truth-check.md). A fix round, at most two, goes in the Run log; report the rows that still fail.
12. **Report** in plain words: counts by lens and kind, the inferred rows dropped because their code is gone, the rows that are "resolved, claim not read-checked", the top findings by impact, the biggest coverage gaps, what failed the truth check or was not checked, and what you did not read.

## Acting on findings

Stop after step 12 unless asked. When asked to act (sentences three and four of the prompt): group related findings into issues, fix confirmed ones with a regression test that fails before the fix, and send the fixes to issues and PRs. Do not edit the snapshot afterwards: a later run writes a new one. Confirm before opening issues or pushing.
