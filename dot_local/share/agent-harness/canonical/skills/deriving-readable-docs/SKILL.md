# Deriving readable docs

Turn any repo into one guide a person can read cold. Code is the source: a sentence about the product rests on the code line that defines it. The repo's own words (README, `docs/`, help text, comments) give intent and names. Tests are optional evidence: they confirm a behaviour when the repo has them.

Output: `GUIDE.md` in a folder outside the repo, default `~/.local/share/derived-docs/<repo-name>/`, or the caller's path. Part 1 is about 1,000 words of plain English, each sentence tagged `[A4.3f9a]` with the id of the appendix line it restates. Part 2 is the appendix: A1 surfaces and A2 evidence (printed by scripts), A3 the whole product, A4 and on one section per capability, A-last what nobody read.

Every mechanical step is a script call: agents write sentences and judge claims; scripts count, cut, join and score. `<skill>` is this skill's folder.

## Rules for every sentence

The cited lines must show everything the sentence says. `references/drafting.md` is the writers' method.

- One behaviour per sentence, at most 18 words. A word is a space-separated token with a letter, digit or underscore; citations and ids (`[A4.3f9a]`) are not words. A longer sentence is split, and each part keeps its condition.
- Every claim ends with a citation in exactly this form: backticked `path/to/file.ext:LINE` or `path/to/file.ext:START-END`, relative to the repo root; several may share one pair of backticks. Cite the line that defines the behaviour, with its flags, branches and early exits. No other backticked text may look like `word:number`.
- A claim that rests on a README, doc, comment or test title says so ("README", "code comment", "in the test"). A claim taken from a name or the layout, without reading its body, is labelled **inferred**.
- A rule too long or spread out to read end to end is not described as a behaviour: state the surface only ("`--foo` takes a number (help text)").
- Never write "No test covers X": `assemble.py` prints what tests cover. Add no security, privacy or threat sections unless the caller asks, and no sentence about the document itself.

## Procedure

1. **Orient.** Record the repo name and `git rev-parse HEAD` (no git: say so). Make a work folder outside the repo. Read the README and `docs/` for names and users.
2. **Surfaces.** Run `python3 -I <skill>/scripts/surfaces.py <repo> --json > surfaces.json`. It lists commands, flags, routes, config and entry points, each a real `path:line`, and misses registries, hand-parsed arguments and UI code. One scout session (Sonnet) reads the README, `docs/` and `surfaces.json` and writes `scout.txt`, the capabilities a user would name one a line, each as a surface name as the code spells it (never a file path), and `groups.txt`, the files each capability's code sits in, for step 5. Run `python3 -I <skill>/scripts/surfaces.py <repo> --resolve scout.txt > scout.resolved`. Drop a name it cannot find and a `WEAK MATCH`.
3. **Tests, if any.** Run `python3 -I <skill>/scripts/harvest_points.py <repo> > points.json`. `assemble.py` reads it for A2; with no tests the file is `[]` and A2 says so.
4. **Budgets.** Whole guide 6,000 words; Part 1 1,000; A3 600; A4 and on 3,900 shared by capability. Under 30k lines, halve all three. Printed rows are not counted.
5. **Frame and section writers.** One fresh Opus session per writer, never one for the whole repo: a frame writer for A3 and one per capability for A4 and on, briefed as `references/drafting.md` ends. Plan 6-10 appendix sections in all, grouping scout names that share code. Each brief lists the writer's files under `Files:` (from `groups.txt`); `python3 -I <skill>/scripts/lint_brief.py brief.md <repo>` fails a file the repo lacks, so run it before the brief goes out. Each writer saves `work/choice.md`, writes its evidence and audit files by hand (no script fills them) and its draft, runs `python3 -I <skill>/scripts/stamp.py draft.md` (an id for each line), marks its condition sheet, audits its own sentences, and runs `python3 -I <skill>/scripts/check_citations.py draft.md <repo> --max-words <budget> --max-sentence-words 18 --audit work/audit.md`, which also wants `work/choice.md`, `work/guards.md` and `work/evidence.md`. Load the `no-ai-slop` skill in each writer.
6. **Part 1.** Put the appendix parts in the work folder as `A3.md`, `A4.md` and so on, run `python3 -I <skill>/scripts/stamp.py <work>/A*.md`, then `python3 -I <skill>/scripts/assemble.py <work> <repo> --index`. A separate Opus front writer gets the appendix sentences plus the index, and nothing else, and writes `part1.md` in six sections: What it is (with a `Who it is for:` sentence: who uses the product, from the README or docs, or that the repo does not say), How to start, What you can do, How the parts fit, What it needs and keeps, What it does not do. How to start holds the first install or run step; each step restates a cited appendix line.
7. **Assemble and gate.** `python3 -I <skill>/scripts/assemble.py <work> <repo> -o GUIDE.md --clean` joins the parts with the printed header, A1, A2 and A-last, and writes `GUIDE.clean.md` without tags. Then `python3 -I <skill>/scripts/lint_main.py GUIDE.md <repo> --surfaces surfaces.json [--fixed fixed-ids.txt]` gates Part 1. It fails a sentence that drops a condition or source label of a line it tags, or that uses an absolute word (any, anything, every, all, only, always, never, nothing, none, unless) no tagged line uses; it fails Part 1 over 1,000 words at any step, and one with no How to start or Who it is for. Send every FAIL back to the front writer and assemble again.
8. **Check citations.** `python3 -I <skill>/scripts/check_citations.py GUIDE.md <repo> --max-words <the whole-guide budget from step 4> --max-sentence-words 18`. A missing line, a number or quoted name not in the cited lines, or a sentence over 18 words fails. Fix and rerun to exit 0.
9. **Check every claim.** Run `python3 -I <skill>/scripts/slice.py GUIDE.md <repo> --out slices`: Part 1 and the appendix are cut apart into slices of at most 60 claims, each with `slice-K.claims.txt` and `slice-K.flags.txt`. One fresh Opus checker session per slice (not a writer) gets `references/check-brief.md` as written, its claims file, the repo and its flags file. The report has one `read` row per claim and ends with the Counts line; name a Part 1 report `part1-*.md`. Fix as `references/fix-rounds.md` says: the lead fixes appendix findings (a fix that splits a sentence splits it, and does not paste the checker's wording); a Part 1 finding is fixed by a fresh Opus front-writer session, and a missing condition also goes to its tagged appendix line. Rerun the step 8 script, then re-check only the changed ids and the lines a fix split or moved (`slice.py ... --ids changed.txt --was <the guide as last cut>`, then the same with `--was --reports ... --record-fixed fixed-ids.txt`). Run at most 2 fix rounds after round 1; the lead makes every cut after that, Part 1 included.
10. **Score.** `python3 -I <skill>/scripts/score.py <name>=<reports folder> --doc GUIDE.md --repo <repo> --slices slices --out score.json`; score each fix round against its own slices folder, `--slices slices-fixN`. It checks each report's counts and its `read` rows, then prints the rate, errors per 1,000 words, words per claim and claims by cause.
11. **Reader check.** On the shipped guide, after the last fix round, follow `references/reader-check.md`: a fresh Opus reader sees Part 1 only (`python3 -I <skill>/scripts/score.py --reader GUIDE.md`) and answers five questions with quotes, which `score.py --reader GUIDE.md --answers answers.md` verifies; a fresh Opus grader marks the answers against the code. The bar: 5 of 5 correct, and `lint_main.py` passes. One fix round (a fresh Opus front writer; it does not reword a sentence in `fixed-ids.txt`), then report the result.
12. **Publish and report.** Publish to shartifacts (skill `using-shartifacts`) only when the caller says Michael reviews the guide. Report the folder, words against each budget, the score line, the reader-check result and what was not read.
