# Deriving readable docs

Turn a repo's validation points into three documents a person can read cold. A validation point is one check with an observed effect: a test, a black-box journey, an acceptance scenario, a Gherkin scenario, or a line the caller supplies in the owner's words. What the points prove is the source of truth. Nothing else has to exist.

Output: `PRD.md`, `DESIGN.md`, `SPEC.md` in a folder outside the repo. Default `~/.local/share/derived-docs/<repo-name>/`; use the caller's path if given. Never write inside the repo unless asked.

## Rules for every sentence

- Narrative plain English for a human. Short paragraphs. No tables of ids, `P12`-style point ids or requirement codes in the prose.
- Every claim ends with a citation in exactly this form: backticked `path/to/file.ext:LINE` or `path/to/file.ext:START-END`, relative to the repo root. Several may share one pair of backticks, separated by commas. Cite the point's own line, or a line you opened. Nothing else in backticks may look like `word:number`.
- A claim that rests only on the caller's list has no repo line. Quote the list item and mark it with no backticks, for example: (from your list, item 3). Number the items yourself if the list has none.
- A claim you took from a point's name without reading its body, or from the repo's structure, or from a doc, is labelled **inferred** in the sentence. A sentence that mixes proven and inferred claims is split, or labelled inferred as a whole. Never present inference as proof.
- Something the repo plainly does that no point backs goes in a short "Not backed by any validation point" section at the end of the document and is never stated as fact elsewhere. Search before writing an entry: grep the test and journey files for the function, command, flag and message names. If a test asserts it, cite that test; the entry is wrong. The same goes for "no test covers".
- Say what the owner wants only when the caller supplied it or the repo states it. Describe what is proven, not what should be.
- A claim that rests on a README, a doc or a code comment says so in the sentence, for example "(README)", "(code comment)", "(journey comment)". Repeat a comment only after the code agrees with it; if the code contradicts it, drop the claim. A sentence that says more than its cited lines show (a wider set, a stronger word, a number or name they lack) is a defect even when the line exists.
- A test proves what its assert and expect lines compare, not its setup, title or the code it starts. Word the claim to the values compared. Wrong: "a resume runs the saved command" (the test asserts a rebuilt command ran); "the ask command reports where it was posted" (it prints a key and a part count); "starts a daemon" (the test runs a `node -e` child). File a behaviour under the trigger the test shows, not a neighbouring one.
- Say what a key, file or value is (an event key, an action row, a config) only after reading its definition and its users.
- A test or journey proves the cases it runs, not a count, a full set, or "next" and "every". A claim that names how many, lists all members, or says next, every or always cites the code that defines the set, or is worded to what the test shows ("at least", "a later wake"). Wrong: "five headline words" (the test checks five, the code defines six). Right: "the headline is one of its words, for example moving or idle".
- Before stating a behaviour flat ("cannot", "is refused", "falls back", "stays", "whatever X"), open the whole function or command that does it and look for flags, branches and early exits that skip it. State the condition or narrow the claim. Wrong: "a workstream cannot be closed without a closing note" (`--no-thread` closes with none). Right: "without `--no-thread`, a close with no note is refused". A "when X, Y" sentence names every condition the code tests (a flag, a type, "target differs from current", "no row at all" against a different row), and says when a value is the test's own example.
- Do not add security, privacy or threat sections unless the caller asks.

## Procedure

1. **Orient.** Record the repo name and `git rev-parse HEAD` (no git: say so). Skim the README and any `AGENTS.md`/`CLAUDE.md` only for names and users. Read a `REQUIREMENTS.md` or existing docs if present: they suggest claims; each still needs a point or goes under "Not backed".
2. **Harvest.** Run `python3 -I <this skill's dir>/scripts/harvest_points.py <repo> > points.json` (outside the repo). It lists points as a JSON array: `id`, `name`, `kind`, `file`, `line`, `framework`, `context`. It covers pytest/unittest, Rust, Go, JS/TS, JUnit, xUnit/NUnit, GoogleTest/Catch2, XCTest, RSpec/minitest, ExUnit, bats/shell and Gherkin, and lists a file named like a journey, e2e, acceptance or smoke script as one `journey-file` point when it finds no cases inside. Same repo, same output.
   Then add by hand what it cannot see: journeys defined through a house helper, checks in another language, and any list of validation points the caller gave in the owner's words (quote those as given). Leave out copies of other repos' tests and eval baselines (the repo's own suite does not run them as checks) and helpers or properties whose names only look like tests, and say so in each header. Record hand-added points in the headers; leave `points.json` as the raw harvest. If the harvest is empty and the caller gave no list, say so and stop; write no documents, and point to `distilling-requirements` for a repo with no validation points.
3. **Group into capabilities.** Cluster points by what a user gets, not by file. Start from `context` and directory, and name each cluster in the user's words. For thousands of points, group by file and directory first, then read selectively. Name a capability only if a point backs it.
4. **Read what carries a claim.** For each capability open the bodies of the points you will cite and note what is done and what is seen. A point known only by its name is cited as inferred. Stop reading a cluster when more points add no new behaviour.
5. **Write the three documents.** Each opens with a short header: repo, commit, which inputs were used (say whether existing docs were read), and the point counts: harvested; left out; used (body read, cited as proven); read by name only (cited as inferred); not cited (grouped by name, no claim made). A journey is one point at its file's first line. Cite the assertion lines you opened inside it, not line 1.
   - **PRD.md.** Who it is for. What they get, one paragraph per capability. Why it matters. What it does not do, only where a point or the repo says so. "Not backed by any validation point".
   - **DESIGN.md.** How the parts fit together and why, from the repo's structure plus what the points prove: the pieces, what each owns, how they talk, which behaviours hold them together. Reasons the repo does not state are labelled inferred. "Not backed by any validation point".
   - **SPEC.md.** Precise behaviours grouped by capability, one short paragraph or list item per behaviour: the trigger, what happens, what the user or caller sees. "Not backed by any validation point".
6. **Remove slop.** Load the `no-ai-slop` skill (Skill tool) and apply it in edit mode to each of the three files, one at a time, editing in place. Keep every backticked citation, number and name exactly as written. Put the `Voice:` line it requires in your report. Load its voice profile only when the caller says the docs are the owner's own writing.
7. **Check citations.** Run `python3 -I <this skill's dir>/scripts/check_citations.py <doc.md> <repo> > <doc>.checks.txt` for each doc. It exits non-zero when a cited file is missing or a line is out of range, when a number or a `backticked` or "double-quoted" string in a sentence is not in its cited lines (widened by 5 lines each side), or when a doc has no citations. A number that lives in a constant fails until you also cite the line that defines it. Fix the citation, cite the defining line, put the citation directly after the clause it backs (a number in a sentence that cites for something else fails), or drop the claim, then rerun until it exits 0. It also lists, without failing, each sentence with an overreach word (every, all, always, never, only, next, none, any, no X), a count of things, or only comment lines behind it. A doc whose claims all come from the caller's list has no repo citations, so the checker exits 2: skip this step for it and say in that doc's header that no citations were checked.
8. **Check every claim (required).** The script cannot tell whether a line supports a sentence. After the docs are written, start fresh checker sessions (not the writer, and not a session that saw the writer's reasoning). The writer builds each slice and its flag list (the step 7 output for those doc lines) and hands the checker `references/check-brief.md` as written, the slice, the repo path, the flag list and `points.json` with the left-out list (the header counts are judged against them). A claim is any sentence, bullet or table row, header counts included. Cut slices at headings, about 100 claims or fewer each, so the checker reads every cited line itself. It judges every claim HOLDS, WRONG, OVERSTATED or UNSUPPORTED from its own read of the code. Helpers may only find code; no helper or fork judges a claim, and a helper's HOLDS does not count. For a count, a set, next, every, always or a flat behaviour (cannot, is refused, falls back, stays), the checker opens the whole defining function, command or list.
   Fix every claim that is not HOLDS: reword it to what the lines show, cite the line that does show it, or move it to "Not backed". Run step 7 again and send each changed sentence, with its paragraph, to a new checker. Stop when a re-check of every changed sentence returns all HOLDS; the text a checker last judged is the text you ship. Write `CHECKS.md` beside the docs: claims checked, the first-pass counts of each verdict, the number of rounds, and the final counts (all HOLDS). A doc with an unchecked claim is not finished.
9. **Publish only if asked.** Publish to shartifacts (skill `using-shartifacts`) only when the caller says the docs are for Michael to review.
10. **Report.** Give the folder, counts (points harvested, used, left out, read by name only), how many claims are inferred, what sits under "Not backed", the `Voice:` line and the citation check result and the `CHECKS.md` counts (first-pass WRONG, OVERSTATED and UNSUPPORTED, rounds, final). Say what you did not read.
