# Deriving readable docs

Turn a repo's validation points into three documents a person can read cold. A validation point is one check with an observed effect: a test, a black-box journey, an acceptance scenario, a Gherkin scenario, or a line the caller supplies in the owner's words. What the points prove is the source of truth. Nothing else has to exist.

Output: `PRD.md`, `DESIGN.md`, `SPEC.md` in a folder outside the repo. Default `~/.local/share/derived-docs/<repo-name>/`; use the caller's path if given. Never write inside the repo unless asked.

## Rules for every sentence

The cited lines must show everything the sentence says. A first draft by one writer for a whole repo had 13 to 16% of claims failed by fresh checkers; `references/drafting.md` is the method that brings that down, and the section writers follow it.

- Narrative plain English for a human. Short paragraphs. No tables of ids, `P12`-style point ids or requirement codes in the prose. One sentence says one thing.
- Every claim ends with a citation in exactly this form: backticked `path/to/file.ext:LINE` or `path/to/file.ext:START-END`, relative to the repo root. Several may share one pair of backticks, separated by commas. Cite the lines that assert it: the `expect` or `assert` lines you opened, not the title, the setup, a nearby line or a line that "looks related". Nothing else in backticks may look like `word:number`.
- A claim that rests only on the caller's list has no repo line. Quote the list item and mark it with no backticks, for example: (from your list, item 3). Number the items yourself if the list has none.
- A test proves one case, and a rule needs the code that defines it: say the case or cite the code (`references/drafting.md`, stage 2). The script fails every, all, always, never, only, each and a count in words when only tests are cited.
- A claim that rests on a title, a comment, the README or a doc says so in the sentence, for example "(README)", "(code comment)", "(test title)". A claim taken from a point's name, or from the repo's structure, without reading its body is labelled **inferred**; a sentence mixing proven and inferred claims is split or labelled inferred as a whole.
- Never "no test covers X" or "not backed" before you grep the test and journey files for the function, command, flag and message names. If a test asserts it, cite it.
- Say what the owner wants only when the caller supplied it or the repo states it. Do not add security, privacy or threat sections unless the caller asks. No sentence about the document itself except its header.

## Procedure

1. **Orient.** Record the repo name and `git rev-parse HEAD` (no git: say so). Skim the README and any `AGENTS.md`/`CLAUDE.md` only for names and users. Read a `REQUIREMENTS.md` or existing docs if present: they suggest claims; each still needs a point or goes under "Not backed".
2. **Harvest.** Run `python3 -I <this skill's dir>/scripts/harvest_points.py <repo> > points.json` (outside the repo). It lists points as a JSON array: `id`, `name`, `kind`, `file`, `line`, `framework`, `context`. It covers the common test frameworks and lists a journey-named file with no cases inside as one `journey-file` point.
   Then add by hand what it cannot see: journeys defined through a house helper, checks in another language, and any list of validation points the caller gave in the owner's words (quote those as given). Leave out copies of other repos' tests and eval baselines (the repo's own suite does not run them as checks) and helpers or properties whose names only look like tests. Write the left-out ids (`P12`), files and folders (a path ending in `/`), one per line, in `left-out.txt` beside `points.json`, and the reason in each header. Leave `points.json` as the raw harvest. If the harvest is empty and the caller gave no list, say so and stop; write no documents, and point to `distilling-requirements` for a repo with no validation points.
3. **Group into capabilities.** Cluster points by what a user gets, not by file. Start from `context` and directory, and name each cluster in the user's words. For thousands of points, group by file and directory first, then read selectively. Name a capability only if a point backs it. Name the few a reader would list (about ten for thousands of points), and merge the rest.
4. **Set a budget, then cut into sections.** The three documents get one word budget: the caller's, else about 1,000 words per capability (PRD 100, DESIGN 150, SPEC 750). More claims are more errors and a document nobody reads. Cut the work into sections of one or two capabilities, at most about 1,000 budget words each. A section's writer drafts that part of the SPEC and also the PRD and DESIGN pieces for its capabilities (`references/drafting.md`, Stage 4), because only the writer who read the code knows its branches; no writer is given a whole doc to summarise. List for each section its budgets (SPEC, PRD, DESIGN), capabilities, the points (ids) it may draw on, the files they and the code they run sit in, and the doc style it needs. The budget is kept by choosing, never by joining behaviours into one sentence.
5. **One writer session per section.** Start a fresh session for each section (never one writer for the whole repo) and brief it as the last part of `references/drafting.md` says. Each writer picks the behaviours that matter for its capabilities, reads those tests and the code behind them itself, and drafts from an evidence table of their asserts. It does not cover every point. Load the `no-ai-slop` skill (Skill tool) in each writer, to apply in edit mode to its section; its voice profile only when the caller says the docs are the owner's own writing. The writer then runs step 7 on its section, audits every sentence twice (the cited lines and the exits `--sheet` lists, then the whole function, its callers, flags and lists), writes one audit row per sentence, and narrows what it cannot state in a clause; `check_citations.py --audit` FAILs a sentence with no row. The sections can run in parallel. Do not tell a writer what the checkers found.
6. **Assemble.** Join the writers' pieces in order under each document's header, with a short opening for the PRD (who it is for) and the DESIGN (the parts) whose sentences restate those pieces and cite the same lines. Each header holds: repo, commit, which inputs were used (say whether existing docs were read), the hand-added points and the left-out reason, and one counts line in this form: `Counts: harvested N; left out N; used N; read by name only N; not cited N.` Step 7 prints this line; paste it, never count by hand. Nothing else in a document states how many points or sentences there are, and no per-file list of uncited points. Change no sentence a writer audited; a sentence you must reword goes back to its writer or is audited again the same way. Write each "Not backed" entry from what the writers report they could not cover, after you grep the tests for it.
   - **PRD.md.** Who it is for. What they get, one paragraph per capability. Why it matters. What it does not do, only where a point or the repo says so. "Not backed by any validation point".
   - **DESIGN.md.** How the parts fit together and why, from the repo's structure plus what the points prove: the pieces, what each owns, how they talk, which behaviours hold them together. Reasons the repo does not state are labelled inferred. "Not backed by any validation point".
   - **SPEC.md.** Precise behaviours grouped by capability, one short paragraph or list item per behaviour: the trigger, what happens, what the user or caller sees. "Not backed by any validation point".
7. **Check citations.** Run `python3 -I <this skill's dir>/scripts/check_citations.py <doc.md> <repo> --points points.json --left-out left-out.txt --max-words <the doc's budget> > <doc>.checks.txt` for each assembled doc (the writers ran it on their sections, with `--max-words <section budget>` and without `--points`). It exits non-zero on a missing file or out-of-range line, a number or a `backticked` or "double-quoted" string that is not in its cited lines (widened by 5 lines each side), a header count that differs from the harvest and the doc's citations, more words than `--max-words`, an overreach word or count with only tests cited, a sentence with no citation and an overreach word, and a "Not backed" string that a test file holds. Fix the citation, cite the defining line, put the citation directly after the clause it backs, word the sentence to the test's case ("in the test", "in this case", "the test shows"), or drop the claim; rerun until it exits 0. With `--points`, which only the lead's run on the assembled doc passes, it also prints the `Counts:` line. Every run lists, without failing, every sentence with an overreach word or a count, and any whose cited lines are all comments. A doc whose claims all come from the caller's list has no repo citations, so the checker exits 2: skip this step for it and say in its header that no citations were checked.
   `--sheet` prints every claim with its cited lines and, under a range inside a function (Python, TS/JS), the early exits above its last line, marked when they sit inside the range: the other paths the sentence has to state or leave out (`scripts/early_exits.py` does the same for one file and line).
8. **Check every claim (required).** The script cannot tell whether a line supports a sentence. After the docs are written, start fresh checker sessions (not a section writer, and not a session that saw a writer's reasoning). You build each slice and its flag list (the step 7 output for those doc lines) and hand the checker `references/check-brief.md` as written, the slice, the repo path, the flag list and `points.json` with the left-out list. A claim is any sentence, bullet or table row, header included. Cut slices at headings, about 100 claims or fewer each, so the checker reads every cited line itself. The brief sets the bar: every claim judged HOLDS, WRONG, OVERSTATED or UNSUPPORTED from the checker's own read of the code.
   Fix every claim that is not HOLDS: reword it to what the lines show, cite the line that does show it, or move it to "Not backed". If a fix changes which points are used, rerun step 7 for the header counts. Run step 7 again and send each changed sentence, with its paragraph, to a new checker. Stop when a re-check of every changed sentence returns all HOLDS; the text a checker last judged is the text you ship. Write `CHECKS.md` beside the docs: claims checked, the first-pass counts of each verdict, the number of rounds, and the final counts (all HOLDS). A doc with an unchecked claim is not finished.
9. **Publish only if asked.** Publish to shartifacts (skill `using-shartifacts`) only when the caller says the docs are for Michael to review.
10. **Report.** Give the folder, the words against the budget, the header counts, how many claims are inferred, what sits under "Not backed", the writers' `Voice:` line, the citation check result and the `CHECKS.md` counts (first-pass WRONG, OVERSTATED and UNSUPPORTED, rounds, final). Say what you did not read.
