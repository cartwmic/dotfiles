# Deriving readable docs

Turn a repo's validation points into three documents a person can read cold. A validation point is one check with an observed effect: a test, a black-box journey, an acceptance scenario, a Gherkin scenario, or a line the caller supplies in the owner's words. What the points prove is the source of truth. Nothing else has to exist.

Output: `PRD.md`, `DESIGN.md`, `SPEC.md` in a folder outside the repo. Default `~/.local/share/derived-docs/<repo-name>/`; use the caller's path if given. Never write inside the repo unless asked.

## Rules for every sentence

On two runs, fresh checkers failed 13% of first-draft claims, for the reasons below. The cited lines must show everything the sentence says.

- Narrative plain English for a human. Short paragraphs. No tables of ids, `P12`-style point ids or requirement codes in the prose. One sentence says one thing.
- Every claim ends with a citation in exactly this form: backticked `path/to/file.ext:LINE` or `path/to/file.ext:START-END`, relative to the repo root. Several may share one pair of backticks, separated by commas. Cite the lines that assert it: the `expect` or `assert` lines you opened, not the title, the setup, a nearby line or a line that "looks related". Nothing else in backticks may look like `word:number`.
- A claim that rests only on the caller's list has no repo line. Quote the list item and mark it with no backticks, for example: (from your list, item 3). Number the items yourself if the list has none.
- **A test proves one case.** Say the case: the trigger the test uses and the values its assert lines compare. Its own inputs, setup and fixture values are the test's, so say "in the test" or "for example" when you name one. Wrong: "a note with a line break or `|` is refused" (the test feeds `" | "`); "the saved state holds every series" (it asserts the count is above 0).
- **A rule needs the code.** Before you write every, all, always, never, only, each, a count, a full list, or a flat "cannot", "is refused", "falls back", "stays", open the whole function or command that defines it, look for flags, branches and early exits, and cite its lines too. Then state each condition the code tests. Without that, word the sentence to the test's case ("at least", "in the test", "a later wake"). The script fails these words when only tests are cited.
- **What a thing is comes from its definition.** Say what a key, file, value, event or layer is only after reading its definition and its users. Copy numbers, names, flags, messages and the place a result appears (standard output, the log, the exit code) from the asserting line, not from memory or a summary.
- A claim that rests on a title, a comment, the README or a doc says so in the sentence, for example "(README)", "(code comment)", "(test title)". Repeat a comment only after the code agrees with it. A claim taken from a point's name, or from the repo's structure, without reading its body is labelled **inferred**; a sentence mixing proven and inferred claims is split or labelled inferred as a whole.
- Never "no test covers X" or "not backed" before you grep the test and journey files for the function, command, flag and message names. If a test asserts it, cite it. The script greps too.
- Say what the owner wants only when the caller supplied it or the repo states it. Do not add security, privacy or threat sections unless the caller asks. No sentence about the document itself except its header.

## Procedure

1. **Orient.** Record the repo name and `git rev-parse HEAD` (no git: say so). Skim the README and any `AGENTS.md`/`CLAUDE.md` only for names and users. Read a `REQUIREMENTS.md` or existing docs if present: they suggest claims; each still needs a point or goes under "Not backed".
2. **Harvest.** Run `python3 -I <this skill's dir>/scripts/harvest_points.py <repo> > points.json` (outside the repo). It lists points as a JSON array: `id`, `name`, `kind`, `file`, `line`, `framework`, `context`. It covers the common test frameworks and lists a journey-named file with no cases inside as one `journey-file` point.
   Then add by hand what it cannot see: journeys defined through a house helper, checks in another language, and any list of validation points the caller gave in the owner's words (quote those as given). Leave out copies of other repos' tests and eval baselines (the repo's own suite does not run them as checks) and helpers or properties whose names only look like tests. Write the left-out ids (`P12`), files and folders (a path ending in `/`), one per line, in `left-out.txt` beside `points.json`, and the reason in each header. Leave `points.json` as the raw harvest. If the harvest is empty and the caller gave no list, say so and stop; write no documents, and point to `distilling-requirements` for a repo with no validation points.
3. **Group into capabilities.** Cluster points by what a user gets, not by file. Start from `context` and directory, and name each cluster in the user's words. For thousands of points, group by file and directory first, then read selectively. Name a capability only if a point backs it.
4. **Read what carries a claim.** For each capability open the bodies of the points you will cite, and every line you will cite, yourself with your own file tools. A helper's summary of a test is not a read; do not write a claim from one. A point known only by its name is cited as inferred. Stop reading a cluster when more points add no new behaviour.
5. **Write the three documents.** Each opens with a short header: repo, commit, which inputs were used (say whether existing docs were read), the hand-added points and the left-out reason, and one counts line in this form: `Counts: harvested N; left out N; used N; read by name only N; not cited N.` Step 7 prints this line; paste it, never count by hand. Nothing else in the document states how many points or sentences there are, and no per-file list of uncited points.
   - **PRD.md.** Who it is for. What they get, one paragraph per capability. Why it matters. What it does not do, only where a point or the repo says so. "Not backed by any validation point".
   - **DESIGN.md.** How the parts fit together and why, from the repo's structure plus what the points prove: the pieces, what each owns, how they talk, which behaviours hold them together. Reasons the repo does not state are labelled inferred. "Not backed by any validation point".
   - **SPEC.md.** Precise behaviours grouped by capability, one short paragraph or list item per behaviour: the trigger, what happens, what the user or caller sees. "Not backed by any validation point".
6. **Remove slop.** Load the `no-ai-slop` skill (Skill tool) and apply it in edit mode to each of the three files, one at a time, editing in place. Keep every backticked citation, number and name exactly as written. Put the `Voice:` line it requires in your report. Load its voice profile only when the caller says the docs are the owner's own writing.
7. **Check citations.** Run `python3 -I <this skill's dir>/scripts/check_citations.py <doc.md> <repo> --points points.json --left-out left-out.txt > <doc>.checks.txt` for each doc. It exits non-zero on a missing file or out-of-range line, a number or a `backticked` or "double-quoted" string that is not in its cited lines (widened by 5 lines each side), a header count that differs from the harvest and the doc's citations, every, each, all, always, never, only or a count in words with only tests cited (not "read-only", "each other" or "each" over a listed set), a sentence with no citation and an overreach word, and a "Not backed" string that a test file holds. Fix the citation, cite the defining line, put the citation directly after the clause it backs (a number in a sentence that cites for something else fails), word the sentence to the test's case ("in the test", "in this case", "the test shows"), or drop the claim; rerun until it exits 0. With `--points` it also prints the `Counts:` line. It also lists, without failing, every sentence with an overreach word or a count, and any whose cited lines are all comments. A doc whose claims all come from the caller's list has no repo citations, so the checker exits 2: skip this step for it and say in its header that no citations were checked.
   **Self-check before step 8.** Run the same command with `--sheet` for each doc: it prints every claim with its cited lines under it. Read each claim against those lines, not against your memory of them, and ask the rules above of it (the test's own value, a branch the code skips, the asserting line, copied names and numbers, a title or comment as the only source). Fix what fails, then rerun the check.
8. **Check every claim (required).** The script cannot tell whether a line supports a sentence. After the docs are written, start fresh checker sessions (not the writer, and not a session that saw the writer's reasoning). The writer builds each slice and its flag list (the step 7 output for those doc lines) and hands the checker `references/check-brief.md` as written, the slice, the repo path, the flag list and `points.json` with the left-out list. A claim is any sentence, bullet or table row, header included. Cut slices at headings, about 100 claims or fewer each, so the checker reads every cited line itself. The brief sets the bar: every claim judged HOLDS, WRONG, OVERSTATED or UNSUPPORTED from the checker's own read of the code.
   Fix every claim that is not HOLDS: reword it to what the lines show, cite the line that does show it, or move it to "Not backed". If a fix changes which points are used, rerun step 7 for the header counts. Run step 7 again and send each changed sentence, with its paragraph, to a new checker. Stop when a re-check of every changed sentence returns all HOLDS; the text a checker last judged is the text you ship. Write `CHECKS.md` beside the docs: claims checked, the first-pass counts of each verdict, the number of rounds, and the final counts (all HOLDS). A doc with an unchecked claim is not finished.
9. **Publish only if asked.** Publish to shartifacts (skill `using-shartifacts`) only when the caller says the docs are for Michael to review.
10. **Report.** Give the folder, the header counts, how many claims are inferred, what sits under "Not backed", the `Voice:` line, the citation check result and the `CHECKS.md` counts (first-pass WRONG, OVERSTATED and UNSUPPORTED, rounds, final). Say what you did not read.
