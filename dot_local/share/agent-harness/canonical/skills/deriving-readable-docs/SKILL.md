# Deriving readable docs

Turn any repo into one guide a person can read cold. Code is the source: what a sentence says about the product rests on the code line that defines it. The repo's own words (README, `docs/`, help text, comments) give intent and names. Tests are optional evidence: they confirm a behaviour when the repo has them, and nothing needs them.

Output: `GUIDE.md` in a folder outside the repo, default `~/.local/share/derived-docs/<repo-name>/`, or the caller's path. Part 1 is about 1,000 words of plain English, each sentence tagged `[A4.3f9a]` with the id of the appendix line it restates (an id sits at the end of each appendix line and stays with it). Part 2 is the appendix: A1 surfaces and A2 evidence (printed by scripts), A3 the product as a whole, A4 and on one section per capability, A-last what nobody read.

Every mechanical step below is a script call. Agents write sentences and judge claims; scripts count, cut, join and score. `<skill>` is this skill's folder.

## Rules for every sentence

The cited lines must show everything the sentence says. `references/drafting.md` is the method the writers follow.

- One behaviour per sentence, at most 18 words, citations excluded. A longer one is split, and each part keeps its condition.
- Every claim ends with a citation in exactly this form: backticked `path/to/file.ext:LINE` or `path/to/file.ext:START-END`, relative to the repo root; several may share one pair of backticks. Cite the line that defines the behaviour, with its flags, branches and early exits. Nothing else in backticks may look like `word:number`.
- A claim that rests on a README, doc, comment or test title says so in the sentence ("README", "code comment", "in the test"). A claim taken from a name or the layout, without reading its body, is labelled **inferred**.
- A rule too long or spread out to read end to end is not described as a behaviour. State the surface only: "`--foo` takes a number (help text)".
- "No test covers X" is never written. `assemble.py` prints what tests cover.
- Add no security, privacy or threat sections unless the caller asks. No sentence about the document itself.

## Procedure

1. **Orient.** Record the repo name and `git rev-parse HEAD` (no git: say so). Make a work folder outside the repo. Read the README and `docs/` only for names and users.
2. **Surfaces.** Run `python3 -I <skill>/scripts/surfaces.py <repo> --json > surfaces.json`. It lists commands, flags, routes, config, entry points and the rest, each a real `path:line`. It misses registries, hand-parsed arguments and UI code. One scout session (Sonnet) reads the README, `docs/` and `surfaces.json` and writes `scout.txt`: the capabilities a user would name, one per line, as the name appears in the code. Run `python3 -I <skill>/scripts/surfaces.py <repo> --resolve scout.txt > scout.resolved`. A name it cannot find, and a `WEAK MATCH` (only a script or test holds it), is dropped.
3. **Tests, if any.** Run `python3 -I <skill>/scripts/harvest_points.py <repo> > points.json`. `assemble.py` reads it for A2: tests found, surfaces named in tests, surfaces never named. With no tests, the file is `[]` and A2 says so.
4. **Budgets.** Whole guide 6,000 words; Part 1 1,000; A3 600; A4 and on 3,900 shared by capability. Under 30k lines, halve all three. Printed rows are not counted.
5. **Frame and section writers.** One fresh Opus session per writer, never one for the whole repo: a frame writer for A3 and one per capability for A4 and on, briefed as the last part of `references/drafting.md` says. Plan 6-10 appendix sections in all, grouping scout names that share code. Each writer runs `python3 -I <skill>/scripts/stamp.py draft.md` (an id for each line; it refuses a line of two sentences: one sentence a line), saves and marks its condition sheet, writes its evidence file, audits its own sentences and runs `python3 -I <skill>/scripts/check_citations.py draft.md <repo> --max-words <budget> --max-sentence-words 18 --audit work/audit.md`, which also wants `work/guards.md` and `work/evidence.md`. Load the `no-ai-slop` skill (Skill tool) in each writer.
6. **Part 1.** Put the appendix parts in the work folder as `A3.md`, `A4.md` and so on, run `python3 -I <skill>/scripts/stamp.py <work>/A*.md`, then `python3 -I <skill>/scripts/assemble.py <work> <repo> --index`. A separate Opus front writer gets the appendix sentences plus the index, and nothing else, and writes `part1.md` in six sections: What it is, How to start, What you can do, How the parts fit, What it needs and keeps, What it does not do. How to start holds the first install or run step; each step restates a cited appendix line. A sentence keeps the conditions and the source label ("The README says") of the lines it restates.
7. **Assemble and gate.** `python3 -I <skill>/scripts/assemble.py <work> <repo> -o GUIDE.md --clean` prints the header, A1, A2 and A-last, joins the parts, and writes `GUIDE.clean.md` without tags. Then `python3 -I <skill>/scripts/lint_main.py GUIDE.md <repo> --surfaces surfaces.json [--fixed fixed-ids.txt]` gates Part 1. Send every FAIL back to the front writer and assemble again. It fails a sentence that drops a condition or source label of a line it tags, and a guide with no How to start.
8. **Check citations.** `python3 -I <skill>/scripts/check_citations.py GUIDE.md <repo> --max-words <the whole-guide budget from step 4> --max-sentence-words 18`. A missing line, a number or quoted name not in the cited lines, or a sentence over 18 words fails. Fix and rerun until it exits 0.
9. **Check every claim.** Run `python3 -I <skill>/scripts/slice.py GUIDE.md <repo> --out slices`. It cuts slices of at most 60 claims and writes `slice-K.claims.txt` (one claim id `N.k` a line) and `slice-K.flags.txt`. Start one fresh Opus checker session per slice (not a writer), and hand it `references/check-brief.md` as written, its claims file, the repo and its flags file. The report names its slice, has one `read` row for each claim with the line it read, and ends with the Counts line; name a Part 1 slice's report file `part1-*.md`. Fix by editing the section files and running `stamp.py` again: a line keeps its id, so Part 1 tags hold. A fix that splits a sentence splits it, and does not paste the checker's wording (that breaks the 18-word limit). A Part 1 finding is fixed by a fresh Opus front-writer session, not by the lead. Only changed sentences go back to a fresh checker: list their ids and run `slice.py ... --ids changed.txt --out slices-fixN --record-fixed fixed-ids.txt`. Run at most 2 fix rounds after round 1. A sentence that still fails after round 2 is cut, or narrowed to what the code shows.
10. **Score.** `python3 -I <skill>/scripts/score.py <name>=<reports folder> --doc GUIDE.md --repo <repo> --slices slices --out score`. It checks each report's counts add up, that it has a row with a real line for every claim of its slice, then prints the rate, errors per 1,000 words, words per claim and claims by cause. The rate uses the checkers' claim count and prints any difference from the script's.
11. **Reader check.** Follow `references/reader-check.md`: a fresh Opus reader sees Part 1 only (`python3 -I <skill>/scripts/score.py --reader GUIDE.md`), answers five questions with quotes, and `score.py --reader GUIDE.md --answers answers.md` verifies the quotes and prints the unknown words; a fresh Opus grader marks the answers against the code. The bar: 5 of 5 correct, and `lint_main.py` passes. The unknown-word list goes in the report and does not gate. One fix round (a fresh Opus front writer; it does not reword a sentence in `fixed-ids.txt`), then report the result.
12. **Publish and report.** Publish to shartifacts (skill `using-shartifacts`) only when the caller says the guide is for Michael to review. Report the folder, the words against each budget, the score line, the reader-check result and what was not read.
